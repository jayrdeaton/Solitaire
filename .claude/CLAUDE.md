This file provides guidance to Claude Code when working in this repository.

# Solitaire

Eleven classic solitaire games in one ad-free, self-contained app (Klondike, Spider, FreeCell, Pyramid, Yukon, Golf, TriPeaks, Canfield, Scorpion, Forty Thieves, Aces Up, in `src/games/`), built with Expo. Part of the `@rific`/`@tastic`/InfiniteToken app ecosystem - depends on `@rific/auto-paper`, `@rific/feedback-press`, `@rific/focus-chain`, `@rific/gestures`, `@rific/splash-gate`, `@rific/toaster`, plus `@tastic/profile` (+ its `@tastic/core`/`@tastic/hud` peers) for player identity (a color + short tag, shared across the fleet via an iOS App Group) - unlike the fleet's physics-driven games, there's still no board-physics or split-screen engine here, just tap/drag card-game logic. A selected player's color/tag only drives cosmetic colors (the card back, the felt and the Paper theme, `src/components/theme.ts`, see the root-felt note below) - settings stay global regardless of who's selected, but stats are kept both device-wide and per profile (`StatsState.profiles`, keyed by `Profile.id` and filled for whichever profile is active when a deal resolves, see `src/stores/gameStats.tsx`).

**Expo has changed.** Read the exact versioned docs at https://docs.expo.dev/versions/v57.0.0/ before writing any code - don't rely on general Expo knowledge, this app is on SDK 57 specifically.

## Commands

```bash
npm run lint          # expo lint .
npm run fix            # expo lint . --fix
npm test               # Jest
npm run typecheck      # tsc
npm run verify         # lint + test + typecheck
npm run doctor         # expo install --fix && expo-doctor
npm start              # Expo dev server
npm run client          # Expo dev server (dev client build)
npm run build:web       # verify, then the web export for games.infinitetoken.com/solitaire/
```

Always run `npm run lint` before finishing any task. This is an app (`"private": true`, no publish scripts) - `verify` doesn't include a build step.

**Builds and OTA updates:** the `build` and `update` scripts are plain `eas build` and `eas update`, with profiles in `eas.json` (`development`, `preview`, `production`). Pass the profile through, e.g. `npm run build -- --profile preview` or `npm run update -- --branch production --environment production --message "..."`. Nothing in them runs `verify`, so run `npm run verify` first. An OTA update also bumps `otaVersion` in `src/constants/release.ts` (the version label players see), committed before publishing. They used to be `@rific/updater`'s `rific-updater-build`/`rific-updater-update` bins, which @rific/updater 0.7.0 removed; the package stays for its OTA update hook. `build:web` is the one exception: it chains `npm run verify &&` before the web export (see "Web on games.infinitetoken.com" below).

## Tooling

Onboarded onto the shared `@infinitetoken` config packages (`eslint-config`, `jest-config`, `tsconfig`) - previously hand-rolled its own `eslint-config-expo`-based config, `jest-expo`-preset-direct config, and `expo/tsconfig.base`-extending tsconfig (the same pattern documented in [Swirlio](../Swirlio/.claude/CLAUDE.md)'s and [BoxHockey](../BoxHockey/.claude/CLAUDE.md)'s CLAUDE.md).

`npx expo install --fix` + `npm update` genuinely found real staleness here - more than any other app surveyed so far: `@expo/metro-runtime`, `@react-native-async-storage/async-storage` (a full major version, `3.1.1` → `2.2.0` - the installed version was actually *ahead* of what SDK 57 expects), `expo-linking`, `expo-router`, `react-native`, `react-native-gesture-handler` (`^3.1.0` → `~2.32.0`, also a major-version rollback), `react-native-reanimated`, `react-native-safe-area-context`, `react-native-worklets`, `@types/jest`, and `jest-expo` were all misaligned with the installed Expo SDK, in both directions. **`npm update` alone wasn't enough to reach a stable clean state - a genuine wrinkle not seen in the other 7 migrated apps.** After the first `expo install --fix` + `npm update` pass, `npm outdated` showed `Current === Wanted` for everything, but `npx expo install --check` had newly drifted on two packages `npm update` had bumped past Expo's compatible range per their own loose semver (`react-dom` `^19.2.3` → resolved `19.2.8`; `react-native-screens` `^4.26.2` → resolved `4.27.0`) - `npm update` respects a package's declared semver range, which doesn't know about Expo's own SDK-compatibility matrix. Fixed by running `expo install --fix` a second time (pins both back to their SDK-57-compatible versions); confirmed clean afterward on both fronts: `npx expo install --check` reports up to date, `npm outdated` shows `Current === Wanted` for every dependency (remaining `Latest` values are all major bumps outside declared ranges, a deliberate-upgrade decision, not routine maintenance).

**On the web target specifically, `@tastic/profile`'s `ProfilesManager` create/edit flow doesn't reliably commit via the Name field's Enter key, and its documented "commit on unmount" fallback doesn't fire either** - confirmed live: typing a name and pressing Return left the row still open/editable, and navigating away via `router.back()` (Settings → Profiles → back) didn't commit it, because React Navigation's web implementation keeps the previous screen mounted (hidden, not unmounted) across a stack pop, unlike native. Worked around during verification by seeding `AsyncStorage`'s web-backing `localStorage` key (`solitaire.profiles.v1`) directly rather than fighting the picker UI.

## How-to-play guide (2026-09-24)

A first-run, replayable "How to Play" flow, built on `@tastic/hud/guide` (the light-peer subpath of `@tastic/hud`; see that package's own CLAUDE.md, "The guide subpath"). Same shape as LightCycles, Snake, AirHockey, BoxHockey and Pong. **The code word is `guide` everywhere, never "onboarding"** (the fleet's word for a round countdown).

- **Content:** `src/constants/guideSteps.tsx`: `getGuideSteps({ touch })`, three cards, pure and hook-free. `touch` is `useIsTouchPrimaryDevice()` and only swaps the verb (tap vs click). **Per-game rules are deliberately NOT here**: `RulesDialog` (`constants/gameRules.ts`, plus its shared Scoring paragraph) already covers each of the 11 games; the guide teaches the suite-wide things a first-timer can't work out alone, and every sentence has to be true in all 11 games at the default settings:
  - **Tap to Play** (Click to Play on desktop): "Tap a card for its best move. Pyramid pairs take two taps." Ten games run the game's `autoMoveHint` on a tap (each screen's `handleCardTap`, Spider's `handlePressCard`; the tableau pick is `engine/autoMove.ts`'s `pickBestTableauTarget`). Pyramid's tap only SELECTS (`handleSelectPyramid`; a tap on the partner removes the pair, a King goes on one tap), so the first sentence would be false there without the scope. **Dragging is deliberately not taught:** a drag can't make every move. The discard pile has no `DropZone` (`games/shared/DiscardCell.tsx`), so an Aces Up discard (its main move; the card still lifts because `hasLegalMove` counts discards) and a Pyramid King both snap back when dragged there (`AcesUpScreen`'s header and `handleDrop`, `PyramidScreen`'s `attemptDrop`). Making the discard a drop zone in those two screens would make a drag line true again.
  - **Lower Is Better**: "Score is moves plus seconds. The first move starts the clock." `engine/score.ts`'s `computeScore` (every game's readout, through `GameChrome`); `useGameSession`'s `registerMove` starts the clock (a stock draw counts); `statsEngine.ts` keeps the LOWER best score. The clock half is otherwise only in the Rules sheet's Scoring paragraph.
  - **Get a Hint**: "Tap the light bulb in any game to see a move you can make." `GameChrome`'s `lightbulb-on-outline` Hint button, in both layouts; `engine/hint.ts`'s `findHint` rings a legal move, or the stock when a draw is the move, and each screen's `handleHint` toasts when there is none. Home has no light bulb, so this doesn't describe what's behind the card. The info button is left out for exactly that reason: every Home tile shows it (`renderRulesButton` in `app/index.tsx`).
  - Art: `src/components/GuideArt.tsx` (`GuideCardPlay`, whose `pointer` is `'finger'` on touch and `'mouse'` on desktop, also picking the screen-reader verb; the pressed seven is outlined in round dots (the Hint picture's ring shape, traced by `roundedRectDots`: React Native's dotted border is square-dotted on Android and the web), with the click cursor in its lower right on desktop. It used to be a fingertip circle centred on the card, which cut across the big pip (it sits below the card's middle; Jay, 2026-10-17); `GuideScore`; `GuideHint`, the Hint button plus a ringed, glowing seven and the eight it goes on; only the card to move is ringed, as in a game). Plain Views plus Paper Icons/Text, colored from `useAutoPaperTheme()`: no Skia/SVG, and deliberately NOT the in-game `PlayingCard`/pile components or `@tastic/cards` (the mini cards are Views). None of hud's shared art (swipe, key caps, split phone) fits a card game.
- **Copy rules (Jay, 2026-09-24):** Title Case titles; one-word buttons (hud's defaults Skip / Back / Next / Ready, no `finishLabel`); bodies of 90 characters or less; no questions, no filler, no vague nouns, no em dashes; every sentence true for everyone who can see it (all 11 games, default settings); don't describe what's already visible behind the dialog; never tell a desktop player to tap or a touch player to click. **Plus a Solitaire-only rule: every body fits in TWO lines** of DejaVu Serif Bold (the app-wide Paper font, `ThemeProvider`'s `fontFamily`) at bodyMedium 14/20 on a 264pt page (a 360dp phone; `guideSteps.test.tsx` caps bodies at 62 characters as a proxy). A third line makes the turned card too tall, see Wiring. Measure a new body against the real TTF (`node_modules/dejavu-fonts-ttf/ttf/DejaVuSerif-Bold.ttf`, e.g. with PIL's `getlength` plus 0.25 letter spacing per character), since widths vary per letter. **Considered and left out:** dragging (see Tap to Play), the info button (visible on every Home tile behind the card), tap-the-readout-to-hide-the-footer (portrait only: false in the wide layout and in a desktop window), the shake on a card with no move (in Pyramid a shake means a failed pair), hint cycling (not true when the hint is a stock draw or the only move), Undo's hold-to-repeat (never checked with a mouse on web), auto-save (it shows itself the first time you come back).
- **Wiring:** `src/components/GuideHost.tsx` (the Redux seen version + `useRotation()` passed as `rotation` + the steps -> `GuideProvider`), mounted in `_layout.tsx` around `<ThemedStack />` inside `OrientationBridge`, so inside PersistGate, the auto-paper/Paper provider and the orientation provider. **The card is the one dialog here that is NOT under an in-frame Portal.Host:** `GuideProvider` renders it beside its children, so its Paper `Portal` lands in the nearest host above `GuideHost`, which is `FeedbackPressProvider`'s own `Portal.Host` (`FeedbackBridge` passes `paper={RNPaper}`), outside every rotated frame. It is handed the frame's live rotation as a transform instead of `rotation={0}` (the same `useRotation()` Home's `RotatedFrame` turns by, so it sits at the angle Home's Settings dialog visually does). Home (`app/index.tsx`'s `Home`) calls `useAutoShowGuide(!resumeGame)` BEFORE the cold-launch resume `<Redirect>` (hooks stay unconditional): held back whenever the launch is about to drop into a saved game, so the guide can never open over a live deal. Settings row: `SettingsDialog`'s `showHowToPlay` (default false) -> `BaseSettingsDialog`'s `onShowHowToPlay`; turned on ONLY at Home's call site, **never in `GameChrome`**: the score counts elapsed seconds, so a guide opened mid-deal would cost the player score.
- **Turned card height:** the fleet's rotation is fake (the OS window stays portrait), so a quarter-turned card's layout HEIGHT has to fit the window's short edge. hud handles that for every game now: `getGuideCardSize` swaps the axes for +/-90, widens the card, caps its height, shrinks the art under 480pt, and each page scrolls if it still doesn't fit (found in this app's review, fixed upstream 2026-09-24). Keeping every body to two lines meant that scroll was never needed at the default text size; since the card's "How to Play" header (2026-10-15, see Dialogs) a page fits a 402pt-tall window exactly and scrolls a little on a 375 or 360pt-wide phone held sideways. Not yet checked on a real device held sideways.
- **Persistence:** `src/redux/guideSlice.ts` (a `createGuideSlice` binding) mounted as `guide` in `store.ts` (its own key: Reset Stats never touches it). `GUIDE_VERSION` (`src/constants/guide.ts`) is what an existing player is stamped with. Players who already have a root store (otaVersion 4+, 464e3e1) are grandfathered by the slice itself. **Players last on otaVersion 3 (25532f0, 2026-09-12) or earlier have NO root store** (it arrived in 6dbe6e5), so `store.ts`'s `persistConfig.migrate` is `createReturningPlayerMigrate(AsyncStorage, LEGACY_STORAGE_KEYS)`: the 20 literal keys 25532f0 really wrote (the 11 `solitaire.game-in-progress.v1.<game>` saves, `solitaire.stats`/`.achievements` via `@tastic/achievements` 0.1.1's namespace, settings, theme, last-active-game, profiles, guest color, sound, vibrate; per-key source in guideSlice.ts), read from that commit's source, not today's constants. otaVersion 1 (5f3078f) and 2 (f065784) wrote the same set. `solitaire.stats.v1.<gameId>` is NOT listed: those builds only ever read it. **Early-write rule:** nothing may write one of those keys before PersistGate opens, or a fresh install is taken for a returning player. Today `solitaire.settings.v1`, `solitaire.theme-settings.v1` and `solitaire.last-active-game.v1` belong to providers mounted OUTSIDE PersistGate (`SettingsProvider`, auto-paper's `ThemeProvider`, `LastActiveGameProvider`), but none writes on mount (auto-paper's `onChange` skips the first render, see `@rific/core`'s `createSettingsContext`; the other two write only from their setters) and every setter call at boot (`ProfileThemeSync`, `OrientationBridge`, the game screens) comes from inside PersistGate. Only finish/skip writes; a replay never does. Bump `GUIDE_VERSION` only for a real controls/scoring change: every player sees it again.
- **Not built:** any in-game entry point (deliberate, see Wiring), and per-game first-visit tips (RulesDialog is the per-game layer).
- **Tested:** `guideSteps.test.tsx` (three illustrated cards per platform, Title Case, bodies <= 90 characters and <= 62 as the two-line proxy, no questions or dashes, touch vs desktop differ only by the verb, the Pyramid scope, no drag promise, the exact score copy, the hint card naming the light bulb and not the info button, each card's art component and pointer, the art's screen-reader labels, the score picture matching `computeScore`), `guideSlice.test.ts` (this app's binding; `LEGACY_STORAGE_KEYS` namespaced, unique, all 11 saved-deal keys, no `stats.v1` keys; the migrate over each key gives `GUIDE_VERSION` and no keys or a failed read gives 0, also end to end through real redux-persist, including a fresh install's second launch after the theme key was written; the real `persistConfig` has the migrate, imported under fake timers because store.ts's persistStore leaves redux-persist's 5s failsafe timer), `components/homeGuide.test.tsx` (the redirect guard), `components/settingsHowToPlay.test.tsx` (the prop -> row), `components/gameChromeHowToPlay.test.tsx` (never in a game). **Not verified live:** nothing here was run on a simulator, device or web build: the card's look (mini-card ink in dark mode, art sizes on a 320pt phone), the transform-rotated card under a fake landscape hold (the 358pt height is an estimate from hud's styles and the real font's widths, not a measurement; check it on a 375pt iOS simulator and a 360dp Android emulator held sideways, at the default and a larger text size), the Settings row, and the auto-show on a genuinely fresh install.
- **Packages:** the guide ships in the published `@tastic/hud` 0.13.0 (`./guide`, with `createReturningPlayerMigrate`). Solitaire has no yalc links any more (2026-09-25: `.yalc/` and `yalc.lock` removed, `@tastic/cards`/`hud`/`profile` installed from npm). ## Testing

- Tests live in `src/__tests__/`, mirroring the source subfolder structure for the games (`games/freecell`, `games/klondike`, `games/pyramid`, `games/spider`) plus a top-level `engine.test.ts`

**The deal animation's destination measurements raced the React commit they depended on, and silently dropped ~90% of the board when it lost.** `CardRegistry.measure(cardId)` (`components/dragdrop/CardRegistry.ts`) only resolves once that card's own registration `useEffect` has run - but the deal's initial implementation called `measure()` for all 28 destination cards *synchronously, right after* `setState(newTableau)`, before React had even committed that render, let alone run the new cards' registration effects. Confirmed live: this raced the *previous* deal's still-registered (but about-to-be-replaced) cards against the *new* deal's not-yet-registered ones, and mostly matched neither - 25 of 28 destinations came back `null` on one measured run, silently excluding those cards from `entries` and leaving them hidden forever (a card whose destination is `null` never gets added to `deal.start()`'s entries, so it never fires `onCardLanded`, so its id never leaves `dealHiddenIds`). The fix: never call `CardRegistry.measure()` synchronously after the `setState` that mounts the new cards. Instead, stash a "deal is pending" token and do the actual measurement from a `useEffect` keyed on `[state]` - React fires effects bottom-up per commit (children's before parents'), so by the time a *parent* component's `[state]`-effect runs, every child `PileView`/`DraggableTableauCard` for that same commit has already run its own registration effect. See `KlondikeScreen.tsx`'s `pendingDealTokenRef` for the pattern; `PyramidScreen.tsx`'s equivalent doesn't need it for the *destination* side, since its destinations are computed analytically (`cardPosition()`) rather than via `CardRegistry.measure()` - it only measures two container refs (the stock pile, the triangle container), which aren't subject to this per-card mount race. It still needs the same `[state]`-deferral for the *origin* side, though: those two container refs are themselves behind Pyramid's `if (!state) return <GameLoading />` branch, so on the very first mount they aren't attached yet at the moment `startNewGame` calls `setState` - calling `runDeal` synchronously right after that (as it originally did) measured two still-null refs and silently skipped the deal (cards just appeared with no animation, every time you navigated to Pyramid fresh). Fixed by giving Pyramid its own `pendingDealTokenRef` + `[state]`-effect, same shape as Klondike/FreeCell/Spider - confirmed all four now defer their initial `runDeal` this way.

**A second, unrelated bug found in the same session: reused React keys across separate deals silently stalled a handful of cards forever.** All 52 cards' ids are shuffle-independent (`${suit}-${rank}-${deckIndex}`, see `engine/deck.ts`) - a fresh deal reuses the exact same ids as the one before it, just redistributed. If `deal.start()` is ever called again while a previous deal's ghosts are still mounted (shouldn't happen in normal play, since the skip-overlay covers the "New Game" button during a deal too, but is easy to trigger via rapid/automated interaction), React reconciles by id and reuses the *same* `DealGhostCard` instance for a repeated id rather than unmounting and remounting it - meaning its `useSharedValue` position and its "already notified" guard ref never reset, since both only initialize on a genuine first mount. Fixed by folding a monotonic generation counter into each ghost's React `key` (`DealLayer.tsx`'s `generation`), forcing a real unmount+mount - and therefore a full state reset - on every `deal.start()` call regardless of id overlap with the deal before it. The same generation is also stamped on every slot (`deal`) and checked in every callback (`generationRef`, bumped synchronously in `start()`, which also `cancel()`s the old slots), because the old slots stay mounted - timers live - until the commit AFTER `start()`: a timer firing in that gap used to report a stale card into the new deal.

**Pyramid's pairing/King removal lands cards in a real discard pile (`PyramidState.discard`, `rules.ts`) instead of just deleting them.** A solo King flies as a single card via the shared `ghost` (`DragGhostLayer`/`useDragGhost`), same as every other single-card flight in this app. A pair instead flies as **two cards travelling independently at the same time**, each from its own real board position straight to the discard pile (`PyramidScreen.tsx`'s `startPairFlight`/`PairFlightGhosts`/`FlyingPairCard`) - not merged into one stack, and not one card visiting the other before either moves. The single shared `ghost` can only ever animate one origin/delta for its whole group (see `DragGhostLayer.tsx`), so two cards converging from different starting points needed their own small overlay instead - the same "N independent simultaneous ghosts" idiom `DealLayer`/`WinCascadeLayer` already use for the same reason (see `DealLayer.tsx`'s doc comment), just with each ghost getting its own independent origin/destination instead of a shared one. Each card's flight is its own `withSpring` at `FLIGHT_SPRING`, the one time every flight in this app takes, so the two cards of a pair leave together and land together. For a drag-completed pair, "first" is still sitting mid-drag in the shared `ghost` at drop time - its live position is read directly off `ghost.originX/Y.value + dx/dy.value` before handing off to its own independent flight and retiring that ghost (`ghost.hide()`). Two earlier shapes of this flight were tried and rejected first: originally "first" visibly flew onto "second" before the (already-merged) pair continued on to discard, as two distinct legs; replacing that with a single flight of the two cards already merged into one stack (skipping the first leg, but still one shared ghost) was also rejected - both read as one object moving, when the actual ask was always two cards animating independently to the same destination at the same time. The discard pile itself (`PyramidScreen.tsx`'s `DiscardCell`) measures its position like `stockViewRef`/`triangleViewRef` (a plain view ref, `measureView()`) rather than `FoundationCell`'s per-card `CardRegistry` registration - there's only ever one discard pile, not a slot whose occupant identity keeps changing. **Undoing a pairing/King removal now animates too, flying each card independently from the discard pile back to its own original spot** (`PyramidScreen.tsx`'s `undoRemoval`, `RemovedCardRef`) - the mirror image of the forward removal flight: one shared origin (the discard pile, which doesn't move) fanning out to each card's own destination, reusing the same `PairFlightCardSpec`/`PairFlightGhosts`/`startPairFlight` machinery (generalized so each card's spec now carries its own `to` as well as its own `from` - the forward flight shares one `to` across cards with independent `from`s, the undo flight shares one `from` with independent `to`s). `UndoEntry` gained a `removedCards: RemovedCardRef[] | null` field (the PileRef each removed card came from) alongside the pre-existing `move: MoveInfo | null` for stock draws - the two are mutually exclusive. **Every undo resolves ALL its endpoints BEFORE it commits, and mounts its ghosts in the same synchronous stretch as the revert** - a pyramid-cell destination is pure math (`cardPosition` + the measured `triangleViewRef`), a waste-bound card's is the always-mounted waste container (`wasteViewRef`; there is one waste slot, so it is the same place the card's own registration would say), and the discard/stock are plain containers too. The old shape (commit the revert, then a `[state]`-effect measured the destinations and only then started the flight) left the restored cards visible NOWHERE for a frame or two (the discard already showing its older top, the cards hidden, no ghost yet) before the ghosts popped in. Undo of a draw and of a recycle measure both endpoints first and do `ghost.show` + `beginFlying` + `setStockHidden(true)` + `commitState` + `flyTo` in one stretch; undoing a draw also freezes the stock slot (`stockHidden`) until the returning ghost lands, instead of showing the returned card at once. The restored card(s) have to be hidden (`pyramidHiddenIds` for a pyramid destination, reusing `flying`/`wasteHiddenCount` for a waste one) in that same commit - React batches same-tick `setState` calls - to avoid a frame where the restored card flashes fully visible before its ghost covers it (same reasoning `startNewGame`'s `setPyramidHiddenIds(dealtIds)` already relies on for the initial deal). A waste-bound card's `flying` entry ends with ITS card's landing (the pair ledger's `flying.cardId`), not with the whole pair, so a landed Ace is not hidden again while the Queen is still on its way. `dealHiddenIds`/`isDealHidden` were renamed to `pyramidHiddenIds`/`isHidden` to reflect that the same hidden-until-landed mechanism now covers two different reasons a pyramid cell's card might be flying in, not just the initial deal. A card whose destination cannot be measured (a rare edge case) simply has no ghost and is not hidden, rather than left stuck invisible forever. **Fast play:** pair flights are independent - `pairFlights` is a list with a per-flight ledger keyed by gen (a landing settles only its own flight; a single slot let the next pair replace the last one, so its ghosts vanished mid-air and its `activeFlightCount` claim never settled), and the discard shows the topmost card not in `discardInAir` under the ghosts (`DiscardCell`'s additive `settledCard`, the `FoundationCell` idiom). Every action claims its flight synchronously (`claimFlight`, generation-stamped) and **re-validates against `stateRef.current` after its measurement awaits** (`replayMove`, then one synchronous `commitRemoval`) - committing the pre-await `result` overwrote whatever committed meanwhile and let a double-tapped King be removed twice. Pinned by `pyramidScreenQuickPlay.test.tsx`, whose mocked measurements have a latency so taps really overlap. **Overlapping draws and the waste:** the waste slot's frozen copy of the pre-flight top goes stale once draw flights overlap (each landed ghost vanished onto the card from before the whole stream), so `wasteInAir` (the waste's `discardInAir`) tracks the drawn cards still flying and the screen passes `StockWaste` the additive `settledWasteTop` (the topmost waste card not in it; omitted - `undefined` - keeps the frozen copy, which every other game and every non-draw flight still uses). **A card is never acted on while its own draw ghost is airborne:** a tap/drop on it (or a pair completed with it) waits - `whenLanded`, re-checked at every landing, bounded by `DEFER_MAX_WAIT_MS` - so the card visibly arrives, THEN flies on (measuring the hidden real card would start a second ghost from a slot the drawn card has not reached, shown twice); a draw waits out a recycle's group ghost still flying into the frozen-empty stock, and a recycle waits out draw ghosts still landing (it would pick the airborne card up twice) - plain draws still overlap freely. The check comes AFTER the measurement awaits and does not yield when nothing is in the way, so an earlier tap's commit is never interleaved with a later one's. **Every such wait is a LOOP, not a single check** (`while (!gate() && budget.left() > 0) await whenLanded(gate, budget.left())`, inline at all three call sites - `attemptMove`, `attemptDrop`, `handleDrawStock`): being resumed is not proof the gate still holds, because a landing resolves EVERY waiter whose predicate held at that instant and their continuations then run one after another - the first (a recycle) re-freezes the stock for the next, which used to draw from the freshly recycled stock while the recycle's group ghost was still flying into it (stock [5], waste [2, 3], three quick stock taps). The loop must stay inline (a helper looping inside an async function hands its answer back across a microtask boundary in which a sibling can change it again), and its deadline is ONE budget per action (`startDeferBudget`), not a fresh `DEFER_MAX_WAIT_MS` per resume. **`commitRemoval` drops a selection that names a card it removes** (`setSelected((sel) => removed.some(refsEqual) ? null : sel)`): an action clears the selection when it starts and may then park in the wait above, and a tap in that window selects the waste as `{waste, 0}` - "whatever is on top" - which, once the deferred pair had removed that card, pointed at the card that was UNDER it (highlighted, and paired by the next tap: a move the player never chose). A selection of an unrelated card made during the wait is kept. **New Game/restore retires every shared-ghost flight still in the air** (`trackFlight`/`hideAirborneFlights`: a King's, draws' - queued ones included -, recycles', undos'), after bumping `dealTokenRef` so their completions are generation-guarded; dropping `pendingFlightRef` alone left queued ghosts mounted for good.

**Pyramid's win is a SWEEP DEAL, then one chain from one pile.** rules.ts still folds whatever is left in the stock/waste into the discard ON the winning move (a won game's discard is all 52 cards, waste bottom-to-top then stock bottom-to-top - the order everything else depends on), so `won` stays game state exactly as before (clock, stat, save, recorded the instant it happens). But nothing flew for that fold, so the leftover cards now fly: the winning removal's `commitRemoval` calls `beginWinSweep`, which claims a flight (`claimFlight`, while the removal's own claim is still held, so `settled` never blips true) and marks every leftover as in the air on the discard (`discardInAir`, so the pile's top is always a card that really landed). Once nothing but the sweep's claim is outstanding (`activeFlightCount` down to 1 - the last removal has landed), `runSweep` deals the leftovers through the existing deal machinery (`useDealAnimator`: same stagger `dealStaggerMs`, spring, throttled sound/haptics and skip-tap - no flight layer of its own), one card per swept card from its own pile (the waste slot for the waste's, the stock slot for the stock's; a pile that cannot be measured deals from the other one, only with no origin at all does a card simply land) to the discard, in the discard array's order, face-up (the deal layer cannot turn a card over in flight, and every swept card is face-up already). The board keeps showing the pre-fold piles (`winHoldView`, kept in `sweepUi.view`, keyed to the won state's identity) and empties each pile when its last card takes off - driven by the deal layer's own take-off signal, `DealAnimator.start`'s additive optional `onCardDealt(cardId)` (once per card, at the instant its ghost is drawn over the spot it leaves; reported for every not-yet-taken-off card when a skip lands the deal at once; silenced by a cancel/restart exactly like `onCardLanded`), `SWEEP_PILE_BLANK_LAG_MS` after the pile's LAST card, on the run's timers so `cancelSweep` clears it. A timer armed from the scheduled delays right before `deal.start` (what this used to be) runs on the wrong clock: the deal's own clock only starts once its ghost pool has rendered and mounted (several frames on a phone) and a card's real take-off is that clock + its re-based delay + the render of its launch, so the timer ran ahead and the pile sat empty until the ghost popped in (worst for a pile whose last card leaves at delay 0). Pinned by `pyramidScreenWin.test.tsx`'s mount-latency cases and `dealLayer.test.tsx`'s `onCardDealt` block. The deal's `onAllLanded` (or a skip, which lands everything at once) settles the claim exactly once; a New Game mid-sweep, or the reveal's fallback timer, ends it via `cancelSweep` (an empty `deal.start([])` is the deal layer's only cancel). Timeline: last removal lands -> sweep (up to ~1.1s for 24 cards) -> 400ms hold -> reveal, so `useWinReveal` gained an additive `maxWaitMs` and Pyramid passes 4s (nominal ~1.9s worst case against the default 2.5s was too thin for a phone's JS stalls). The reveal then launches ONE chain of all 52 discard cards (head = the card on top) from the discard container; the discard blanks only in the commit its ghosts mount (`cascadeHandoff`, now just the discard). **The chain keeps the usual 42ms between cards, so all 52 string out across the bounces behind the leader** (2026-10-17, Jay: "That's what the whole effect is for. So long as they all follow the leader and have enough spacing to not blur into a black streak"). From September it was squeezed into a 13-card chain's half second (`chainSegmentDelayMs`/`CHAIN_MAX_SPAN_MS`, ~9.8ms per card at 52, so it stayed within one bounce), and the stacked shadows of cards that close together read as a black streak down the chain's side; both are gone. `ChainSpec.segmentDelayMs` and `isGhostVisible`'s delay parameter remain, used only by tests. Pinned by `pyramidScreenWin.test.tsx` (a deal harness that follows the real deal's timeline; its 52-card case checks the chain has no `segmentDelayMs`). Don't split a pile into several chains or squeeze it again without asking Jay.

**Golf and TriPeaks sweep their leftover stock onto the waste before the cascade, too** (2026-10-17, Jay: "I'd like the remainder cards to be added to the stack before doing the win animation"). Both win with the tableau cleared, often with cards still in the stock, and the cascade carried only the waste, so those cards just sat in the stock under the celebration. `games/shared/useWinStockSweep.ts` deals them, top card first (as a draw takes them), face up, with the deal layer (`dealStaggerMs`, the deal spring, sound and skip-tap), from the stock slot onto the waste slot once the winning card has landed (`othersSettled`: no flight and no initial deal in the air). New Game, restore, an undo of the winning move and `runWinCascade` (the reveal's fallback firing first) call `cancel()`, which takes the ghosts out of the air with an empty `deal.start([])`. **Landscape rotation is a fake: the OS stays portrait-locked and the whole app is visually rotated** (`@tastic/core`'s `OrientationProvider` reads the accelerometer; `useRotation()` gives 0/90/-90/180). Every screen draws inside a rotated frame: each game via `withGameProviders` (`@tastic/core`'s `FakeLandscapeView`), and Home, Achievements and Profiles via `RotatedScreen` (see the `RotatedScreen.tsx` bullet below); the root layout's toaster and update dialog sit in their own frame laid over the whole `Stack` (`_layout.tsx`'s `RootOverlays`). Nothing in the app is left in physical portrait. Several things here exist only because of how that goes wrong:
- **Every rotated frame keeps ONE identical element tree at every angle.** `FakeLandscapeView` through 0.8.0 returned a different tree at 0deg vs +/-90deg (`<View>` vs `<View><View>`), so React unmounted and remounted the WHOLE game screen - every card, all providers, and Inner's state (undo stack, hints) - on every rotation. Measured in the simulator: ~700-800ms of JS per rotation versus ~90-250ms for the update it should be. This app carried a local stand-in (`components/RotatedGameView.tsx`) until `@tastic/core` fixed it upstream (identical tree since 0.9.x, `passThrough`/`rotation` props since 0.12.0), and swapped back to `FakeLandscapeView` on 2026-10-08. Don't reintroduce a per-angle branch in the tree. At 0deg/180deg `FakeLandscapeView` SPLITS the caller's style: the outer View gets the keys that place/size it in its parent (position/insets, flex/flexGrow/flexShrink/flexBasis, width/height/min/max, aspectRatio, margins, alignSelf, display, zIndex, transform/transformOrigin; the exact list is `OUTER_STYLE_KEYS` in @tastic/core's FakeLandscapeView.tsx), the inner one gets the rest (flexDirection/flexWrap included; `direction` goes to both) plus `flexGrow/flexShrink: 1, flexBasis: 'auto'` to fill the outer. Every call site here (`withGameProviders`, and hud's `RotatedFrame` for `RotatedScreen` and `RootOverlays`) passes just `{ flex: 1 }`, which lays out exactly as the old stand-in did (its outer was always `flex: 1`, its inner the caller's style); a new call site with padding, a background or an absolute style should check which View each key lands on.
- **The "wide" layout (`components/gameLayout.ts`) is what makes landscape playable.** Any window whose ROTATED footprint is landscape (`isWide`: a phone held sideways, an iPad, a desktop browser) drops the vertical chrome bands (portrait reserves 56pt top + 98pt bottom, which would eat 154 of a ~402pt-tall landscape screen): `GameChrome` puts the footer controls (Undo/New Game/Hint/Rules) in a column in the RIGHT side gutter (where the thumb is) and the moves/score/time readout in the LEFT one, hides the title (rules stay reachable from the info button, which only the wide column has), and the corner buttons stay put. Hiding the footer is portrait-only (there the footer floats over the board; in landscape it sits in a gutter and hiding it would give the board nothing back). The two gutters are PER-SIDE (`leftGutter`/`rightGutter`, each = its chrome column + its OWN safe-area inset): sizing both from the larger inset left ~44pt of dead space between the footer buttons and the board on the small-inset side of a phone held sideways. `useGameLayout()` gives every screen its `contentWidth` (net of the gutters) and `availableHeight`. Portrait is byte-for-byte unchanged.

- **Home is `router.dismissTo('/')`, never `router.replace('/')`** (`GameChrome.tsx`). `replace` mounted a brand-new Home on top of the one already beneath the game, so every round trip leaked one more live Home (each a full menu); `dismissTo` pops back to the existing Home and only falls back to replace semantics when nothing is beneath (a deep link or the cold-launch resume). `back()` errors in that no-history case and `dismissAll()` returns nothing for a single-route stack, which is why `replace` had been picked in the first place.

**Also landed (second pass):**
- **Saves are coalesced** (`stores/gameInProgress.ts`). Every move used to `JSON.stringify` the whole board plus the whole undo stack (each undo entry embeds a full state snapshot - ~1MB after 300 Klondike moves, several MB for a long Spider game) synchronously in the move's own commit, and a foundation cascade does dozens of moves back to back. `saveGameInProgress` now only remembers the latest object and writes it after 500ms of quiet (3s max wait during an unbroken burst); it also flushes when the app leaves the foreground, when any game screen unmounts (`useSaveInProgressBackstop`), and before every read, and `clearGameInProgress` drops a pending write so it can't resurrect a cleared game. A hard crash can lose only the last half second of moves. Covered by `src/__tests__/stores/gameInProgress.test.ts`. `lastActiveGame` also skips rewriting an unchanged value.
- **Deal ghosts are a small pool of reusable slots** (`DealLayer.tsx`: `GhostSlot`, `ghostPoolSize`, `LOOKAHEAD_MS`/`LAUNCH_TICK_MS`; the absolute-deadline departures, face-up launch cap and slot-idle coalescing added on top are described in the face-up bullet below). A deal used to mount a full `PlayingCard` per dealt card (~52 mounts + 52 unmounts of card art; measured at ~half of a deal's remaining JS cost). Now `start()` sizes a fixed pool from the delays (the most flights that can overlap, counting each ghost as occupied from 150ms before its flight to ~80ms after it lands: 17 slots for 28 cards, 31 for 52) and `launchDue()` hands each card to a free slot ~150ms before its flight, re-basing its delay onto the launch. The deal's clock starts when the slots have MOUNTED (the `[generation]` effect), not at `start()`, so a slow mount delays every departure uniformly instead of spending the first cards' delays and sending them off together; cards that are LATE after a JS stall are spaced `LATE_LAUNCH_MIN_GAP_MS` apart (on-time cards keep their scheduled time) so a hitch doesn't become a blob plus a second blob. A slot is launched imperatively (`launch(spec, order)`: shared values reset to the origin/opacity 0 *before* the React commit that shows it, so the previous landing spot never flashes) and is hidden again by React state (`job` -> null), NOT a UI-thread opacity write, so it disappears in the same commit the caller's `onCardLanded` reveals the real card (a UI write ahead of that commit would blink a card-shaped hole). A landed slot is offered for reuse only from an EFFECT after that commit (`onIdle`), never from the landing callback itself - relaunching it in its landing tick would write the reset to the UI thread ahead of the reveal. Face-down deals reuse identical backs (the slot's face element is `useMemo`'d, so a relaunch renders nothing); face-up deals re-render a face instead of mounting one. `order` becomes `zIndex` so a later card still paints above an earlier one whichever slot it lands in. Skip lands both the in-flight slots (`completeNow`) and the not-yet-launched queue; a restart mid-deal keys slots by `${generation}-${slot}` (same key-reuse guard as before). The click and buzz play on the deal's beat, not per card (see Haptics below). Covered by `src/__tests__/components/dealLayer.test.tsx`; verified on device for Yukon (52), Klondike (28) and FreeCell (52).

DealLayer's slot wrapper (`styles.slot`: absolute, top/left 0, only an absolute child) and DragGhostLayer's ghost container (only absolute children) laid out as exactly that. Ruled out on the way (each an A/B on the Simulator, not reasoning): the wrapper's zIndex/opacity toggling, the card box's size changing at its first face mount, Reanimated's synchronous transform path (animating `top`/`left` instead had the identical offsets), and card-view recycling alone (keeping the cards mounted only reduced it - the previous deal's pool and other unmounts feed the same pool). Guarded by `dealLayer.test.tsx`'s "ghost slot frames" and `dragGhostLayer.test.tsx`'s "ghost container frame" - nothing else about the layout needs the size, so it is exactly what a cleanup pass would remove. Pyramid's/Spider's/WinCascade's flight views have in-flow card content (non-zero frames) and are not exposed; a NEW overlay whose only children are absolute must set a size.
- **Unplayable cards dim once, for the whole board, after the deal - never card by card while it deals** (`games/shared/useDimAfterDeal.ts`, wired into FreeCell, Golf, Forty Thieves and Pyramid - the games whose deal leaves face-up cards buried; Spider/Canfield deal none, so they don't need it). A screen calls `hold()` with its New Game, `release()` when the deal has landed (its `onAllLanded`, and every bail-out path) and `releaseNow()` on restore; the dimming (`PileView`'s `dimUnplayable`, Pyramid's `dimHold`) is off while `held`, and turns on `DEAL_DIM_SETTLE_MS` (150ms) after the last landing - every buried card's scrim then fades in together (`dimFadeIn`/`HeldDimScrim`), and a `DEAL_DIM_MAX_HOLD_MS` backstop dims a deal that never reports back. Reanimated then committed animated props through the shadow tree (`IOS_SYNCHRONOUSLY_UPDATE_UI_PROPS` was off until 2026-10-17), where they raced React's own commits. So **`FadingDimScrim` hands over to the plain, React-owned scrim the moment its fade reports done** (`fadeInDimScrim`'s `onDone`, `DIM_FADE_BACKSTOP_MS` if the callback never comes) - a finished dim is never left depending on the last value an animation wrote. - **Face-up deals are slower on purpose, and hand off without a visible pop** (FreeCell, Yukon's face-up half, Forty Thieves, Golf). The compressed ~18ms stagger is fine for identical card backs, but a face-up ghost is a distinct readable card that costs a real React commit per launch (a court card is ~100-150 SVG nodes, 63% of a face-up deck's nodes; a face-down relaunch renders nothing), so those deals janked. `paceFaceUpDeal(entries)` (`dealSpring.ts`; applied in each of those four `runDeal`s right after the entries are built, before anything reads them) stretches only the gaps in front of FACE-UP groups to `FACE_UP_STAGGER_MS` (44ms; picked when every card clicked and buzzed, each throttled to one per 40ms; a deal now plays both on its own beat, see Haptics below) capped so the whole deal fits `FACE_UP_TARGET_TOTAL_MS` (2000ms): FreeCell ~33.7ms/2.0s (was 1.2s), Forty Thieves 44ms/2.0s, Golf 44ms/1.8s, Yukon 28 backs at 18ms then 24 faces at 44ms/1.8s. The solved-board finish is the one exception: any move of the player's that leaves the board solved starts it (next paragraph). **An arm never outlives its cascade:** `useAutoFoundationCascade` disarms on every way out of its loop (ran dry, Auto-Move off, an undo, a 3s landing wait that ran out, misses) and drops an arm its effect can't start at once; `useAutoFinish` drops a move's permission when its loop ends or it can't follow (Auto-Move off, an undo), and keeps it only while the board isn't solved yet (a cascade a foundation play set off may still make it so). **A SOLVED board finishes by itself after any move of the player's, and its pace ramps up** (Jay, 2026-10-12, asked for it to start after ANY move; 2026-10-14 changed his mind: "I dont want it to start automatically, I want it to also wait for user interaction to play a card to the foundation, and I want the speed to ramp up, instead of just immediately flying in to the foundation"; 2026-10-17 changed it back: "I want auto play to start automatically after cards are all revealed and sorted highest to lowest in games like klondike and yukon and freecell", "and whatever else", so every game that has the finish; the ramp stays). `useAutoFinish` (FreeCell, Klondike, Yukon, Canfield, Forty Thieves; Spider and Scorpion build no foundations card by card, so a sorted board there is not one foundation moves alone can clear):
- **Solved** (each game's `canAutoFinish`): not already won (`isFullyAutoCompletable` is TRUE on a won board), nothing hidden (no face-down card anywhere; the stock, waste and Canfield's reserve empty), and every remaining card clears by foundation moves alone (the NON-draw `isFullyAutoCompletable`; Forty Thieves' own, since its 8 foundations are not one per suit). FreeCell hides nothing, so its `canAutoFinish` is just every column sorted. The hidden-card checks are the point: the draws-aware finish through the stock reads face-down and stock cards, and a plain column move setting it off would give the stock order away. That one still needs a foundation play, unchanged.
- **Trigger:** ANY move of the player's, tap or drag, to any pile, that leaves the board solved (`finish.afterPlayerMove(from)` next to `cascade.afterPlayerMove(to)`: a column move that turns the last face-down card over, one that empties the waste or the reserve, a foundation play), or the cascade a foundation play set off, the moment it makes the board solved (the move's permission is kept while the board isn't solved yet). Two things never start it. A move that takes a card back OFF a foundation (`from` a foundation): it stops one still running, and the card isn't sent straight back up. And an undo, a resume or New Game (`finish.suppress()` next to every `cascade.disarm()` there; in `startNewGame` itself, since the win banner calls it directly): undoing a card off a solved board leaves it solved, and it would fly straight back up. The player's next move starts it again. A player's draw never sets it off (a draw always leaves the stock or the waste with a card). Honors Auto-Move to Foundation.
- **Hand-off:** every game's cascade `computeNextStep` (FreeCell's `nextSafeCascadeStep`) returns null once the board is solved, so the cascade ends and the finish takes over at its own pace; otherwise both loops fight over the same cards (misses, and three misses end a loop). A draws-aware sweep through the stock switches to the finish pace the moment it empties the stock and waste.
- **Pace ramps up:** `finishGapMs(i)` (dragSpring.ts) is the gap in front of the finish's i-th card: `FINISH_RAMP_START_MS` (= `AUTO_PLAY_STAGGER_MS`, 96ms, so a cascade handing over to the finish doesn't slow down) for the first, then each gap keeps `FINISH_RAMP_FACTOR` (0.85) of what is left above `FINISH_STAGGER_MS` (`scaledMs(30)` = 48ms, the top speed): 96, 89, 83, 77, 73 ... ~59 by the 10th card, ~50 by the 20th. A miss doesn't advance the ramp. Those three constants are the knobs. Flights unchanged (`FLIGHT_SPRING`, so cards to one foundation still land in order). The gap runs on a FIXED clock: each card leaves its gap after the card before it LEFT, not after that card's measurement and commit (the old loop slept a full gap after each commit, so the real gap was 96ms plus that overhead). A card slower to measure than the gap is followed at once. 48 is just above `useCascadeFeedback`'s 45ms floor, so a step whose measurement comes back quicker than the one before can occasionally lose its tick. The hook owns the wait for a card whose own pile is still landing (`isLanding`, bounded by `FINISH_LANDING_WAIT_MS`, now in `useAutoFinish.ts`; a wait that runs out is a miss). Every screen's `firePlay` takes a third `stillWanted` check (default `cascade.isArmed()`; the finish passes `isAllowed`).

- **The safe-card cascade** (`useAutoFoundationCascade`, engine mechanism A) starts from the player's tap or drag of a card to a foundation. Like every game's cascade (see below), its cards overlap.
- **The finish** (`useAutoFinish`, engine mechanism B) starts as soon as the whole board can go up on foundation moves alone (`canAutoFinish` - every column sorted highest-to-lowest, freecell cards included) after any move of the player's, or once the cascade a foundation play set off makes it so - without waiting for that move to land. Pinned by `the last card leaves one stagger after the card before it...`. `nextSafeCascadeStep` returns null the moment the board is finishable, so the two never both fire at one settle.
- **Auto-played cards follow the player's card at once and overlap, in every game with auto-play** (`useAutoFoundationCascade`, FreeCell/Klondike/Yukon/Canfield/Forty Thieves). The cascade used to send one card per settle - each card waited for the one before it to LAND, the first one for the player's own (a full flight plus two measurements and a couple of renders each), which read as "way too slow" (Jay, 2026-10-02). Now it is a loop that starts the moment it is armed (its `[state]` effect runs right after the arming move's commit) and sends every card `AUTO_PLAY_STAGGER_MS` (96ms) after the one before LEFT (a fixed clock since 2026-10-17, like the finish's; it used to count from each card's commit, after its measurement) - the first one 96ms after the player's own card, while that is still in the air - so ~5 cards are in the air at once. Because every flight takes the same time (see the flight-pace paragraph below), they land in exactly the order they left, and the gap is purely how quick the stream reads. The ONE thing a card waits for is its own pile to stop landing (`isLanding`, from `useFlightConcurrency`, kept live in `updateFlying` rather than read off a render): picking up a card whose own ghost is still airborne shows it twice (a card the sweep just drew onto the waste, a card the player just dropped there). A draw/draw-and-play waits the same way for the stock and the waste (the deal layer flies one draw-3 batch at a time; a second `deal.start` would cancel the first). After a wait the card goes at once, with no extra gap. The hook has no `settled` input any more; a wait that runs out (3s) ends the cascade (the next foundation play starts a new one). Every screen's `firePlay` resolves `true`/`false` (committed or not), for the miss count. One gap for every auto-played card: the old separate sweep gap and the `sweepingRef` latch are gone. - **Every auto-played step is its own undo entry, in every game with auto-play** (FreeCell, Klondike, Yukon, Canfield, Forty Thieves), so one Undo takes back exactly one card and the player can stop where they like. **Undo is a queue, every press is one undo, and undos overlap each other's flights - a held Undo streams the cards back like the auto-play streams them up** (2026-10-07; Jay: holding Undo "only undoes one move every other click"). Every game's `handleUndo` used to refuse to start while ANY flight was in the air, and the hold repeated on a fixed 400ms `setInterval` (`@rific/feedback-press`'s `useHoldToRepeat`) against a ~540ms real undo flight: every other tick was dropped, and still clicked. Now:

**Every card flight takes ONE fixed time, there is ONE pace knob, and a ghost is only ever retired at its spring's REAL end.** `dragdrop/dragSpring.ts`'s `FLIGHT_SPRING` (scale-1 225ms = 360ms at the default) is every flight: tap-to-move, undo, draw-1, a recycle, every auto-played and finish card (`DragGhostLayer`'s `flyTo` on a `show()` flight), Pyramid's pair flights (`FlyingPairCard`), Spider's completed-run flights (`FlyingSequenceCard`) and Klondike's/Canfield's draw-3 fans and their undo (through the deal layer: `DealAnimator.start`'s optional 6th `spring` argument, which also sizes the ghost pool and times the landing check) - however far it goes (Jay, 2026-10-01). Distance-scaled flights let a short hop overtake a long one to the same pile (two quick taps, or an auto-played card after a tap), and `FoundationCell`'s `settledCard` counts in-air cards, so the overtaken card showed on the pile while still airborne; and once flights overlap, a stream's pace is its gap, not its flight. Two exceptions: **a drag's drop** (`flyTo` on a `showLive()` flight - `flyTo` takes no pace options, it decides by `source`) settles over `dropSpringFor(the distance the finger left)` (scale-1 130-320ms = 208-512), because the card is usually nearly there and a full flight would leave the ghost covering the real card after every drag; and **everything else through the deal layer** (`DEAL_SPRING`, 280ms, unscaled - `start`'s default: deals, Spider/Scorpion stock deals, Aces Up rounds, Pyramid's win sweep, Klondike's legacy cascade-return undo). `SNAP_BACK_SPRING` (240ms) is unchanged too. `FLIGHT_TIME_SCALE` (1.6) multiplies the flight and drop durations. `scaledMs(ms)` is how any constant that must follow a flight derives from it (never hard-code a second copy): `AUTO_PLAY_STAGGER_MS` (`scaledMs(60)` = 96) and `FINISH_STAGGER_MS` (`scaledMs(30)` = 48, the solved-board finish's top speed), so the auto-play streams overlap their flights the same way at any pace, `useAutoFinish`'s `FINISH_LANDING_WAIT_MS` (2 x `springSettleMs(FLIGHT_SPRING)` = 966), `GameChrome`'s `UNDO_HOLD_REPEAT_MS` (= `AUTO_PLAY_STAGGER_MS`, see the undo paragraph above), Pyramid's `DEFER_MAX_WAIT_MS` (3 x a flight's settle = ~1.45s, so a deferral can never expire before its own draw ghost can land) and `SWEEP_WIN_REVEAL_MAX_WAIT_MS` (twice the nominal last-removal + sweep + hold timeline). Deliberately NOT scaled: `DEAL_SPRING`/`dealStaggerMs` (the deal), `SNAP_BACK_SPRING`, `useWinReveal`'s 400ms hold (a beat after the LAST landing, whatever the pace) and its 2.5s max wait (still ~3.7x the slowest single flight), `useCascadeFeedback`'s 45ms floor (a sound-pool limit, not a pace). **Reanimated's duration-based `withSpring` `duration` is the PERCEPTUAL duration: the spring really runs 1.5x that** (springUtils.ts's `perceptualCoefficient`), **and its solver caps stiffness at 8000, which with the default mass of 4 is reached at ~184ms: every shorter duration silently ran as the SAME ~283ms spring.** So the old 40-170ms (scale 1) sweep/auto-play flights were ~283ms springs whose ghost was retired at 40-170ms, with up to ~180px still to travel - the "cards vanish partway through" report. `FLIGHT_SPRING_MASS` (0.1) lifts the cap (critically damped motion depends only on sqrt(stiffness/mass)); the springs are exact down to ~30ms. Every timer that covers a spring uses `springSettleMs(config)` = `ceil(1.25 x duration + 33)`, never the bare `duration` (`DragGhostLayer`'s `settleAfter` - snapBack included - Pyramid's `FlyingPairCard`, Spider's `FlyingSequenceCard`; the deal's own timer is left at the bare `DEAL_SPRING` duration - measured 2.5px short of a 300px flight (7px of 900px) with the spring two frames late, judged not visible; a deliberate follow-up if it ever is): the 1.25 puts the tail under 0.4px for any distance, and the 33ms (two 60Hz frames) is the UI thread starting the spring after the JS timer that covers it - absolute, so it is added rather than folded into the factor (a flat 1.3 leaves 2.6px of a 100px sweep flight). `src/__tests__/components/dragSpring.test.ts` drives Reanimated's OWN `withSpring` frame by frame and requires < 1px residual at the retire time for every config at 60-900px (worst 0.68px, with the spring starting two frames late; the old timer left 50-310px on the sweep tier), and that every flight really ends at 1.5 x its duration. **Same-source hand-off rule (`DragGhostLayer.tsx`):** `showLive`'s persistent gesture values are shared by every drag from one slot/column, so a flight only sits on them WHILE ITS DRAG IS IN PROGRESS - `DragFlightHandle.release()` (called by `PileView`/`DraggableCard` as the first thing at drag end, before any await: a drop can sit in a hit test, a measurement or Pyramid's deferral for hundreds of ms) hands the ghost values of its own holding the same position. The ghost reads BOTH value sets from its first render and a `handedOff` shared value, written last, switches it (no re-render, no remount, no seam - cloning values under a mounted ghost, tried before, needs a re-render and jumps). After release a next drag from the same source can never touch the flight, applied or not; only a SNAP-BACK in progress (the very card being picked up again) and a drag that never released are still ended by a new claim (`liveOwnersRef`). `PileView` also captures its drag's own flight BEFORE the hit-test await (it used to read `flightRef` after it, so an overlapping drag's drop was applied with - and flew - the wrong ghost), and both `PileView` and `DraggableCard` stamp each drag with a token so a late drop/snap-back outcome never un-hides the cards under a NEWER drag. ## Scoring (audited 2026-10-14)

- **Score = moves + seconds, lower is better** (`engine/score.ts`'s `computeScore`, the one formula: GameChrome's readout, WinBanner, the recorded stat).
- **A move** is one `session.registerMove()`: every board change a player could make, tap or drag, a stock draw or recycle, a Spider/Scorpion stock deal, an Aces Up round, a Pyramid pair or King, AND every auto-play (the cascade, the solved-board finish, the draws-aware sweep's draws, recycles and draw-and-plays, which count as two) - Jay, 2026-10-14: with auto-plays free, turning Auto-Move off raised the score; now it only saves taps. NOT counted: Undo presses (and an undo never takes a move back off the count), hints, Spider's run removal and Pyramid's win sweep (rules, not moves a player could make).
- **Variants** (`engine/variants.ts`): one game under one rule set, the unit stats are kept in (`StatsState.variants` is keyed by `VariantId`) and par is set for. A game's DEFAULT variant keeps the bare game id (`'klondike'` = Draw 1, `'spider'` = 1 Suit, `'canfield'` = Draw 3, `'scorpion'` = Assisted...), so stats from before variants carry over into it with no migration; the rest are `<game>-<rule>` (`'klondike-draw3'`, `'spider-4suit'`...). Each screen names its deal's variant from the rule it was DEALT with (its own state, e.g. `klondikeVariant(klondikeDraw)`), not the live setting, and passes it to the win/loss hooks and every `record*` call; the hooks derive the game (`gameOfVariant`) for the save. Per-game figures ("Klondike Solved", Games Solved, totals) sum over a game's variants (`getGameWins`/`getGamesWon`); streaks are per variant. The Stats screen shows each game's default variant always and the others once played.
- **Expert par** (`engine/par.ts`, `parFor(variant)` = `{ moves, seconds, score }`; plain "par" until 2026-10-17, see Personal par below): moves = the median winning move count of a simulated Hint-following player (a little randomness, up to 10 tries per deal, 300 deals per variant, on the real `rules.ts`; 2026-10-14), seconds = the moves a player decides (all but foundation plays in the five auto-play games) x `SECONDS_PER_DECISION` (3, the one time knob), score = moves + seconds. ESTIMATED, not measured: Spider 2/4 suit and both Forty Thieves rules (the simulated player never won), and Golf No Wrap / Aces Up rest on 9 and 2 wins. **Re-measure with `npm run par`** (`scripts/simulate-par.mjs`, ~40s, deterministic; `--only <prefix>`, `--deals`, `--tries`) after any change to a game's rules or to Hint: it bundles the real rules with esbuild (with `@tastic/cards` aliased to its plain `src/types.ts`) and prints a PAR_INPUTS block to paste, commenting out variants with under 20 wins. A new variant needs a controller in its `CONTROLLERS` map or it stops. WinBanner shows the player's par (below) under each number, plus "Score N% under your par" ("expert par" before a first win): the percentage is the score's alone, with no "Lower is better" since par already says it, and no period (Jay 2026-10-17). **The trophy and "You Won!" take the medal the score earned, in metal** (`playerParMedal` in `engine/par.ts`, `games/shared/MedalHeader.tsx`, Jay 2026-10-17), against the player's par; against expert par (`parMedal`, before a first win) bronze at par or over, silver for any amount under, gold from 35% under (`GOLD_MEDAL_PERCENT_UNDER_PAR`, the Low Score achievement's gold line), rounded like the "Score N% under par" line. Each is a gentle top-to-bottom metal gradient (`MEDAL_METALS`: a touch lighter at the top, a touch deeper at the bottom, no hard step) over a 2pt stamped drop shadow, the same in both modes: flat colors (the tier colors mixed with black) read as brown, dull silver and mustard gold in light mode, and he asked for a sheen. A polished-chrome version with a pale highlight and a hard horizon just below the middle was tried first and dropped: it read as old-school WordArt and cut the trophy into two bands. `MedalHeader` redraws hud's `DialogHeader` layout (its 64/32pt icon, gaps and title variants) because `DialogHeader` takes one flat color. Native masks a gradient View (`experimental_backgroundImage`) with each glyph through `@react-native-masked-view/masked-view`, the pair auto-paper's `FadingScrollView` uses; the web clips a CSS gradient to the letters (`backgroundClip: 'text'`), since the web MaskedView only draws the mask. Seen in headless Chrome on the web build, all three medals in light and dark: readable, silver the palest on the light frosted card. **Not seen on a phone**: the native masked path is unverified. Not the Low Score achievement's own tiers (bronze at par, silver 20% under), which are lifetime milestones. Expert par is also in the Rules sheet's Scoring paragraph (GameChrome's `par` prop; Home's sheet has none) and on the Stats screen next to each best ("· expert par 345"). The speed/fewest_moves/low_score achievements (same ids, so unlocked tiers stay) are now best/par ratios across every variant (`getBestParRatio`): at par / 20% / 40% under on time, at par / 5% / 10% on moves, at par / 20% / 35% on score; the Overall section shows one "Best Score" vs expert par instead of the raw cross-game bests, which only ever named the quickest game.
- **Personal par** (Jay, 2026-10-17: expert par was out of reach, silver rare and gold never, and he wanted it to follow each player and "still feel rewarding without being easy"): a win's medal is measured against the player's OWN last `RECENT_WINS_KEPT` (20) wins in that variant. `playerParFor(variant, recent)` gives `{ kind, moves, seconds, score, goldScore }`: each number its own median (so they needn't add up), `goldScore` the best fifth's last score (`floor(n/5)`-th best: the 4th of 20, so about 1 win in 5; null under five wins, so gold needs five wins on file), `kind: 'expert'` (= `parFor`) with no wins yet. `playerParMedal`: bronze at or over (rounded, so "at your par" is bronze), silver under, gold at or under `goldScore`, never without silver. The bar follows the player both ways, so a steady player gets silver or better about half the time and gold about 1 in 5 (pinned by a simulation in `winBanner.test.tsx`). **Stored** in `redux/recentWinsSlice.ts` (persisted in root): by player (profile id or `GUEST_PLAYER_ID`), then variant, oldest first, `{ score, moves, seconds }`. `stores/gameStats.tsx`'s `recordDealWon` takes the par from the store BEFORE adding the win (`lastWin: { variant, par }` in the context) and WinBanner (now given `variant`, not `par`) judges the shown score against `lastWin.par` (expert par if it names another variant), so a win reached again after an Undo, which is recorded once, still gets its own score's medal. A player's reset and a deleted profile drop theirs (`stores/playerData.ts`), Reset Stats on All Profiles everyone's. Stats keep only a best per variant, so nothing from before fills it: every player started on expert par. The Stats screen shows "Your Par" per variant for one player (the one picked, or guest on a phone with no profiles; not All Profiles). The achievements stay on expert par. Pinned by `winBanner.test.tsx` (the card, `playerParFor`, the medal rates) and `stores/playerData.test.tsx` (measured before joining, per player, the cap, resets). Seen on the web build in headless Chrome (402x874): with no wins a seeded Klondike win showed expert par and silver; with ten wins of 330-420 on file a 322 showed gold, "Par 375" and "Score 14% under your par", and joined them (Stats: Your Par 370). Not seen on a device.
- **The clock** (`useGameSession`) starts with the first move, stops at the winning commit (Spider: the winning move, before its last run sweeps), and PAUSES while anything holds it (`setPaused(reason, paused)`, a set of reasons): `'app'` whenever the app is not `active` (a call, the app switcher, the home screen), and `'dialog'` while GameChrome's Rules or Settings is open (Jay, 2026-10-14; the New Game confirm doesn't pause). A first move or a resume made while held starts held. It used to keep running in the background, so time away counted only when the OS kept the app alive. Elapsed is banked in ms, so pauses don't drop part-seconds. Time on Home doesn't count either: the game screen unmounts and its save holds the elapsed time it was left at.
- **A save holds the elapsed time from when it was MADE**, so `useSaveInProgressBackstop` saves again (through the screen's own guarded `save`) on unmount and when the app leaves the foreground, as well as every 10s. Before, leaving a game handed back up to 10s of clock every trip.
- **Win recording reads `session.getMoves()`/`getElapsed()`**, never a render's `session.moves`: an auto-played winning card commits after a measurement await, and a move the player made during it is only in the live count (`checkWin(next)` takes no move count any more).
- **Losses:** `record.losses` (labelled "Lost" on the Stats screen) is both a New Game over a deal in progress and a dead board (`useStuckLossCheck`). Both use `recordDealAbandoned`. **A dead board's loss is recorded when the player LEAVES it** (Jay, 2026-10-14): New Game (each screen's `handleNewGame`, which the LossBanner's New Game also calls) or leaving the screen (`useStuckLossCheck`'s unmount, which also clears the save). Undo out of it cancels it. It used to be recorded on arrival, which counted one deal twice after an Undo (a loss plus a win, or two losses). The dead board is never saved (the saves skip `stuck`), so a killed app resumes one move before it, the same as an Undo.
- Pinned by `components/gameSession.test.tsx`, `components/stuckLossCheck.test.tsx`, `gameChromeHowToPlay.test.tsx` (the dialog hold), `statsEngine.test.ts` (variants, par ratios), `games/shared/winBanner.test.tsx`, and the five auto-play games' screen tests (move counts).

## Hints (2026-10-14)

- **No more ping-pong.** Every game's `scoreHintMove` measures a move's runs the same way before and after it (`a` = the run the moving group's base card continued at its source, `b` = the run it lands on, net = max(count + b, a) - max(count + a, b)), so a move and its exact reverse score as opposites and a relocation that gains nothing scores 0; the size tiebreak only applies to a score already above 0. Aces Up gained a scorer (it had none, so Hint showed a lone card to the empty pile and back). Scorpion's already-complete K-A column moved whole into an empty column no longer earns the completion bonus. Klondike and Forty Thieves also score a waste play onto a column (it scored 0, so Hint drew instead); Forty Thieves' waste card into an empty column still scores 0. On top of that, `findHint` never suggests a SHUFFLE (`isShuffle`: scores 0 or less and its exact reverse is legal right after), which is what kept the ping-pong going on boards with nothing to draw (Yukon, FreeCell, Spider with an empty column, Scorpion's dealt stock); if that leaves nothing, Hint draws or reports none ("No helpful moves right now."). A followed-Hint simulation over 200 deals per game: Canfield, Aces Up and FreeCell 0 reversals; Yukon 20, Spider 1-suit 39, Spider 4-suit 8, Scorpion 8-9 (from thousands each), all after a move that turned a card over, which can't really be undone. Each game's `rules.test.ts` pins its case, `engine.test.ts` the shuffle filter. **Known, not fixed:** Spider's Hint never suggests filling an empty column so the stock can be dealt again; Aces Up's `isStuck` never declares a loss while a lone card can still move to an empty pile, though that move can never lead to a discard.
- **A run gets ONE outline, not a ring per card** (Jay, 2026-10-14), for a hint and a selection alike: `PileView` draws `RunOutline` (PlayingCard.tsx, the same `hintRing`/`selectedRing` style, so it looks like one card's ring stretched over the run) over the run's own box from `columnTops` (head's top to the bottom card's bottom, zIndex above every card, `layout={FAN_GLIDE}` so it glides with the column), and the run's cards draw no ring of their own. Per-card rings drew a ladder of lines across a run, and each hint glow spilled over the face of the card above. A single card keeps its own ring; a selection wins over a hint (as on one card); no outline while any card of the run is hidden. No screen passes a `selectedCount` above 1 today, so only hints show it. Pinned by `pileViewRunOutline.test.tsx`; the outline was NOT looked at on the simulator (the simulator tool's taps arrive late and kept landing on the wrong screen).
- **The ring marks only what to move** (`hintCountFor` rings the source run, never the destination; Pyramid rings both cards of a pair, `pairHinted`, since both leave), with a soft glow (`boxShadow` on `PlayingCard`'s `hintRing`) that breathes with the ring (`startHintPulse`, 1100ms to 0.4 and back). **Its color is the app theme's tertiary, lifted** (Jay, 2026-10-14: a theme color, muted like everything else, and not the card back's own hue, or a ringed card in a stack blends into the backs beside it): `theme.ts` fills TableColors' `hintGreen` slot (the name is `@tastic/cards`' type; nothing in that package draws it) with `getTonalColor(getTriadicPalette(cardBack, THEME_HARMONY).tertiary, HINT_RING_TONE)`. `ProfileThemeSync` seeds the Paper theme with that same muted card back, so this IS the theme's tertiary, only lighter (`HINT_RING_TONE` 0.62 in `constants/theme.ts`, so it reads on the dark felt by lightness, not hue alone). The card back is the theme's primary; the felt stays the card back's 180-degree opposite (Jay kept it over a triad felt), so the ring sits 120 degrees from the back and 60 from the felt. The guide's `GuideHint` uses the same color. Pinned by `hintRingColor.test.tsx` (8 profile colors, light and dark).
- **The glide** (Jay: "a ghost animation of one card going to another"): each press of the Hint button shows a see-through copy (0.7 opacity) of the hinted card or run lifting off, gliding onto where it would land (`HINT_GLIDE_MS` = `scaledMs(300)`) and fading there; the real cards never move. `components/hinting/HintGlideLayer.tsx` (`HintGlideProvider`, innermost in `withGameProviders`, so it paints over the board and under every real flight) draws it; `games/shared/useHintGlide.ts` measures the anchor card (CardRegistry) and the landing spot: the destination's top card (one fan step below it in a column, at the step the column uses now, `fanTops.ts`), an empty pile's drop zone, or a card-sized container for a spot that isn't one (Aces Up's and Pyramid's discard, `measureSlot`). It claims nothing, hides nothing and registers nothing, so no flight or undo waits on it; a board change drops it (on screen or still measuring). A drawStock hint has no glide (the stock is ringed), and neither has an Auto Hint (2026-10-15, Jay: the button shows the ghost and the outline, Auto Hint just the outline; each screen's `handleHint` skips `playHintGlide` on `request.auto`). ## OS portrait lock (2026-10-08)

The OS is locked to portrait on every device and the app draws all rotation itself (`@tastic/core`'s `OrientationProvider` reads the accelerometer). `@tastic/core`'s Expo config plugin (`"@tastic/core"` in `app.json`'s `plugins`) owns every native setting that depends on: `orientation: "portrait"`; `ios.requireFullScreen` plus a Portrait-only iPad orientation list (audit F009: without it Expo forces all four iPad orientations, so iOS turned the screen on top of the app's own rotation, and Split View, Slide Over and Stage Manager are the price); and `android:appCategory="game"` (Android 16 and later ignore the portrait lock on tablets and unfolded foldables, except for games). Don't set any of those by hand here, and don't add `expo-screen-orientation` (it re-enables upside down on home-button iPhones). The why behind each is in @tastic/core's README. Check the result with `npx expo config --type introspect`; it only takes effect in a new native build.

## Web on games.infinitetoken.com (2026-10-17)

The web build is served at https://games.infinitetoken.com/<game>/ with every other Tastic game on that one origin, so they share browser storage and, through it, `@tastic/profile`'s player roster (the web side of the App Group). Games-Web, the hub at games.infinitetoken.com, proxies `/<game>/*` to this project's own production deployment (see its CLAUDE.md). Before this, each game had its own subdomain. Same section in Hangman, LightCycles, Snake and Solitaire.

- **The build:** `build:web` runs `verify`, then `WEB_BASE_URL=/<game> expo export -p web --output-dir web-build/<game>`. `app.config.ts` (identical in all four) turns `WEB_BASE_URL` into `experiments.baseUrl` only when it's set: a base URL also reaches native bundles, asset paths and EAS updates, so it never goes in `app.json`. Expo writes the export flat and prefixes the URLs inside it, so the output folder is what puts the files under `/<game>/`, and this project's own deployment serves the same paths the hub forwards. Building more than one game locally: run them one at a time with `--clear`, or Metro's shared cache leaks one app's config into the next.
- **`vercel.json`** (identical in all four): `buildCommand` is `npm run build:web`, the output is `web-build`, `cleanUrls` is on, and a `/<game>/...` path that isn't a file rewrites to `/<game>/index`, the path `cleanUrls` gives `index.html` (the form Vercel's instant static serving answers; see the 2026-10-16 note). A request on the old `<game>.infinitetoken.com` domain (still attached to this project) redirects to the same path under `games.infinitetoken.com/<game>/`, and its `/privacy` to the hub's privacy page. The host pattern names the four games rather than matching any subdomain, so it can never match `games.` itself. The bare root has its own rule, because Vercel's `/:path*` doesn't match `/` (seen live on Solitaire v1.2.0 2026-10-17: `/klondike` redirected, `/` was a 404). The redirects stay temporary until the move is checked live.
- **Privacy and store links:** the per-game `public/privacy.html` is gone. The one privacy policy is the hub's `/privacy`, and `store.config.json` points there, with support at `/support` and marketing at `/<game>`.
- **Storage:** redux-persist's `keyPrefix` is `'<game>:'`, so this game's state is `<game>:root` in localStorage instead of the `persist:root` every game used to write, which on one origin would have been each other's state. REHYDRATE still reports key `root`, so `guideSlice`'s `persistKey` is unchanged. Any other key this game writes must be namespaced by the game too. The prefix applies on native as well; saves under the old key were abandoned (nothing has shipped).
- **Skia** (Snake, LightCycles): `canvaskit.wasm` is served from `/<game>/canvaskit.wasm`. Until `@tastic/hud` hands canvaskit a `locateFile`, canvaskit resolves it relative to the page, which only works from `/<game>/` and the pages directly under it; the hub redirects the bare `/<game>` to `/<game>/` for that reason.

The icons are opaque 1024px squares on `#FAFAFA` (light) and `#050505` (dark). Each splash is its icon's art on a transparent background. The `expo-splash-screen` plugin paints the same two colors behind it, at `imageWidth` 200. `expo.icon` is `icon-dark.png`, `web.favicon` is `splash-dark.png`, `ios.icon` is the dark/light pair, and there is no Android `adaptiveIcon` (Android uses `expo.icon`). The favicon is the transparent splash art, not the opaque icon, because it looks better in a browser tab (2026-10-16), so `splash-dark.png` has to read on both light and dark tabs. Snake is the only game whose light and dark art differ (its body and head fill). The other games keep two identical splash files so the config is the same everywhere. Icon and splash changes only take effect in a new native build. The splash fades out over 400ms in every game: each calls `SplashScreen.setOptions({ fade: true, duration: 400 })` next to `preventAutoHideAsync()`, because iOS doesn't fade unless told to (Android always does). Solitaire's call was missing until 2026-10-17 (`_layout.tsx`). It's a JS call to a native module every build already has, so it ships in an OTA.

## Safari shadow lines (2026-10-16)

Jay saw two faint vertical lines under the last card of a FreeCell column in desktop Safari, running down to where the column's old bottom card had been. Every card that leaves a column did it in WebKit: the shadowed Pressable sits inside the card's absolute wrapper, and when the card is removed WebKit does not repaint the part of the shadow outside the card, so its two side edges stay until something else repaints there (a forced repaint clears them; the DOM has nothing at that spot). Not the wrapper's idle `translateX(0)` from the shake style: dropping it changed nothing. The fix is `willChange: 'transform'` on web on PlayingCard's shadow style (`WEB_OWN_LAYER`), so each card is its own compositing layer and its pixels go with it. Don't remove it as noise. Chrome never showed it (its DOM is identical), native is untouched. Checked in a WKWebView window (the same WebKit as Safari 26.6) at 1300x720: without the fix 4 of 4 departures left the lines (three cards to freecells, one undo off a column), with it 0 of 8 (to freecells, to a column, and two undos taking cards off freecells). Not checked: Safari on an iPhone or iPad, and the GPU memory of ~52-104 card layers on a low-end phone's browser.

## Speeding through the stock (2026-10-16)

Jay watched his kids speed through Klondike's stock: quick taps sometimes did nothing, and the flip-over lagged. Every stock tap is one draw now, however fast, and a held stock deals by itself.
- **One press target for the stock** (`StockWaste`): a feedback-press `Pressable` (`testID='stock-pile'`, label Draw / Turn over) that stays mounted and fully opaque whatever it draws; the card back, the empty slot and the frozen look are art inside it, never pressable themselves. Three ways taps used to be lost: on iOS, NO tap reached the stock while a turn-over flew into it (about half a second), because the hidden stock is drawn at `opacity: 0` and React Native on iOS hit-tests no view under 1% opacity (`RCTViewComponentView`'s `betterHitTest`; the web does, which is why it never showed there); a press that began on the card and ended after the swap to the empty slot (or back) went with the unmounted one; and the last card's take-off hold ignored the tap. A tap now always goes to the screen, which decides. Never put a touch target inside a view hidden with opacity 0.
- **A tap waits instead of being dropped** (`games/shared/stockWait.ts`: a 16ms poll, 3s budget, the loop inline right before the commit, like Pyramid's `whenLanded`). Klondike's `drawCanGo`: anything waits while a turn-over's cards are still flying into the stock (the stock is drawn as it was, empty, until they land); in Draw 3 every draw waits while anything is landing on the waste; Draw 1 draws overlap freely. Canfield's: in Draw 3, or for a turn-over (it has no flight), while anything is landing on the waste. Pyramid already waited this way.
- **Draw 3 fans go one at a time.** Two quick Draw 3 taps (Klondike's option, Canfield's default) used to start a second `deal.start()` while the first fan flew, which cancels the first: its cards vanished mid-air and never reported landing, so the waste stayed frozen and Undo waited for good until a New Game. Seen fixed on the web build (fans one after another, Undo working after).
- **The flip-over turns cards back in mid-air** (Klondike Draw 1, `recycleWaste`): the last cards drawn, still flying to the waste, are peeled out of their flights (`peelInAir`, as a held Undo's and a tapped run's are) and go to the stock from where they are; the clump of landed cards takes off from the waste. Before, Klondike turned the waste over at once and the card in the air was drawn twice (flying in, and on top of the clump flying out). The waste keeps drawing the clump's top (`holdWasteTop`, the `wasteTakeOff` state: its own take-off hold is for the card in the air) until the clump's ghost shows. Draw 3 (deal-layer flights can't be peeled) and Pyramid wait for the cards to land instead.
- **Taps that waited are paced** (`createStockQueue`): they go `STOCK_QUEUE_GAP_MS` (`stockWait.ts`, the auto-play's 96ms) apart once the way is clear, not all in the landing's frame (three cards flying as one). Klondike and Canfield only: in Pyramid a tap on a card can be parked beside them and they must resume in tap order (a paced draw let a parked pair go first; `pyramidScreenQuickPlay.test.tsx`'s parked-pair cases).
- **Overlapping Draw 1 draws show the card that landed** (Klondike and Canfield pass `settledWasteTop`, as Pyramid does): the frozen copy of the top from before the whole stream was never refreshed while taps kept coming, so each landing card vanished onto an older one until the next landed.
- **Holding the stock** (`components/stockHold.ts`'s `useStockHold`, the `useUndoHold` loop): a draw (or turn-over) at the 400ms long press, then a draw `STOCK_HOLD_REPEAT_MS` (250ms) after each has started, until the finger lifts. 250 is so each card can be read and let go on (Jay, 2026-10-18: at the auto-play's 96ms it "flies through the cards way too fast"), yet a 24-card stock still goes through in about six seconds; it is the one knob, and queued taps don't use it. It never turns the waste over (`repeat: true` at an empty stock is refused), so it stops where the stock runs out; a hold started on the empty stock turns it over, waits for the cards to land, and deals on. Only where the stock turns over (`canRecycle`: Klondike, Canfield, Pyramid); in Golf, TriPeaks and Forty Thieves one hold would deal the whole stock, which never comes back. A screen's `handleDrawStock` takes `StockRequestOptions` (`repeat`, `cancelled` = the finger lifted) and resolves true once it has committed.
- Seen on the web build (402x874, synthetic pointer events 120ms apart): 30 taps through a whole stock and over the flip-over gave 30 moves, the turn-over went at once (turnaround), the waiting taps went as the cards landed and then ~110ms apart; a hold drew a card every ~105ms and stopped at the empty stock; Draw 3 fans one after another. Not checked on a device: the iOS tap fix itself (pinned structurally by `stockWaste.test.tsx`), and the feel. Pinned by `stockWaste.test.tsx`, `stockHold.test.tsx`, `slotTakeOffHold.test.tsx`, and the `speeding through the stock` describes in `klondikeScreenWin`/`canfieldScreenWin` (each fails on the old code).

## Haptics (2026-10-17)

Jay felt the deal stutter on his phone and asked whether the buzz fired on landing. It didn't (every card buzzed at take-off), but the rule now is: **a card buzzes when it is played, never when it lands**, and the deal and the auto-play buzz on a steady beat. `useCardSounds.ts` has the full list.
- **A press:** every card (and the stock) is a feedback-press `Pressable`, which buzzes at touch-down. That is a tap's only buzz: each screen's tap handler (`handleCardTap`, Spider's `handlePressCard`), the player's draws and turn-overs, and Pyramid's `commitRemoval` no longer buzz a second time as the card takes off (they still click). A held stock's repeat draws (`opts.repeat`) buzz, since nothing pressed them.
- **A drag's release** (`PileView`'s `handleDragEnd`, `DraggableCard`'s `handleRelease`): `hapticCard` once the drop stands. A refused drop's invalid sound and buzz play as the snap-back STARTS (`DragGhostLayer`'s `snapBack`), not when the card is back.
- **A deal** (`DealLayer.tsx`): click and buzz together on a beat picked from the deal's own schedule (`dealBeatTicks`: the first card, then the next card at least `DEAL_BEAT_MIN_GAP_MS` (60) later, so every Nth card of the regular stagger: 68ms for a 28-card deal, 72ms for a compressed 52-card one, 67-88ms face up). `runBeat` plays them on the deal's clock (`startedAtRef`), so a late timer never pushes the rest back; beats a JS stall made overdue are one beat, and a beat within half a gap of the last is dropped. A skip is one beat, Reduce Motion one for the whole deal. It used to be one click and buzz per card from each card's own take-off timer, throttled to one per 40ms: every second or third card at uneven gaps, ~25 iOS haptic calls a second on the main thread, where the flights are drawn. Every deal-layer flight gets the beat (initial deals, Spider/Scorpion stock deals, Aces Up rounds, draw-3 fans, the win sweeps, undo deals).
- **Auto-play** (`useAutoFoundationCascade`, `useAutoFinish`): each screen passes `beat: cascadeFeedback`, played the moment a card leaves on the hook's clock, before its measurement (`firePlay`/`fireDrawAndPlay` play none any more). The cascade's gap is now a fixed clock too. A plain sweep draw plays its own (a draw-3 fan's is the deal's beat).
- **The click keeps the beat too** (`@rific/feedback-press` 0.13.1+): its `useAudioPool` used to rewind a player (`seekTo(0)`) and only play once the seek resolved, on every trigger, and a seek resolves at uneven times, so the deal's clicks drifted off the buzz's beat. Each player now rewinds as its clip finishes (the clip is 0.1s and each of the 8 players comes round every ~0.5s), so a beat only calls `play()`. Not heard on a device.
- **Unchanged:** Undo (each undo clicks and buzzes, so a tapped Undo buzzes at its press and again as the card leaves), Spider's completed-run flight (a buzz per card at take-off), a Hint hold's hints.
- Pinned by `dealLayer.test.tsx` (`dealBeatTicks`, the steady beat, the stall, skip, Reduce Motion), `useAutoFoundationCascade.test.tsx` and `useAutoFinish.test.tsx` (the fixed clock and the beat before the measurement), `dragGhostLayer.test.tsx` (the release buzz, the invalid buzz at the snap-back's start). **Not felt on a device:** whether the deal still stutters on Jay's phone, and how the beat feels.

## Keep Awake (2026-10-17)

Every game screen keeps the screen from dimming and locking while it's up (`@rific/core`'s `useKeepAwake('game')` in `GameChrome`, which every one of the eleven game routes renders, released on unmount), unless the player turns off the Keep Awake row in Settings (default on, read live so the toggle applies mid-game). There is no `/game` route here, so `GameChrome` is the one place that covers them all; Home, Stats and Profiles don't hold it. One tag is safe because only one game screen is ever mounted: they're reached only from Home (its links and the resume `Redirect`), never from each other. Expo only keeps the screen awake by itself in development builds.

- **The setting is core's, not this app's:** `keepAwakeReducer` is mounted as `keepAwake` in `store.ts` (persisted like every key but `gameInProgress`), and `_layout.tsx`'s `KeepAwakeBridge` (FeedbackBridge's shape: `initialValue` from the slice, `onChange` dispatching `keepAwakeActions.initialize`) mounts core's `KeepAwakeProvider` with `expoKeepAwake={ExpoKeepAwake}` (`import * as ExpoKeepAwake from 'expo-keep-awake'`), just inside FeedbackBridge. Handing it the module is what turns the feature on: without it `useKeepAwake` does nothing and hud hides the row. `useKeepAwake` drops both expo-keep-awake rejections (web refuses a wake lock in a frame without the Permissions-Policy, and rejects a release when none is held). The same day's first version (`Settings.keepAwake`, an effect in `GameChrome` and dialog props) was replaced by this before it was committed.
- **It follows the player** like the rest of the Settings sheet: `PlayerSettings` has a `keepAwake` entry, `playerSettingsMiddleware` files and loads it with `sound`/`haptic` (merged over the live value, so a player filed before it existed keeps what is on screen). Pinned by `playerSettingsSlice.test.ts`.
- The row is `@tastic/hud`'s (0.23.0+): `BaseSettingsDialog` reads core's setting itself, with no props, and shows the row (caption "Stop auto-lock mid-match") only when `useExpoKeepAwake()` returns a module and the device is touch-first (native and touch-first browsers), like Lock Orientation. Needs `@rific/core` 0.4.0+.
- `expo-keep-awake` was already installed as a dependency of `expo`, so it is already in existing native builds; it's a direct dependency (`~58.0.3`, via `npx expo install`). No new native build needed.
- Same feature as AirHockey, BoxHockey, LightCycles, Pong and Snake (2026-10-15), and added to ArcheryDuel, Hangman, HexFleet and Solitaire on 2026-10-17. Jay chose to include the turn-based games: the OS auto-lock only counts touches, so a long think on a turn can lock a release build too. The hook's comment is Snake's except for that one clause (Snake names tilt, keyboard steering and watching the CPU).

## Animated props skip the shadow tree on iOS (2026-10-17)

Jay felt deals stutter on his phone. `package.json`'s `reanimated.staticFeatureFlags` turns on `IOS_SYNCHRONOUSLY_UPDATE_UI_PROPS` (Reanimated 4.7's way to set a static flag: `pod install` reads it into the Reanimated pod's compiler flags).
- **What it does:** each frame, Reanimated writes non-layout animated styles (opacity, transform, colors, border radii, shadows) straight to the views instead of committing them through the shadow tree. React commits still pick the latest values up from Reanimated's registry, and Reanimated writes its own values again right after every React mount, in the same main-thread pass. With it off, Reanimated skipped its commits from the start of each React commit until that commit mounted, so every ghost in the air held still for a frame or more and then jumped; a deal commits at every landing.
- **Measured** on the iOS 27 simulator with Release builds (arm64, one per flag value, the same JS bundle in both), each frame timed by a test-only magenta bar moved by RN's native driver along the bottom edge: frames mid-deal where every card held still between frames where they moved went from 95 in 24 Klondike deals to 0 in 23, and from 61 in 20 FreeCell deals to 0 in 21. Frames where the whole screen stalled did not change (about 1.6 per Klondike deal either way; FreeCell 27-31, the simulator drawing 52 shadowed faces at about 30fps), so those are not this flag's to fix, and a phone may differ.
- **Hand-offs checked** with a blip detector (a patch that changes for 1-3 frames and then returns exactly, its surroundings still before and after; the recorder's repeated frames dropped), every flag-on flag looked at frame by frame: the 44 deals, scripted presses on every card of seeded Klondike and Yukon boards (moves, shakes, auto-play, draws) followed by 40 undos 96ms apart (peels), Pyramid pairs, Kings and draws, the seeded FreeCell finish into the win cascade and fireworks, a Spider run flying to its slot, a drag and a snap-back. No hole, blank face, flash at an old landing spot or doubled card; every flag was a card moving more than its own size in a frame, a take-off or a firework, and the flag-on runs had fewer flags than flag-off in every case. For the dim fade see the dim-after-deal bullet.
- **What it costs: `measure` lags a slide.** `measure`/`measureInWindow` (and Reanimated's own `measure`) read the shadow tree, which now learns an animated transform only at the next React commit that carries Reanimated's registry, or at its 500ms settled-value sync (`FORCE_REACT_RENDER_FOR_SETTLED_ANIMATIONS`). A probe put the scoreboard toggle up to 55pt off for 0.3-1.6s after its slide while the clock was stopped; with the clock running, a moved press on the lowered scoreboard was still ignored about 10s later. RN's Pressable keeps a press only while the finger stays within 20pt (30 below) of where `measure` put the button at press-in, so a press that moved a little was dropped (Reanimated's docs list this caveat, issue 10121). Reproduced with the simulator tool's touch paths: flag off works, flag on ignored, flag on with the fix works. Fixed by widening the scoreboard's and the footer buttons' `pressRetentionOffset` by their slides (`GameChrome.tsx`, pinned by `gameChromePressRetention.test.tsx`). Nothing else here measures a view under a Reanimated transform except through the card shake (8pt at most); the fan glide is a layout animation, so flight measurements are unchanged, and UIKit picks the touched view from real positions either way. A new Pressable inside a view Reanimated moves needs the same widening (or a gesture-handler press, which hit-tests natively).
- **Seen in both builds, so not this flag:** a plain tap on the lowered scoreboard where Undo sits brought the controls back and also pressed Undo (the simulator tool's tap; a touch path with a little movement didn't). Not looked into, and not checked on a device.
- **Shipping:** it is compiled into the Reanimated pod, so it needs a new native build; an OTA can't carry it. It doesn't change the fingerprint (`@expo/fingerprint` reads only `package.json`'s `scripts`; 1f2cf54 with and without it), so the new build keeps the current runtime version, OTA updates reach old and new builds alike, and nothing fingerprint-based will ask for that build: start it by hand. iOS only (`ANDROID_SYNCHRONOUSLY_UPDATE_UI_PROPS` stays off). Not checked on a phone.
- **How it was measured, to redo it:** no app code changed for the test. A scratch copy of the repo (node_modules symlinked) got the harness pieces (the clock bar, an auto New Game, scripted presses read from a seeded setting, a `measure` probe), its bundle went through `expo export:embed` and `hermesc -emit-binary -O` into copies of the Release apps, with the copy's assets added at the app root (the symlink changes the node_modules asset paths) and `EXUpdatesEnabled` off in `Expo.plist`, so an OTA could not replace the bundle. The store was seeded before each launch under the `solitaire:` prefix; `store/seed/write-store.py` still writes the old `persist:` keys.

## Every dealt card leaked through its drag gesture (2026-10-18)

Jay: the game "starts to struggle as I keep pressing New Game". It was a real leak: every card a deal unmounted stayed in memory for the rest of the session, with its fiber, its worklets, its shared values and (through its animated ref's `ShadowNodeWrapper`) its native views, about 60 cards and 3.6MB of native memory per New Game in Klondike. Garbage-collection pauses grew with the live heap until play stuttered.
- **The cause:** the card drag gestures (`PileView`'s `DraggableTableauCard`, `DraggableCard`) called `runOnJS(handleStart)` / `runOnJS(handleEnd)` with the component's own callbacks. react-native-worklets keeps a native strong reference to every `runOnJS` target for as long as the worklet's serialized copy lives, and Hermes counts that as a GC root. The copy is cached for as long as the component holds its gesture, and the callback's closure holds the component, so root -> callback -> component -> gesture -> cached copy -> root: nothing in the loop is ever collected. Neither the WeakMap cache nor gesture-handler's `animatedHandlers` shared value is the retainer (patching each, one at a time, changed nothing).
- **The fix:** `callWorkletCallback`/`useWorkletCallback` from `@rific/core` 0.5.0 (they started as this app's own `components/dragdrop/workletCallbacks.ts`, which was deleted once core shipped a superset: any arguments, and the callback need not be stable). A worklet calls only the module-level `callWorkletCallback(key, ...args)`; the component registers its live callback under a `useId` key with `useWorkletCallback(callback)` (in an effect, removed on unmount). **Never hand `runOnJS`/`scheduleOnRN` a callback the same component also reaches its worklet from** (a gesture, an animated style, an event handler it holds). A one-shot animation callback the component doesn't hold (`dimScrimAnimation`'s `onDone`) can't form the loop. Since 2026-10-18 every call is `scheduleOnRN(callWorkletCallback, key, ...args)` from `react-native-worklets` (`runOnJS` is deprecated in Reanimated 4), and `dimScrimAnimation`'s `onDone` is `scheduleOnRN(onDone)` with no key.
- **Libraries fixed the same way (2026-10-18):** `@rific/toaster` 0.9.0 (its dismiss reaction held `handleDismiss` for every toast), `@rific/drawer` 0.8.0, `@rific/scroll-view` 1.1.0 and `@rific/resizable-input` 0.5.0 now use the same helper; this app installs toaster 0.9.0 (JS only, can ship in an OTA). Not verified on a device.
- **Measured** in a Debug build on the iOS 27 simulator, through heap snapshots taken over CDP (Metro's inspector, `HeapProfiler.takeHeapSnapshot`; the socket needs an `Origin: http://127.0.0.1:8081` header) while a harness copy dealt Klondike every 3 seconds: before, the heap grew 183 -> 431MB over 30 deals and the retained card worklets 60 a deal; after, 67.5 -> 80.7 -> 87.3MB at deals 10, 40 and 72, card worklets 26 -> 54 -> 58 (the live board plus the previous one), JS lag flat. In the Release build the leak showed as +18,000 malloc allocations a deal and JS lag rising from 254 to 346ms per second over 40 deals, with GC spikes growing to 900ms per second. The web build never leaked (no worklet runtime). Not checked on a device; the fix is JS only, so it can ship in an OTA.
