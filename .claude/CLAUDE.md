This file provides guidance to Claude Code when working in this repository.

# Solitaire

An ad-free, self-contained solitaire suite (Klondike, Spider, FreeCell, Pyramid) built with Expo. Part of the `@rific`/`@tastic`/InfiniteToken app ecosystem — depends on `@rific/auto-paper`, `@rific/feedback-press`, `@rific/focus-chain`, `@rific/splash-gate`, `@rific/toaster`, plus `@tastic/profile` (+ its `@tastic/core`/`@tastic/hud` peers) for player identity (a color + short tag, shared across the fleet via an iOS App Group) — unlike the fleet's physics-driven games, there's still no board-physics or split-screen engine here, just tap/drag card-game logic. A selected player's color/tag only drives the cosmetic card-back and table-felt palette (`src/components/theme.ts`) — it never segments `stats.ts`/`settings.ts`, which stay global regardless of who's selected.

**Expo has changed.** Read the exact versioned docs at https://docs.expo.dev/versions/v57.0.0/ before writing any code — don't rely on general Expo knowledge, this app is on SDK 57 specifically.

## Commands

```bash
npm run lint          # expo lint .
npm run fix            # expo lint . --fix
npm test               # Jest (5 suites, 73 tests)
npm run typecheck      # tsc
npm run verify         # lint + test + typecheck
npm run doctor         # expo install --fix && expo-doctor
npm start              # Expo dev server
npm run client          # Expo dev server (dev client build)
```

Always run `npm run lint` before finishing any task. This is an app (`"private": true`, no publish scripts) — `verify` doesn't include a build step.

**No `build:*`/`update` scripts exist in this app at all**, unlike every other app migrated onto this tooling so far (Swirlio, LightCycles, BoxHockey, CashierFu-Utility, Pong, AirHockey, Snake all have EAS `build:development`/`build:preview`/`build:production` and `update` scripts gated behind `verify`). Solitaire's `package.json` never had EAS build/update scripts to begin with — nothing here to gate. If EAS scripts are added later, gate them the same way (`"npm run verify && " + <script>`, inline-chained onto the script's own definition, not a separate `pre<script>` hook) — see Swirlio's CLAUDE.md for the full reasoning.

## Tooling

Onboarded onto the shared `@infinitetoken` config packages (`eslint-config`, `jest-config`, `tsconfig`) — previously hand-rolled its own `eslint-config-expo`-based config, `jest-expo`-preset-direct config, and `expo/tsconfig.base`-extending tsconfig (the same pattern documented in [Swirlio](../Swirlio/.claude/CLAUDE.md)'s and [BoxHockey](../BoxHockey/.claude/CLAUDE.md)'s CLAUDE.md).

`npx expo install --fix` + `npm update` genuinely found real staleness here — more than any other app surveyed so far: `@expo/metro-runtime`, `@react-native-async-storage/async-storage` (a full major version, `3.1.1` → `2.2.0` — the installed version was actually *ahead* of what SDK 57 expects), `expo-linking`, `expo-router`, `react-native`, `react-native-gesture-handler` (`^3.1.0` → `~2.32.0`, also a major-version rollback), `react-native-reanimated`, `react-native-safe-area-context`, `react-native-worklets`, `@types/jest`, and `jest-expo` were all misaligned with the installed Expo SDK, in both directions. **`npm update` alone wasn't enough to reach a stable clean state — a genuine wrinkle not seen in the other 7 migrated apps.** After the first `expo install --fix` + `npm update` pass, `npm outdated` showed `Current === Wanted` for everything, but `npx expo install --check` had newly drifted on two packages `npm update` had bumped past Expo's compatible range per their own loose semver (`react-dom` `^19.2.3` → resolved `19.2.8`; `react-native-screens` `^4.26.2` → resolved `4.27.0`) — `npm update` respects a package's declared semver range, which doesn't know about Expo's own SDK-compatibility matrix. Fixed by running `expo install --fix` a second time (pins both back to their SDK-57-compatible versions); confirmed clean afterward on both fronts: `npx expo install --check` reports up to date, `npm outdated` shows `Current === Wanted` for every dependency (remaining `Latest` values are all major bumps outside declared ranges, a deliberate-upgrade decision, not routine maintenance).

- `eslint.config.cjs` — `@infinitetoken/eslint-config/expo`, no local override. Confirmed directly, not just assumed: `@infinitetoken/eslint-config`'s own CLAUDE.md documents auditing all 23 real Expo apps in the fleet before this preset was built, and found Solitaire's old hand-rolled config differed from the other 20 byte-identical apps only by semicolons — a formatting difference, not a functional one. The plain one-liner is exactly correct.
- `tsconfig.json` — `extends: "@infinitetoken/tsconfig/expo"`, keeps only the path-valued local bits (`paths`, `include`) — no `exclude` needed (`.claude/worktrees/` doesn't exist here, confirmed via `ls` before deciding), and no `@shopify/react-native-skia` redirect (this app doesn't depend on that package at all — grepped `package.json` and `src/` to confirm, not assumed from precedent).
- `jest.config.cjs` — `@infinitetoken/jest-config/expo`, no options at all. The old `jest.config.ts` had `testPathIgnorePatterns: ['/node_modules/', '/.expo/']` (rather than the fleet-typical `.claude/worktrees/` entry) — dropped without replacement, since the shared preset's default `roots: ['<rootDir>/src']` already scopes Jest's crawl away from `.expo/` (which lives at repo root) regardless of what's in `testPathIgnorePatterns`.

`@infinitetoken/eslint-config` (`^0.2.0`), `@infinitetoken/jest-config` (`^0.2.3`), and `@infinitetoken/tsconfig` (`^0.4.1`) are all on real published versions — never yalc-linked for this app. `eslint-plugin-package-json` and `ts-node` were removed from `devDependencies` (both redundant under the shared presets).

**`@tastic/profile` requires `@shopify/react-native-skia` as a real installed dependency, even though Solitaire only uses `@tastic/hud`'s `usePopoverHost`/`PopoverHost`/`InlineColorPicker` and never its Skia-rendered `TriggerGaugeHost`.** `@tastic/hud`'s `dist/index.mjs` is a single barrel file that unconditionally imports the `TriggerGaugeHost` module (and therefore `@shopify/react-native-skia`) alongside everything else — Metro's bundler and `tsc` both statically resolve that whole barrel from any import of `@tastic/hud`/`@tastic/profile`, regardless of which named exports are actually used, so omitting skia breaks both `npm run typecheck` (`Cannot find module '@shopify/react-native-skia'` inside `@tastic/hud/src/TriggerGauge.tsx`) and `expo export`/Metro bundling (`Unable to resolve module @shopify/react-native-skia`) — confirmed by installing it (pinned `2.6.2`, matching every other `@tastic/hud` consumer in the fleet — BoxHockey, LightCycles, AirHockey) plus a `"postinstall": "setup-skia-web"` script (copies `canvaskit.wasm` into `public/`, needed for the web target), which resolved both. Unlike BoxHockey, this app's `tsconfig.json` did *not* need the extra `@shopify/react-native-skia` `paths` redirect BoxHockey's CLAUDE.md documents (a separate issue where skia's own `customConditions: ["react-native"]` resolution pulls in an unused-`React`-import source file that fails `noUnusedLocals`) — that didn't reproduce here, possibly due to a newer skia/`@tastic/hud` version resolving differently; re-check if it resurfaces.

**`FeedbackPressProvider` needs an explicit `paper={RNPaper}` prop (`import * as RNPaper from 'react-native-paper'`) or every Paper-mapped wrapper it injects — critically `@tastic/hud`'s/`@tastic/profile`'s internal `TouchableRipple` usage (the color-swatch trigger, profile rows, the "New Profile" row) — silently falls back to a plain `Pressable` that drops the `style` prop entirely.** Before this was wired, the Player section's color-swatch trigger in `ProfilesManager`/`InlineColorPicker` rendered with no background fill and a tiny, wrongly-sized hit box (its `backgroundColor`/`width`/`height`/`borderRadius` inline style silently discarded) — confirmed by reading `@rific/feedback-press/src/components/paper/TouchableRipple.tsx`'s fallback branch directly. Fixed the same way BoxHockey's `src/components/Feedback.tsx` does it: pass the already-imported `react-native-paper` module straight into `<FeedbackPressProvider paper={RNPaper} ...>` (`src/app/_layout.tsx`). This was a real, previously-latent gap — Solitaire's own `Pressable` usage elsewhere never needed it, since nothing before `@tastic/profile` used any of `@rific/feedback-press`'s Paper-flavored wrappers.

**On the web target specifically, `@tastic/profile`'s `ProfilesManager` create/edit flow doesn't reliably commit via the Name field's Enter key, and its documented "commit on unmount" fallback doesn't fire either** — confirmed live: typing a name and pressing Return left the row still open/editable, and navigating away via `router.back()` (Settings → Profiles → back) didn't commit it, because React Navigation's web implementation keeps the previous screen mounted (hidden, not unmounted) across a stack pop, unlike native. Only a hard browser navigation (a real page reload) actually unmounts the screen and would trigger that fallback. This is a gap in the third-party package's web behavior, not in Solitaire's own integration code — `onCreate`/`onSave`/`onDelete` are wired exactly per the package's documented prop shape. Unconfirmed whether this also affects native (where screens genuinely unmount on pop) — worth a real device check before relying on the unmount fallback there. Worked around during verification by seeding `AsyncStorage`'s web-backing `localStorage` key (`solitaire.profiles.v1`) directly rather than fighting the picker UI.

## Architecture

```
src/
  app/          - expo-router routes (index, settings, profiles, one screen per game)
  components/   - shared UI (PlayingCard, PileView, StockWaste, theme, card/drag-drop primitives)
    cards/      - card-face rendering (CardBack, CardFace, CourtFigure, SuitPip)
    dragdrop/   - drag-and-drop primitives (registries, ghost layer, draggable card/drop zone) -
                  supports exactly one flying card/group at a time (drag, tap-to-auto-move)
    dealing/    - the initial-deal animation engine (DealProvider/useDealAnimator in DealLayer.tsx) -
                  a deliberately separate module from dragdrop/, since a deal needs N independently
                  flying cards at once, which the single-ghost drag/drop layer can't do. Wired into
                  all four games, each with its own flight origin: Klondike/Pyramid measure a real
                  stock-pile/triangle view ref; Spider (stock is a fan of face-down packets, no
                  single view to measure) measures a real registered stock card via CardRegistry
                  instead; FreeCell (no stock UI at all) repurposes its far-right freecell as a
                  decorative deck placeholder shown only while dealing (see FreeCellScreen.tsx's
                  dealOriginRef) - freecells are never touched by the initial deal, so nothing real
                  is ever hidden under it. FreeCell also flies its cards in face-up (unlike Klondike's
                  forced face-down flight), matching how FreeCell actually deals in real life.
  engine/       - shared card/deck/pile primitives, RNG, auto-move
  games/        - one subfolder per game (freecell, klondike, pyramid, spider), each with its own
                  rules.ts + <Game>Screen.tsx; games/shared/ exists but is currently empty. Every
                  game also has its own dealSequence.ts, layered on top of rules.ts's unrelated
                  internal deal-slicing order - kept as separate per-game copies rather than a
                  shared import (see Spider's own dealSequence.ts for the explicit rationale), to
                  keep each game's logic self-contained. Klondike/Spider/FreeCell's actually
                  reorder column-major storage into round-robin visiting order; Pyramid's is a much
                  thinner pass-through (its own flat index order already IS the natural apex-first,
                  row-by-row deal order - nothing to reorder), kept anyway as the same named,
                  separately-testable seam the other three have, decoupling the deal's visual order
                  from rules.ts's storage order even though the two happen to coincide today.
  stores/       - persisted settings/stats/theme/profiles (theme, app settings, win stats, the
                  @tastic/profile roster + active-profile selection)
  utils/        - splash-gate wiring
  __tests__/    - test suites (engine.test.ts, games/<game>/rules.test.ts)
  __mocks__/    - manual Jest mocks for native/Expo modules
```

**The deal animation's destination measurements raced the React commit they depended on, and silently dropped ~90% of the board when it lost.** `CardRegistry.measure(cardId)` (`components/dragdrop/CardRegistry.ts`) only resolves once that card's own registration `useEffect` has run — but the deal's initial implementation called `measure()` for all 28 destination cards *synchronously, right after* `setState(newTableau)`, before React had even committed that render, let alone run the new cards' registration effects. Confirmed live: this raced the *previous* deal's still-registered (but about-to-be-replaced) cards against the *new* deal's not-yet-registered ones, and mostly matched neither — 25 of 28 destinations came back `null` on one measured run, silently excluding those cards from `entries` and leaving them hidden forever (a card whose destination is `null` never gets added to `deal.start()`'s entries, so it never fires `onCardLanded`, so its id never leaves `dealHiddenIds`). The fix: never call `CardRegistry.measure()` synchronously after the `setState` that mounts the new cards. Instead, stash a "deal is pending" token and do the actual measurement from a `useEffect` keyed on `[state]` — React fires effects bottom-up per commit (children's before parents'), so by the time a *parent* component's `[state]`-effect runs, every child `PileView`/`DraggableTableauCard` for that same commit has already run its own registration effect. See `KlondikeScreen.tsx`'s `pendingDealTokenRef` for the pattern; `PyramidScreen.tsx`'s equivalent doesn't need it for the *destination* side, since its destinations are computed analytically (`cardPosition()`) rather than via `CardRegistry.measure()` — it only measures two container refs (the stock pile, the triangle container), which aren't subject to this per-card mount race. It still needs the same `[state]`-deferral for the *origin* side, though: those two container refs are themselves behind Pyramid's `if (!state) return <Loading/>` branch, so on the very first mount they aren't attached yet at the moment `startNewGame` calls `setState` — calling `runDeal` synchronously right after that (as it originally did) measured two still-null refs and silently skipped the deal (cards just appeared with no animation, every time you navigated to Pyramid fresh). Fixed by giving Pyramid its own `pendingDealTokenRef` + `[state]`-effect, same shape as Klondike/FreeCell/Spider — confirmed all four now defer their initial `runDeal` this way.

**A second, unrelated bug found in the same session: reused React keys across separate deals silently stalled a handful of cards forever.** All 52 cards' ids are shuffle-independent (`${suit}-${rank}-${deckIndex}`, see `engine/deck.ts`) — a fresh deal reuses the exact same ids as the one before it, just redistributed. If `deal.start()` is ever called again while a previous deal's ghosts are still mounted (shouldn't happen in normal play, since the skip-overlay covers the "New Game" button during a deal too, but is easy to trigger via rapid/automated interaction), React reconciles by id and reuses the *same* `DealGhostCard` instance for a repeated id rather than unmounting and remounting it — meaning its `useSharedValue` position and its "already notified" guard ref never reset, since both only initialize on a genuine first mount. Fixed by folding a monotonic generation counter into each ghost's React `key` (`DealLayer.tsx`'s `generationRef`), forcing a real unmount+mount - and therefore a full state reset - on every `deal.start()` call regardless of id overlap with the deal before it.

**Pyramid's pairing/King removal now lands cards in a real discard pile (`PyramidState.discard`, `rules.ts`) instead of just deleting them, with the codebase's first two-stage ghost flight**: the "first" card (whichever one travels - the previously-selected card on a tap-completed pair, or the actively-dragged card on a drop-completed pair) flies onto the "second" (stationary) card, then both fly together (as a 2-card `useDragGhost()` group, `offsetStep: 0` so they land in one exact overlapping stack) on to the discard pile. Since `DragGhostLayer.flyTo` always hides the ghost right before invoking its `onArrived` callback, stage 2 needs its own fresh `ghost.show()` call (with the new 2-card content, origin reset to stage 1's landing point) inside stage 1's callback - continuing the same flight isn't possible, only starting a new one. The discard pile itself (`PyramidScreen.tsx`'s `DiscardCell`) measures its position like `stockViewRef`/`triangleViewRef` (a plain view ref, `measureView()`) rather than `FoundationCell`'s per-card `CardRegistry` registration - there's only ever one discard pile, not a slot whose occupant identity keeps changing. Undo for a pairing/King removal is deliberately left unanimated (reverts instantly, same as before this feature) - Pyramid's undo model snapshots the whole prior state rather than replaying a reverse move, so `discard` already reverts correctly for free; only the animation is out of scope for now, a known and intentional gap rather than a leftover one.
