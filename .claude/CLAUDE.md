# Solitaire

An ad-free, self-contained solitaire suite (Klondike, Spider, FreeCell, Pyramid, Yukon, Golf, TriPeaks, Canfield, Scorpion, Forty Thieves, Aces Up — 11 games, `src/games/`) built with Expo. Part of the `@rific`/`@tastic`/InfiniteToken app ecosystem — depends on `@rific/auto-paper`, `@rific/feedback-press`, `@rific/focus-chain`, `@rific/splash-gate`, `@rific/toaster`, plus `@tastic/profile` (+ its `@tastic/core`/`@tastic/hud` peers) for player identity (a color + short tag, shared across the fleet via an iOS App Group) — unlike the fleet's physics-driven games, there's still no board-physics or split-screen engine here, just tap/drag card-game logic. A selected player's color/tag only drives the cosmetic card-back palette (`src/components/theme.ts`) - the felt is deliberately NOT profile-tinted, see the root-felt note below — it never segments `stats.ts`/`settings.ts`, which stay global regardless of who's selected.

**Expo has changed.** Read the exact versioned docs at https://docs.expo.dev/versions/v57.0.0/ before writing any code — don't rely on general Expo knowledge, this app is on SDK 57 specifically.

## Commands

```bash
npm run lint          # expo lint .
npm run fix            # expo lint . --fix
npm test               # Jest
npm run typecheck      # tsc
npm run verify         # lint + test + typecheck
npm run doctor         # expo install --fix && expo-doctor
npm start              # Expo dev server
npm run client          # Expo dev server (dev client build)
```

Always run `npm run lint` before finishing any task. This is an app (`"private": true`, no publish scripts) — `verify` doesn't include a build step.

**No `build:*`/`update` scripts exist in this app at all**, unlike every other app migrated onto this tooling so far (Swirlio, LightCycles, BoxHockey, CashierFu-Utility, Pong, AirHockey, Snake all have EAS `build:development`/`build:preview`/`build:production` and `update` scripts gated behind `verify`). Solitaire's `package.json` never had EAS build/update scripts to begin with — nothing here to gate. If EAS scripts are added later, gate them the same way (`"npm run verify && " + <script>`, inline-chained onto the script's own definition, not a separate `pre<script>` hook) — see Swirlio's CLAUDE.md for the full reasoning.

## Tooling

Onboarded onto the shared `@infinitetoken` config packages (`eslint-config`, `jest-config`, `tsconfig`) — previously hand-rolled its own `eslint-config-expo`-based config, `jest-expo`-preset-direct config, and `expo/tsconfig.base`-extending tsconfig (the same pattern documented in [Swirlio](../Swirlio/.claude/CLAUDE.md)'s and [BoxHockey](../BoxHockey/.claude/CLAUDE.md)'s CLAUDE.md).

`npx expo install --fix` + `npm update` genuinely found real staleness here — more than any other app surveyed so far: `@expo/metro-runtime`, `@react-native-async-storage/async-storage` (a full major version, `3.1.1` → `2.2.0` — the installed version was actually *ahead* of what SDK 57 expects), `expo-linking`, `expo-router`, `react-native`, `react-native-gesture-handler` (`^3.1.0` → `~2.32.0`, also a major-version rollback), `react-native-reanimated`, `react-native-safe-area-context`, `react-native-worklets`, `@types/jest`, and `jest-expo` were all misaligned with the installed Expo SDK, in both directions. **`npm update` alone wasn't enough to reach a stable clean state — a genuine wrinkle not seen in the other 7 migrated apps.** After the first `expo install --fix` + `npm update` pass, `npm outdated` showed `Current === Wanted` for everything, but `npx expo install --check` had newly drifted on two packages `npm update` had bumped past Expo's compatible range per their own loose semver (`react-dom` `^19.2.3` → resolved `19.2.8`; `react-native-screens` `^4.26.2` → resolved `4.27.0`) — `npm update` respects a package's declared semver range, which doesn't know about Expo's own SDK-compatibility matrix. Fixed by running `expo install --fix` a second time (pins both back to their SDK-57-compatible versions); confirmed clean afterward on both fronts: `npx expo install --check` reports up to date, `npm outdated` shows `Current === Wanted` for every dependency (remaining `Latest` values are all major bumps outside declared ranges, a deliberate-upgrade decision, not routine maintenance).

**`@tastic/profile` requires `@shopify/react-native-skia` as a real installed dependency, even though Solitaire only uses `@tastic/hud`'s `usePopoverHost`/`PopoverHost`/`InlineColorPicker` and never its Skia-rendered `TriggerGaugeHost`.** `@tastic/hud`'s `dist/index.mjs` is a single barrel file that unconditionally imports the `TriggerGaugeHost` module (and therefore `@shopify/react-native-skia`) alongside everything else — Metro's bundler and `tsc` both statically resolve that whole barrel from any import of `@tastic/hud`/`@tastic/profile`, regardless of which named exports are actually used, so omitting skia breaks both `npm run typecheck` (`Cannot find module '@shopify/react-native-skia'` inside `@tastic/hud/src/TriggerGauge.tsx`) and `expo export`/Metro bundling (`Unable to resolve module @shopify/react-native-skia`) — confirmed by installing it (pinned `2.6.2`, matching every other `@tastic/hud` consumer in the fleet — BoxHockey, LightCycles, AirHockey) plus a `"postinstall": "setup-skia-web"` script (copies `canvaskit.wasm` into `public/`, needed for the web target), which resolved both. **`FeedbackPressProvider` needs an explicit `paper={RNPaper}` prop (`import * as RNPaper from 'react-native-paper'`) or every Paper-mapped wrapper it injects — critically `@tastic/hud`'s/`@tastic/profile`'s internal `TouchableRipple` usage (the color-swatch trigger, profile rows, the "New Profile" row) — silently falls back to a plain `Pressable` that drops the `style` prop entirely.** Before this was wired, the Player section's color-swatch trigger in `ProfilesManager`/`InlineColorPicker` rendered with no background fill and a tiny, wrongly-sized hit box (its `backgroundColor`/`width`/`height`/`borderRadius` inline style silently discarded) — confirmed by reading `@rific/feedback-press/src/components/paper/TouchableRipple.tsx`'s fallback branch directly. Fixed the same way BoxHockey's `src/components/Feedback.tsx` does it: pass the already-imported `react-native-paper` module straight into `<FeedbackPressProvider paper={RNPaper} ...>` (`src/app/_layout.tsx`). This was a real, previously-latent gap — Solitaire's own `Pressable` usage elsewhere never needed it, since nothing before `@tastic/profile` used any of `@rific/feedback-press`'s Paper-flavored wrappers.

**On the web target specifically, `@tastic/profile`'s `ProfilesManager` create/edit flow doesn't reliably commit via the Name field's Enter key, and its documented "commit on unmount" fallback doesn't fire either** — confirmed live: typing a name and pressing Return left the row still open/editable, and navigating away via `router.back()` (Settings → Profiles → back) didn't commit it, because React Navigation's web implementation keeps the previous screen mounted (hidden, not unmounted) across a stack pop, unlike native. Only a hard browser navigation (a real page reload) actually unmounts the screen and would trigger that fallback. This is a gap in the third-party package's web behavior, not in Solitaire's own integration code — `onCreate`/`onSave`/`onDelete` are wired exactly per the package's documented prop shape. Unconfirmed whether this also affects native (where screens genuinely unmount on pop) — worth a real device check before relying on the unmount fallback there. Worked around during verification by seeding `AsyncStorage`'s web-backing `localStorage` key (`solitaire.profiles.v1`) directly rather than fighting the picker UI.

## How-to-play guide (2026-09-24)

A first-run, replayable "How to Play" flow, built on `@tastic/hud/guide` (the light-peer subpath of `@tastic/hud`; see that package's own CLAUDE.md, "The guide subpath"). Same shape as LightCycles, Snake, AirHockey, BoxHockey and Pong. **The code word is `guide` everywhere, never "onboarding"** (the fleet's word for a round countdown).

- **Content:** `src/constants/guideSteps.tsx`: `getGuideSteps({ touch })`, three cards, pure and hook-free. `touch` is `useIsTouchPrimaryDevice()` and only swaps the verb (tap vs click). **Per-game rules are deliberately NOT here**: `RulesDialog` (`constants/gameRules.ts`, plus its shared Scoring paragraph) already covers each of the 11 games; the guide teaches the suite-wide things a first-timer can't work out alone, and every sentence has to be true in all 11 games at the default settings:
  - **Tap to Play** (Click to Play on desktop): "Tap a card for its best move. Pyramid pairs take two taps." Ten games run the game's `autoMoveHint` on a tap (each screen's `handleCardTap`, Spider's `handlePressCard`; the tableau pick is `engine/autoMove.ts`'s `pickBestTableauTarget`). Pyramid's tap only SELECTS (`handleSelectPyramid`; a tap on the partner removes the pair, a King goes on one tap), so the first sentence would be false there without the scope. **Dragging is deliberately not taught:** a drag can't make every move. The discard pile has no `DropZone` (`games/shared/DiscardCell.tsx`), so an Aces Up discard (its main move; the card still lifts because `hasLegalMove` counts discards) and a Pyramid King both snap back when dragged there (`AcesUpScreen`'s header and `handleDrop`, `PyramidScreen`'s `attemptDrop`). Making the discard a drop zone in those two screens would make a drag line true again.
  - **Lower Is Better**: "Score is moves plus seconds. The first move starts the clock." `engine/score.ts`'s `computeScore` (every game's readout, through `GameChrome`); `useGameSession`'s `registerMove` starts the clock (a stock draw counts); `statsEngine.ts` keeps the LOWER best score. The clock half is printed nowhere in the game.
  - **Get a Hint**: "Tap the light bulb in any game to see a move you can make." `GameChrome`'s `lightbulb-on-outline` Hint button, in both layouts; `engine/hint.ts`'s `findHint` rings a legal move, or the stock when a draw is the move, and each screen's `handleHint` toasts when there is none. Home has no light bulb, so this doesn't describe what's behind the card. The info button is left out for exactly that reason: every Home tile shows it (`renderRulesButton` in `app/index.tsx`).
  - Art: `src/components/GuideArt.tsx` (`GuideCardPlay`, whose `pointer` is `'finger'` on touch and `'mouse'` on desktop, also picking the screen-reader verb; `GuideScore`; `GuideHint`, the Hint button plus a ringed seven and eight). Plain Views plus Paper Icons/Text, colored from `useAutoPaperTheme()`: no Skia/SVG, and deliberately NOT the in-game `PlayingCard`/pile components or `@tastic/cards` (the mini cards are Views). None of hud's shared art (swipe, key caps, split phone) fits a card game.
- **Copy rules (Jay, 2026-09-24):** Title Case titles; one-word buttons (hud's defaults Skip / Back / Next / Ready, no `finishLabel`); bodies of 90 characters or less; no questions, no filler, no vague nouns, no em dashes; every sentence true for everyone who can see it (all 11 games, default settings); don't describe what's already visible behind the dialog; never tell a desktop player to tap or a touch player to click. **Plus a Solitaire-only rule: every body fits in TWO lines** of DejaVu Serif Bold (the app-wide Paper font, `ThemeProvider`'s `fontFamily`) at bodyMedium 14/20 on a 264pt page (a 360dp phone; `guideSteps.test.tsx` caps bodies at 62 characters as a proxy). A third line makes the turned card too tall, see Wiring. Measure a new body against the real TTF (`node_modules/dejavu-fonts-ttf/ttf/DejaVuSerif-Bold.ttf`, e.g. with PIL's `getlength` plus 0.25 letter spacing per character), since widths vary per letter. **Considered and left out:** dragging (see Tap to Play), the info button (visible on every Home tile behind the card), tap-the-felt-to-hide-the-footer (portrait only: false in the wide layout and in a desktop window), the shake on a card with no move (in Pyramid a shake means a failed pair), hint cycling (not true when the hint is a stock draw or the only move), Undo's hold-to-repeat (never checked with a mouse on web), auto-save (it shows itself the first time you come back).
- **Wiring:** `src/components/GuideHost.tsx` (the Redux seen version + `useRotation()` passed as `rotation` + the steps -> `GuideProvider`), mounted in `_layout.tsx` around `<ThemedStack />` inside `OrientationBridge`, so inside PersistGate, the auto-paper/Paper provider and the orientation provider. **The card is the one dialog here that is NOT under an in-frame Portal.Host:** `GuideProvider` renders it beside its children, so its Paper `Portal` lands in the nearest host above `GuideHost`, which is `FeedbackPressProvider`'s own `Portal.Host` (`FeedbackBridge` passes `paper={RNPaper}`), outside every rotated frame. It is handed the frame's live rotation as a transform instead of `rotation={0}` (the same `useRotation()` Home's `RotatedFrame` turns by, so it sits at the angle Home's Settings dialog visually does). Home (`app/index.tsx`'s `Home`) calls `useAutoShowGuide(!resumeGame)` BEFORE the cold-launch resume `<Redirect>` (hooks stay unconditional): held back whenever the launch is about to drop into a saved game, so the guide can never open over a live deal. Settings row: `SettingsDialog`'s `showHowToPlay` (default false) -> `BaseSettingsDialog`'s `onShowHowToPlay`; turned on ONLY at Home's call site, **never in `GameChrome`**: the score counts elapsed seconds, so a guide opened mid-deal would cost the player score.
- **Turned card height:** the fleet's rotation is fake (the OS window stays portrait), so a quarter-turned card's layout HEIGHT has to fit the window's short edge. hud handles that for every game now: `getGuideCardSize` swaps the axes for +/-90, widens the card, caps its height, shrinks the art under 480pt, and each page scrolls if it still doesn't fit (found in this app's review, fixed upstream 2026-09-24). Keeping every body to two lines means that scroll is never needed at the default text size. Not yet checked on a real device held sideways.
- **Persistence:** `src/redux/guideSlice.ts` (a `createGuideSlice` binding) mounted as `guide` in `store.ts` (its own key: Reset Stats and the hand-rolled settings store never touch it). `GUIDE_VERSION` (`src/constants/guide.ts`) is what an existing player is stamped with. Players who already have a root store (otaVersion 4+, 464e3e1) are grandfathered by the slice itself. **Players last on otaVersion 3 (25532f0, 2026-09-12) or earlier have NO root store** (it arrived in 6dbe6e5), so `store.ts`'s `persistConfig.migrate` is `createReturningPlayerMigrate(AsyncStorage, LEGACY_STORAGE_KEYS)`: the 20 literal keys 25532f0 really wrote (the 11 `solitaire.game-in-progress.v1.<game>` saves, `solitaire.stats`/`.achievements` via `@tastic/achievements` 0.1.1's namespace, settings, theme, last-active-game, profiles, guest color, sound, vibrate; per-key source in guideSlice.ts), read from that commit's source, not today's constants. otaVersion 1 (5f3078f) and 2 (f065784) wrote the same set. `solitaire.stats.v1.<gameId>` is NOT listed: those builds only ever read it. **Early-write rule:** nothing may write one of those keys before PersistGate opens, or a fresh install is taken for a returning player. Today `solitaire.settings.v1`, `solitaire.theme-settings.v1` and `solitaire.last-active-game.v1` belong to providers mounted OUTSIDE PersistGate (`SettingsProvider`, auto-paper's `ThemeProvider`, `LastActiveGameProvider`), but none writes on mount (auto-paper's `onChange` skips the first render, see `@rific/core`'s `createSettingsContext`; the other two write only from their setters) and every setter call at boot (`ProfileThemeSync`, `OrientationBridge`, the game screens) comes from inside PersistGate. Only finish/skip writes; a replay never does. Bump `GUIDE_VERSION` only for a real controls/scoring change: every player sees it again.
- **Not built:** any in-game entry point (deliberate, see Wiring), and per-game first-visit tips (RulesDialog is the per-game layer).
- **Tested:** `guideSteps.test.tsx` (three illustrated cards per platform, Title Case, bodies <= 90 characters and <= 62 as the two-line proxy, no questions or dashes, touch vs desktop differ only by the verb, the Pyramid scope, no drag promise, the exact score copy, the hint card naming the light bulb and not the info button, each card's art component and pointer, the art's screen-reader labels, the score picture matching `computeScore`), `guideSlice.test.ts` (this app's binding; `LEGACY_STORAGE_KEYS` namespaced, unique, all 11 saved-deal keys, no `stats.v1` keys; the migrate over each key gives `GUIDE_VERSION` and no keys or a failed read gives 0, also end to end through real redux-persist, including a fresh install's second launch after the theme key was written; the real `persistConfig` has the migrate, imported under fake timers because store.ts's persistStore leaves redux-persist's 5s failsafe timer), `components/homeGuide.test.tsx` (the redirect guard), `components/settingsHowToPlay.test.tsx` (the prop -> row), `components/gameChromeHowToPlay.test.tsx` (never in a game). **Not verified live:** nothing here was run on a simulator, device or web build: the card's look (mini-card ink in dark mode, art sizes on a 320pt phone), the transform-rotated card under a fake landscape hold (the 358pt height is an estimate from hud's styles and the real font's widths, not a measurement; check it on a 375pt iOS simulator and a 360dp Android emulator held sideways, at the default and a larger text size), the Settings row, and the auto-show on a genuinely fresh install.
- **Packages:** the guide ships in the published `@tastic/hud` 0.13.0 (`./guide`, with `createReturningPlayerMigrate`). Solitaire has no yalc links any more (2026-09-25: `.yalc/` and `yalc.lock` removed, `@tastic/cards`/`hud`/`profile` installed from npm). ## Architecture

```
src/
  app/          - expo-router routes (index, settings, profiles, one screen per game)
  components/   - shared UI (PlayingCard, PileView, StockWaste, theme, card/drag-drop primitives)
    cards/      - card-face rendering (CardBack, CardFace, CourtFigure, SuitPip)
    dragdrop/   - drag-and-drop primitives (registries, ghost layer, draggable card/drop zone) -
                  supports exactly one flying card/group at a time (drag, tap-to-auto-move)
    dealing/    - the initial-deal animation engine (DealProvider/useDealAnimator in DealLayer.tsx) -
                  a deliberately separate module from dragdrop/, since a deal needs N independently
                  flying cards at once, which the single-ghost drag/drop layer can't do. Wired into
```

**The deal animation's destination measurements raced the React commit they depended on, and silently dropped ~90% of the board when it lost.** `CardRegistry.measure(cardId)` (`components/dragdrop/CardRegistry.ts`) only resolves once that card's own registration `useEffect` has run — but the deal's initial implementation called `measure()` for all 28 destination cards *synchronously, right after* `setState(newTableau)`, before React had even committed that render, let alone run the new cards' registration effects. Confirmed live: this raced the *previous* deal's still-registered (but about-to-be-replaced) cards against the *new* deal's not-yet-registered ones, and mostly matched neither — 25 of 28 destinations came back `null` on one measured run, silently excluding those cards from `entries` and leaving them hidden forever (a card whose destination is `null` never gets added to `deal.start()`'s entries, so it never fires `onCardLanded`, so its id never leaves `dealHiddenIds`). The fix: never call `CardRegistry.measure()` synchronously after the `setState` that mounts the new cards. Instead, stash a "deal is pending" token and do the actual measurement from a `useEffect` keyed on `[state]` — React fires effects bottom-up per commit (children's before parents'), so by the time a *parent* component's `[state]`-effect runs, every child `PileView`/`DraggableTableauCard` for that same commit has already run its own registration effect. See `KlondikeScreen.tsx`'s `pendingDealTokenRef` for the pattern; `PyramidScreen.tsx`'s equivalent doesn't need it for the *destination* side, since its destinations are computed analytically (`cardPosition()`) rather than via `CardRegistry.measure()` — it only measures two container refs (the stock pile, the triangle container), which aren't subject to this per-card mount race. It still needs the same `[state]`-deferral for the *origin* side, though: those two container refs are themselves behind Pyramid's `if (!state) return <GameLoading />` branch, so on the very first mount they aren't attached yet at the moment `startNewGame` calls `setState` — calling `runDeal` synchronously right after that (as it originally did) measured two still-null refs and silently skipped the deal (cards just appeared with no animation, every time you navigated to Pyramid fresh). Fixed by giving Pyramid its own `pendingDealTokenRef` + `[state]`-effect, same shape as Klondike/FreeCell/Spider — confirmed all four now defer their initial `runDeal` this way.

**A second, unrelated bug found in the same session: reused React keys across separate deals silently stalled a handful of cards forever.** All 52 cards' ids are shuffle-independent (`${suit}-${rank}-${deckIndex}`, see `engine/deck.ts`) — a fresh deal reuses the exact same ids as the one before it, just redistributed. If `deal.start()` is ever called again while a previous deal's ghosts are still mounted (shouldn't happen in normal play, since the skip-overlay covers the "New Game" button during a deal too, but is easy to trigger via rapid/automated interaction), React reconciles by id and reuses the *same* `DealGhostCard` instance for a repeated id rather than unmounting and remounting it — meaning its `useSharedValue` position and its "already notified" guard ref never reset, since both only initialize on a genuine first mount. Fixed by folding a monotonic generation counter into each ghost's React `key` (`DealLayer.tsx`'s `generation`), forcing a real unmount+mount - and therefore a full state reset - on every `deal.start()` call regardless of id overlap with the deal before it. The same generation is also stamped on every slot (`deal`) and checked in every callback (`generationRef`, bumped synchronously in `start()`, which also `cancel()`s the old slots), because the old slots stay mounted - timers live - until the commit AFTER `start()`: a timer firing in that gap used to report a stale card into the new deal.

**Pyramid's pairing/King removal lands cards in a real discard pile (`PyramidState.discard`, `rules.ts`) instead of just deleting them.** A solo King flies as a single card via the shared `ghost` (`DragGhostLayer`/`useDragGhost`), same as every other single-card flight in this app. A pair instead flies as **two cards travelling independently at the same time**, each from its own real board position straight to the discard pile (`PyramidScreen.tsx`'s `startPairFlight`/`PairFlightGhosts`/`FlyingPairCard`) - not merged into one stack, and not one card visiting the other before either moves. The single shared `ghost` can only ever animate one origin/delta for its whole group (see `DragGhostLayer.tsx`), so two cards converging from different starting points needed their own small overlay instead - the same "N independent simultaneous ghosts" idiom `DealLayer`/`WinCascadeLayer` already use for the same reason (see `DealLayer.tsx`'s doc comment), just with each ghost getting its own independent origin/destination instead of a shared one. Each card's flight is its own `withSpring` at `FLIGHT_SPRING`, the one time every flight in this app takes, so the two cards of a pair leave together and land together. For a drag-completed pair, "first" is still sitting mid-drag in the shared `ghost` at drop time - its live position is read directly off `ghost.originX/Y.value + dx/dy.value` before handing off to its own independent flight and retiring that ghost (`ghost.hide()`). Two earlier shapes of this flight were tried and rejected first: originally "first" visibly flew onto "second" before the (already-merged) pair continued on to discard, as two distinct legs; replacing that with a single flight of the two cards already merged into one stack (skipping the first leg, but still one shared ghost) was also rejected - both read as one object moving, when the actual ask was always two cards animating independently to the same destination at the same time. The discard pile itself (`PyramidScreen.tsx`'s `DiscardCell`) measures its position like `stockViewRef`/`triangleViewRef` (a plain view ref, `measureView()`) rather than `FoundationCell`'s per-card `CardRegistry` registration - there's only ever one discard pile, not a slot whose occupant identity keeps changing. **Undoing a pairing/King removal now animates too, flying each card independently from the discard pile back to its own original spot** (`PyramidScreen.tsx`'s `undoRemoval`, `RemovedCardRef`) - the mirror image of the forward removal flight: one shared origin (the discard pile, which doesn't move) fanning out to each card's own destination, reusing the same `PairFlightCardSpec`/`PairFlightGhosts`/`startPairFlight` machinery (generalized so each card's spec now carries its own `to` as well as its own `from` - the forward flight shares one `to` across cards with independent `from`s, the undo flight shares one `from` with independent `to`s). `UndoEntry` gained a `removedCards: RemovedCardRef[] | null` field (the PileRef each removed card came from) alongside the pre-existing `move: MoveInfo | null` for stock draws - the two are mutually exclusive. **Every undo resolves ALL its endpoints BEFORE it commits, and mounts its ghosts in the same synchronous stretch as the revert** - a pyramid-cell destination is pure math (`cardPosition` + the measured `triangleViewRef`), a waste-bound card's is the always-mounted waste container (`wasteViewRef`; there is one waste slot, so it is the same place the card's own registration would say), and the discard/stock are plain containers too. The old shape (commit the revert, then a `[state]`-effect measured the destinations and only then started the flight) left the restored cards visible NOWHERE for a frame or two (the discard already showing its older top, the cards hidden, no ghost yet) before the ghosts popped in. Undo of a draw and of a recycle measure both endpoints first and do `ghost.show` + `beginFlying` + `setStockHidden(true)` + `commitState` + `flyTo` in one stretch; undoing a draw also freezes the stock slot (`stockHidden`) until the returning ghost lands, instead of showing the returned card at once. The restored card(s) have to be hidden (`pyramidHiddenIds` for a pyramid destination, reusing `flying`/`wasteHiddenCount` for a waste one) in that same commit - React batches same-tick `setState` calls - to avoid a frame where the restored card flashes fully visible before its ghost covers it (same reasoning `startNewGame`'s `setPyramidHiddenIds(dealtIds)` already relies on for the initial deal). A waste-bound card's `flying` entry ends with ITS card's landing (the pair ledger's `flying.cardId`), not with the whole pair, so a landed Ace is not hidden again while the Queen is still on its way. `dealHiddenIds`/`isDealHidden` were renamed to `pyramidHiddenIds`/`isHidden` to reflect that the same hidden-until-landed mechanism now covers two different reasons a pyramid cell's card might be flying in, not just the initial deal. A card whose destination cannot be measured (a rare edge case) simply has no ghost and is not hidden, rather than left stuck invisible forever. **Fast play:** pair flights are independent - `pairFlights` is a list with a per-flight ledger keyed by gen (a landing settles only its own flight; a single slot let the next pair replace the last one, so its ghosts vanished mid-air and its `activeFlightCount` claim never settled), and the discard shows the topmost card not in `discardInAir` under the ghosts (`DiscardCell`'s additive `settledCard`, the `FoundationCell` idiom). Every action claims its flight synchronously (`claimFlight`, generation-stamped) and **re-validates against `stateRef.current` after its measurement awaits** (`replayMove`, then one synchronous `commitRemoval`) - committing the pre-await `result` overwrote whatever committed meanwhile and let a double-tapped King be removed twice. Pinned by `pyramidScreenQuickPlay.test.tsx`, whose mocked measurements have a latency so taps really overlap. **Overlapping draws and the waste:** the waste slot's frozen copy of the pre-flight top goes stale once draw flights overlap (each landed ghost vanished onto the card from before the whole stream), so `wasteInAir` (the waste's `discardInAir`) tracks the drawn cards still flying and the screen passes `StockWaste` the additive `settledWasteTop` (the topmost waste card not in it; omitted - `undefined` - keeps the frozen copy, which every other game and every non-draw flight still uses). **A card is never acted on while its own draw ghost is airborne:** a tap/drop on it (or a pair completed with it) waits - `whenLanded`, re-checked at every landing, bounded by `DEFER_MAX_WAIT_MS` - so the card visibly arrives, THEN flies on (measuring the hidden real card would start a second ghost from a slot the drawn card has not reached, shown twice); a draw waits out a recycle's group ghost still flying into the frozen-empty stock, and a recycle waits out draw ghosts still landing (it would pick the airborne card up twice) - plain draws still overlap freely. The check comes AFTER the measurement awaits and does not yield when nothing is in the way, so an earlier tap's commit is never interleaved with a later one's. **Every such wait is a LOOP, not a single check** (`while (!gate() && budget.left() > 0) await whenLanded(gate, budget.left())`, inline at all three call sites - `attemptMove`, `attemptDrop`, `handleDrawStock`): being resumed is not proof the gate still holds, because a landing resolves EVERY waiter whose predicate held at that instant and their continuations then run one after another - the first (a recycle) re-freezes the stock for the next, which used to draw from the freshly recycled stock while the recycle's group ghost was still flying into it (stock [5], waste [2, 3], three quick stock taps). The loop must stay inline (a helper looping inside an async function hands its answer back across a microtask boundary in which a sibling can change it again), and its deadline is ONE budget per action (`startDeferBudget`), not a fresh `DEFER_MAX_WAIT_MS` per resume. **`commitRemoval` drops a selection that names a card it removes** (`setSelected((sel) => removed.some(refsEqual) ? null : sel)`): an action clears the selection when it starts and may then park in the wait above, and a tap in that window selects the waste as `{waste, 0}` - "whatever is on top" - which, once the deferred pair had removed that card, pointed at the card that was UNDER it (highlighted, and paired by the next tap: a move the player never chose). A selection of an unrelated card made during the wait is kept. **New Game/restore retires every shared-ghost flight still in the air** (`trackFlight`/`hideAirborneFlights`: a King's, draws' - queued ones included -, recycles', undos'), after bumping `dealTokenRef` so their completions are generation-guarded; dropping `pendingFlightRef` alone left queued ghosts mounted for good.

**Pyramid's win is a SWEEP DEAL, then one chain from one pile.** rules.ts still folds whatever is left in the stock/waste into the discard ON the winning move (a won game's discard is all 52 cards, waste bottom-to-top then stock bottom-to-top - the order everything else depends on), so `won` stays game state exactly as before (clock, stat, save, recorded the instant it happens). But nothing flew for that fold, so the leftover cards now fly: the winning removal's `commitRemoval` calls `beginWinSweep`, which claims a flight (`claimFlight`, while the removal's own claim is still held, so `settled` never blips true) and marks every leftover as in the air on the discard (`discardInAir`, so the pile's top is always a card that really landed). Once nothing but the sweep's claim is outstanding (`activeFlightCount` down to 1 - the last removal has landed), `runSweep` deals the leftovers through the existing deal machinery (`useDealAnimator`: same stagger `dealStaggerMs`, spring, throttled sound/haptics and skip-tap - no flight layer of its own), one card per swept card from its own pile (the waste slot for the waste's, the stock slot for the stock's; a pile that cannot be measured deals from the other one, only with no origin at all does a card simply land) to the discard, in the discard array's order, face-up (the deal layer cannot turn a card over in flight, and every swept card is face-up already). The board keeps showing the pre-fold piles (`winHoldView`, kept in `sweepUi.view`, keyed to the won state's identity) and empties each pile when its last card takes off - driven by the deal layer's own take-off signal, `DealAnimator.start`'s additive optional `onCardDealt(cardId)` (once per card, at the instant its ghost is drawn over the spot it leaves; reported for every not-yet-taken-off card when a skip lands the deal at once; silenced by a cancel/restart exactly like `onCardLanded`), `SWEEP_PILE_BLANK_LAG_MS` after the pile's LAST card, on the run's timers so `cancelSweep` clears it. A timer armed from the scheduled delays right before `deal.start` (what this used to be) runs on the wrong clock: the deal's own clock only starts once its ghost pool has rendered and mounted (several frames on a phone) and a card's real take-off is that clock + its re-based delay + the render of its launch, so the timer ran ahead and the pile sat empty until the ghost popped in (worst for a pile whose last card leaves at delay 0). Pinned by `pyramidScreenWin.test.tsx`'s mount-latency cases and `dealLayer.test.tsx`'s `onCardDealt` block. The deal's `onAllLanded` (or a skip, which lands everything at once) settles the claim exactly once; a New Game mid-sweep, or the reveal's fallback timer, ends it via `cancelSweep` (an empty `deal.start([])` is the deal layer's only cancel). Timeline: last removal lands -> sweep (up to ~1.1s for 24 cards) -> 400ms hold -> reveal, so `useWinReveal` gained an additive `maxWaitMs` and Pyramid passes 4s (nominal ~1.9s worst case against the default 2.5s was too thin for a phone's JS stalls). The reveal then launches ONE chain of all 52 discard cards (head = the card on top) from the discard container; the discard blanks only in the commit its ghosts mount (`cascadeHandoff`, now just the discard). **A 52-card chain at the usual 42ms per card trails its head by ~2.1s - more than two bounce half-periods - and splits into a wave** (the ~28-card discard chain it replaced already did), so `ChainSpec` gained an additive `segmentDelayMs` and Pyramid passes `chainSegmentDelayMs(count)` (`winCascadeMotion.ts`: the usual delay, tightened so the whole head-to-tail span stays within `CHAIN_MAX_SPAN_MS` = 500ms, ~9.8ms per card at 52); `isGhostVisible` takes the chain's own delay. Pinned by `pyramidScreenWin.test.tsx` (a deal harness that follows the real deal's timeline) and `winCascadeMotion.test.ts` (a 52-card chain bends at most once with the cap, twice without).

**Landscape rotation is a fake: the OS stays portrait-locked and the whole app is visually rotated** (`@tastic/core`'s `OrientationProvider` reads the accelerometer; `useRotation()` gives 0/90/-90/180). Every screen draws inside a rotated frame: each game via `withGameProviders` (`RotatedGameView`), and Home, Achievements and Profiles via `RotatedScreen` (see the `RotatedScreen.tsx` bullet below); the root layout's toaster and update dialog sit in their own frame laid over the whole `Stack` (`_layout.tsx`'s `RootOverlays`). Nothing in the app is left in physical portrait. Several things here exist only because of how that goes wrong:
- **`RotatedGameView` replaces `@tastic/core`'s `FakeLandscapeView` on purpose.** `FakeLandscapeView` (through 0.8.0) returned a different element tree at 0deg vs +/-90deg (`<View>` vs `<View><View>`), so React unmounted and remounted the WHOLE game screen - every card, all providers, and Inner's state (undo stack, hints) - on every rotation. Measured in the simulator: ~700-800ms of JS per rotation versus ~90-250ms for the update it should be. `RotatedGameView` keeps one identical tree at every angle and only swaps styles. Don't reintroduce a per-angle branch in the tree. (Fixed upstream in the next `@tastic/core` release, unpublished at the time of writing - swap back once it ships.)
- **The "wide" layout (`components/gameLayout.ts`) is what makes landscape playable.** Any window whose ROTATED footprint is landscape (`isWide`: a phone held sideways, an iPad, a desktop browser) drops the vertical chrome bands (portrait reserves 56pt top + 88pt bottom, which would eat 144 of a ~402pt-tall landscape screen): `GameChrome` puts the footer controls (Undo/New Game/Hint/Rules) in a column in the RIGHT side gutter (where the thumb is) and the moves/score/time readout in the LEFT one, hides the title (rules stay reachable from the info button), and the corner buttons stay put. Tap-the-felt-to-hide-the-footer is portrait-only (there the footer floats over the board, so hiding it frees room; in landscape it sits in a gutter and hiding it would give the board nothing back). The two gutters are PER-SIDE (`leftGutter`/`rightGutter`, each = its chrome column + its OWN safe-area inset): sizing both from the larger inset left ~44pt of dead space between the footer buttons and the board on the small-inset side of a phone held sideways. `useGameLayout()` gives every screen its `contentWidth` (net of the gutters) and `availableHeight`. Portrait is byte-for-byte unchanged.
- **Cards are sized to fit the height in the wide layout** (`useFittedCardWidth` + a per-game `src/games/<game>/boardModel.ts`). A board's height is affine in card width (`columnBoardModel`: top row + tallest STARTING tableau column + a face-up headroom + paddings), so the fit is closed-form; each `boardModel.test.ts` asserts the model against a real deal. When the fit shrinks the cards, `useFittedGap` spreads the leftover width into the gaps (up to `CARD_GAP_MAX`). `useTableauMaxHeight` has no floor in the wide layout (the per-game 300-460pt floors are portrait-tuned and exceed a landscape screen). Pyramid/TriPeaks fit their own real board height (`geometry.ts`). Scorpion's wide layout has no top row: the assisted stock packet is absolutely positioned one gap past column 7 (tableau centred on its own, so the width budget is 7+2 columns; `useTableauMaxHeight(..., { topRowCards: 0 })`), which gives ~59pt cards on 874x402 and no tableau jump when the stock is dealt/undone. Known trade-off: Yukon's deep starting columns give ~46pt cards.
- **The game's dialogs render inside the rotated frame.** Paper's `Portal` mounts at the APP ROOT by default - outside the rotated frame - so Settings/Rules/the New Game confirm used to rotate themselves with a transform while their layout (a `maxHeight: '90%'` sheet) was still resolved against the PORTRAIT window: turned 90deg they ran off a 402pt-wide screen, and the Settings sheet lost its first row (Lock Orientation, the one you need to get OUT of landscape) with no way to scroll to it. `withGameProviders` mounts a `Portal.Host` inside `RotatedGameView` and OUTSIDE the three providers (so it paints above their ghost overlays and DealLayer's skip-tap layer); `GameChrome` passes `rotation={0}` to its dialogs. Home, Achievements and Profiles do the same through `RotatedScreen` (`portalHost`: a `Portal.Host` inside the frame; `rotation={0}` on Home's `SettingsDialog` and on Achievements' `BaseStatsScreen`, which forwards it to its reset `ConfirmDialog`; `compact={isWide}` on Home's `RulesDialog`; Profiles' delete-confirm is a plain Paper `Portal` inside `@tastic/profile` with no rotation of its own, so the in-frame host is all it needs), and so does the root layout's `UpdateDialog` (`RootOverlays`' `RotatedFrame portalHost`, its `rotation` left at 0). No dialog uses the app-root portal host any more: a new one must render under one of these hosts and be told `rotation={0}`.
- **`@tastic/hud`'s `ContentGutter` read raw `useWindowDimensions()`, which never changes under a fake rotation** - it capped the rotated board at the portrait width. `RotatedContentGutter` sizes from the rotated width (and reserves the wide layout's side gutters). hud's `ContentGutter` reads the rotated width too since 0.13.0, but it is NOT a drop-in replacement: it caps against the whole window and splits the leftover equally, and its `leftGutter`/`rightGutter` props are decorations drawn inside that leftover, not reserved widths - so the wide layout's per-side chrome columns would overlap the board. Keep `RotatedContentGutter` unless hud grows per-side reserved widths.
- **Every screen-space measurement (`measureInWindow`, Reanimated `measure()`, `e.absoluteX/Y`) is a transformed bounding box in true screen space** - confirmed on iOS/Fabric. The ghost overlays (`DragGhostLayer`, `DealLayer`, `WinCascadeLayer`, Spider's `SequenceFlightGhosts`, Pyramid's `PairFlightGhosts`) live inside the rotated frame, so subtracting the overlay's offset (right only at 0deg) put ghosts in the wrong place and moved a dragged card along the wrong axis. `overlayFrame.ts`'s `useOverlayFrame()`/`toLocal()` convert screen -> rotated-frame via the card's centre. That conversion assumes the measured rect is CARD-SIZED: measure a card slot (`StockWaste`'s `wasteRef`), never a wider wrapper. Pyramid/TriPeaks compute some endpoints analytically (a measured container's top-left + a local `cardPosition` offset), which is only right at 0deg - `localOffsetToScreenPoint` composes those through the container's centre (`geometry.ts` in each game). All of it is unit-tested in `src/__tests__/components/overlayFrameMath.test.ts` and each `geometry.test.ts`.
- **Home (`app/index.tsx`) rotates the same way, with a two-pane landscape layout.** `Home` only owns the cold-launch resume `<Redirect>` (so nothing else mounts while redirecting); `HomeMenu` wraps `HomeContent` in `RotatedScreen` (`RotatedGameView` + `Portal.Host`, plus a `FocusedStatusBar` leaf that mounts `GameStatusBar` only while the screen is focused - Home stays mounted beneath a game/Achievements/Profiles, all of which rotate, and expo-status-bar keeps a mount-order stack of props, so a covered screen's hidden bar would stay hidden over the next one; a leaf, so a focus flip doesn't re-render the menu). Geometry comes from `components/homeLayout.ts` (`computeHomeLayout` pure + `useHomeLayout()` reading `useRotatedWindowDimensions()`/`rotateInsets()`, the `gameLayout.ts` recipe; unit-tested in `homeLayout.test.ts`): `isWide` (rotated footprint wider than tall) puts the scaled hero (`HeroCards`' `scale` prop), title, subtitle and then the player chip (the same order as portrait, centred as one group) in a left pane and the game tiles in a right-pane `ScrollView` grid of vertical tiles (2-3 columns), with a 56pt gutter for the cog like the game footers; each side hugs its own safe-area inset. Portrait is the original single scrolling column. Home swaps whole trees between portrait and wide (the tiles, hero and panel remount on crossing the threshold - cheap here, unlike a game board; and `isWide` is held via `useFrozenWhileHidden` while Home is covered by a game/Achievements, so rotating a game doesn't rebuild the invisible menu - it re-syncs when Home is shown again), so everything that must survive lives ABOVE the branch (`HomeContent`'s state, the dialogs, the popover host), and the profile popover is closed on every rotation/layout change (its trigger is unmounted or moved under it). The rotated top/bottom insets are ~0 on a portrait-locked OS (a sideways phone has only left/right insets: +90 gives left 62/right 34, -90 the mirror) - nothing leans on them for breathing room.
- **`components/RotatedScreen.tsx` is the one frame every routed screen and the root overlays share.** `RotatedFrame` = `RotatedGameView > SafeAreaInsetsContext.Provider > [Portal.Host] > a flex:1 column (alignSelf center, width 100%, optional maxWidth)` - the same elements at every ROTATION angle, so a rotation never remounts anything inside (`portalHost` adds/removes the Portal.Host element, so it must be static per call site). `rotatedSafeArea` re-provides the safe-area insets already remapped onto the frame's own edges (`rotateInsets`), for a subtree that reads `useSafeAreaInsets()` itself (Achievements' `BaseStatsScreen`, `@tastic/profile`'s `ProfilesManager`, the Toaster, Paper's Modal content); Home and the games rotate insets themselves (`useHomeLayout`/`useGameLayout`), so they leave it off - both on would rotate twice. `portalHost` mounts a Paper `Portal.Host` inside the frame (every dialog portaled into it must be told `rotation={0}`). `passThrough` makes the frame's own boxes `box-none` so touches fall through to whatever is beneath (root overlays only; every box between the absoluteFill wrapper and the toast cards is `box-none`, including Paper's `PortalHost`, so the transparent overlay never blocks the Stack - verified in the simulator and by reading react-native-web's mapping). `maxContentWidth` caps the centred column ONLY in the wide layout (Achievements/Profiles pass 640; portrait, including a portrait iPad or desktop window, is never capped). `RotatedScreen` = `FocusedStatusBar` + `RotatedFrame portalHost`, used by Home (no insets provider), Achievements and Profiles (`rotatedSafeArea`, `maxContentWidth`). Pinned by `rotatedScreen.test.tsx` and `achievementsProfilesScreens.test.tsx`. **The root toaster works inside a turned frame as of `@rific/toaster` 0.7.1**, with no rotation prop of its own: its swipe-to-dismiss is measured in the toast's OWN coordinates (RNGH's `x`/`y` are relative to the attached view, computed through ancestor transforms, unlike window-space `translationX/Y`) - see `@rific/toaster`'s own CLAUDE.md for the mechanism. The keyboard-aware lift needed no change: `OrientationProvider`'s `portraitWhileKeyboard` (see the Home bullet's sibling note below) already reverts rotation to 0 while the software keyboard is up, so the toaster's own physical-bottom assumption is correct whenever it matters.
- **The Home corner buttons (trophy/cog) live in ONE plain zIndex:10 box-none View, never carry a zIndex themselves.** A Paper `IconButton` is a `Surface`, and on iOS `Surface` (`SurfaceIOS`) moves only `position`/`top`/`left`/`width`/`flex`/... onto its OUTERMOST view and leaves `zIndex` on an inner layer - so an `IconButton` with `style={{ zIndex: 10 }}` is still stacked at 0 on native, below any later full-screen sibling (Home's `ScrollView`), and got no touches (it looked right because the scroller is transparent there; web/Android keep the whole style on one view, which is why it only ever failed on iOS). `GameChrome` already avoided it by wrapping `CornerActionButtons` in a zIndex:10 View. **Going Home / entering a game is fast because of four invariants - don't undo them.** It used to take seconds (5s then 7.6s on the 1st and 2nd Home tap in a dev bundle, and growing by ~2.5s every round trip; 2.7s then 4.1s even with a production JS bundle), and this file used to call that "pre-existing, wait it out". Measured with the Simulator (production JS = `expo start --dev-client --no-dev --minify`, which isolates React dev-mode overhead from the real cost) after these fixes: Home tap ~20ms with no JS stall (was 2.7-4.1s), Home's first mount ~140ms (was 1.3-1.5s), game entry 0.2-0.5s of JS.
- **Home is `router.dismissTo('/')`, never `router.replace('/')`** (`GameChrome.tsx`). `replace` mounted a brand-new Home on top of the one already beneath the game, so every round trip leaked one more live Home (each a full menu); `dismissTo` pops back to the existing Home and only falls back to replace semantics when nothing is beneath (a deep link or the cold-launch resume). `back()` errors in that no-history case and `dismissAll()` returns nothing for a single-route stack, which is why `replace` had been picked in the first place.
- **`lastActiveGame` is not React state** (`stores/lastActiveGame.tsx`). Only Home ever read it, as a one-shot cold-launch resume; exposing it as state made every set/clear (each game mount, each Home tap) re-render every consumer and made each Home in the stack swap its whole menu for a `<Redirect>` and rebuild it, with the one-frame preview deferral already defeated (its `previewsRevealed` state survives the swap). The provider value is now stable for its lifetime and Home reads `consumeResumeGame()` once via `useState(consumeResumeGame)`. Any set/clear also drops a pending resume, so a deep link straight into a game can't later bounce back into a stale one. Covered by `src/__tests__/stores/lastActiveGame.test.tsx`.

**Also landed (second pass):**
- **Saves are coalesced** (`stores/gameInProgress.ts`). Every move used to `JSON.stringify` the whole board plus the whole undo stack (each undo entry embeds a full state snapshot - ~1MB after 300 Klondike moves, several MB for a long Spider game) synchronously in the move's own commit, and a foundation cascade does dozens of moves back to back. `saveGameInProgress` now only remembers the latest object and writes it after 500ms of quiet (3s max wait during an unbroken burst); it also flushes when the app leaves the foreground, when any game screen unmounts (`useSaveInProgressBackstop`), and before every read, and `clearGameInProgress` drops a pending write so it can't resurrect a cleared game. A hard crash can lose only the last half second of moves. Covered by `src/__tests__/stores/gameInProgress.test.ts`. `lastActiveGame` also skips rewriting an unchanged value.
- **Deal ghosts are a small pool of reusable slots** (`DealLayer.tsx`: `GhostSlot`, `ghostPoolSize`, `LOOKAHEAD_MS`/`LAUNCH_TICK_MS`; the absolute-deadline departures, face-up launch cap and slot-idle coalescing added on top are described in the face-up bullet below). A deal used to mount a full `PlayingCard` per dealt card (~52 mounts + 52 unmounts of card art; measured at ~half of a deal's remaining JS cost). Now `start()` sizes a fixed pool from the delays (the most flights that can overlap, counting each ghost as occupied from 150ms before its flight to ~80ms after it lands: 17 slots for 28 cards, 31 for 52) and `launchDue()` hands each card to a free slot ~150ms before its flight, re-basing its delay onto the launch. The deal's clock starts when the slots have MOUNTED (the `[generation]` effect), not at `start()`, so a slow mount delays every departure uniformly instead of spending the first cards' delays and sending them off together; cards that are LATE after a JS stall are spaced `LATE_LAUNCH_MIN_GAP_MS` apart (on-time cards keep their scheduled time) so a hitch doesn't become a blob plus a second blob. A slot is launched imperatively (`launch(spec, order)`: shared values reset to the origin/opacity 0 *before* the React commit that shows it, so the previous landing spot never flashes) and is hidden again by React state (`job` -> null), NOT a UI-thread opacity write, so it disappears in the same commit the caller's `onCardLanded` reveals the real card (a UI write ahead of that commit would blink a card-shaped hole). A landed slot is offered for reuse only from an EFFECT after that commit (`onIdle`), never from the landing callback itself - relaunching it in its landing tick would write the reset to the UI thread ahead of the reveal. Face-down deals reuse identical backs (the slot's face element is `useMemo`'d, so a relaunch renders nothing); face-up deals re-render a face instead of mounting one. `order` becomes `zIndex` so a later card still paints above an earlier one whichever slot it lands in. Skip lands both the in-flight slots (`completeNow`) and the not-yet-launched queue; a restart mid-deal keys slots by `${generation}-${slot}` (same key-reuse guard as before). Haptics are capped at one per 40ms like the sound pool. Covered by `src/__tests__/components/dealLayer.test.tsx`; verified on device for Yukon (52), Klondike (28) and FreeCell (52).

DealLayer's slot wrapper (`styles.slot`: absolute, top/left 0, only an absolute child) and DragGhostLayer's ghost container (only absolute children) laid out as exactly that. New Game unmounts all 52 real tableau cards (a card whose flight hasn't landed is only a bare `FlyingCardSlot` - see the dim-after-deal bullet below), whose outer views have frame `(0, index * fanOffset)` inside their column - a slot wrapper that drew one from the (LIFO) recycle pool sat at `y = index * fanOffset`, and every card that slot ever flew rendered exactly that many fan steps too low (x untouched, since a card's x within its column is 0), from its very first flight, for the whole deal, while the shared values, the shadow tree AND `measureInWindow` all said it was on target (they read the shadow tree; only the UIView was stale). Then the ghost's settle check passed (the values WERE right), the real card revealed at the right spot, and the card visibly "snapped up" - the bug this project chased across several sessions as a timing/settle problem. Pinned down with a frame-scanning detector over Simulator recordings (a card top edge below the deepest legal row): offsets of exactly 4 and 5 fan steps, always the same two of 18 slots, in every deal; 0 anomalous frames in 392 over 5 deals once the wrapper and card box carry `slotSize` (`width/height` = card size), and DragGhostLayer's container its group size. Ruled out on the way (each an A/B on the Simulator, not reasoning): the wrapper's zIndex/opacity toggling, the card box's size changing at its first face mount, Reanimated's synchronous transform path (animating `top`/`left` instead had the identical offsets), and card-view recycling alone (keeping the cards mounted only reduced it - the previous deal's pool and other unmounts feed the same pool). Guarded by `dealLayer.test.tsx`'s "ghost slot frames" and `dragGhostLayer.test.tsx`'s "ghost container frame" - nothing else about the layout needs the size, so it is exactly what a cleanup pass would remove. Pyramid's/Spider's/WinCascade's flight views have in-flow card content (non-zero frames) and are not exposed; a NEW overlay whose only children are absolute must set a size.
- **Unplayable cards dim once, for the whole board, after the deal - never card by card while it deals** (`games/shared/useDimAfterDeal.ts`, wired into FreeCell, Golf, Forty Thieves and Pyramid - the games whose deal leaves face-up cards buried; Spider/Canfield deal none, so they don't need it). A screen calls `hold()` with its New Game, `release()` when the deal has landed (its `onAllLanded`, and every bail-out path) and `releaseNow()` on restore; the dimming (`PileView`'s `dimUnplayable`, Pyramid's `dimHold`) is off while `held`, and turns on `DEAL_DIM_SETTLE_MS` (150ms) after the last landing - every buried card's scrim then fades in together (`dimFadeIn`/`HeldDimScrim`), and a `DEAL_DIM_MAX_HOLD_MS` backstop dims a deal that never reports back. Why: dimming each card as it landed mounted ~35 animated scrims one by one under cards still in flight, and **on iOS a fade's final opacity was measurably lost** - a whole deal's first row of buried cards stayed undimmed while JS had rendered them dimmed and every fade reported `finished` (reproduced ~1 deal in 3, pixel-checked; a resumed board's plain scrim never failed). This build commits Reanimated's animated props through the shadow tree (`IOS_SYNCHRONOUSLY_UPDATE_UI_PROPS` is off), where they race React's own commits. So **`FadingDimScrim` hands over to the plain, React-owned scrim the moment its fade reports done** (`fadeInDimScrim`'s `onDone`, `DIM_FADE_BACKSTOP_MS` if the callback never comes) - a finished dim is never left depending on the last value an animation wrote. Verified: 11 FreeCell deals and a Forty Thieves deal pixel-checked after settling (0 wrongly lit cards; the flagged ones were all real two-card runs), and frame-tracked: ~0 dimmed cards during the deal, all ~43 at once after. **The dim waits for the deal to finish in JS, not on screen:** the ghosts reach their spots on the UI thread on schedule, but each landing's reveal commit costs JS time, so the landing reports trail the ghosts (52-card FreeCell: last report ~2.1s after the first against a ~1.72s schedule), and the dim - and the skip layer's end - follow the reports, roughly 0.5s after the board looks complete.
- **A card whose flight has not landed is a `FlyingCardSlot`, not nothing and not the real card** (`PileView.tsx`). Every game's deal (all but FreeCell, which computes destinations analytically) and every tap-to-move/drop onto a tableau column finds where to fly by measuring the destination card through `CardRegistry` (`measureInWindow` on a registered, non-zero-size view). An earlier pass skipped flying cards from the tree entirely to save their mount cost and adapted only FreeCell - **that silently dropped eight games' deal animations (Forty Thieves measured 0/40 destinations; the cards just appeared) and every tableau-bound flight (the ghost was hidden, the card popped in)**, and no test noticed. Pinned by `pileViewMemo.test.tsx` ("keeps a card whose flight has not landed mounted and registered"). **When you change what a shared component mounts, check every game's use of what it used to provide** - here, a registration nine screens measure.
- **Every face-up card is ONE pre-rasterized `Image`** (`PlayingCard`; `src/components/cardFaceBitmaps.ts` + `assets/cardFaces/`, both GENERATED by `node scripts/generate-card-face-bitmaps.mjs` - rerun it whenever `@tastic/cards`' `CardFace` art or `palettes.ts`' card inks change; nothing checks for drift). A frame scan of a recorded deal found no blank/unloaded face, but the recorder only kept ~87 frames, so a one-frame decode flash is not ruled out - check a Release build on a device. `FoundationSlot`'s muted hint and `SettingsDialog`'s style swatches still draw the vector `CardFace`.

- **Initial deals are compressed to ~1.2s** (`dealStaggerMs(count)` in `dealSpring.ts`). - **Face-up deals are slower on purpose, and hand off without a visible pop** (FreeCell, Yukon's face-up half, Forty Thieves, Golf). **FreeCell's auto-play is two separate things, both started only by the player** (`src/games/freecell/autoPlay.ts` is the pure policy, unit-tested in `src/__tests__/games/freecell/autoPlay.test.ts`; the other foundation games - Klondike/Yukon/Canfield/Forty Thieves - still use the older "any manual foundation move arms the cascade" behavior, on purpose, since the request was FreeCell-specific).
- **The safe-card cascade** (`useAutoFoundationCascade`, engine mechanism A) starts ONLY from a TAP whose tap-to-move resolved to a foundation. `applyMove`'s `opts.viaTap` (passed by `handleCardTap`, absent from `attemptDrop`/`PileView`'s `dragConfig.onDrop`) is what tells a tap from a drag; a drag onto a foundation, a tap that lands on a column/freecell, and every silent move arm nothing. Like every game's cascade (see below), its cards overlap.
- **The finish** (`useAutoFinish`, engine mechanism B) starts as soon as the whole board can go up on foundation moves alone (`canAutoFinish` - every column sorted highest-to-lowest, freecell cards included), after ANY player move (a drag or a tap, to a column or a freecell, not just a foundation one), once the player's own move has landed. It is a plain async loop like the cascade's (below): each card leaves `FINISH_STAGGER_MS` (= `WIN_SWEEP_STAGGER_MS`, 96ms) after the last, so ~5 flights overlap and a 20-card finish takes under three seconds instead of a full flight-plus-measure round trip per card. The board's LAST card first waits (<= `FINISH_LAST_CARD_WAIT_MS`, two flights) for the earlier flights to land, so the win cascade doesn't start over cards still in the air. `nextSafeCascadeStep` returns null the moment the board is finishable, so the two never both fire at one settle.
- **Auto-played cards overlap, in every game with auto-play** (`useAutoFoundationCascade`, FreeCell/Klondike/Yukon/Canfield/Forty Thieves). The cascade used to send one card per settle: each card waited for the one before it to LAND (a full flight plus two measurements and a couple of renders). It is now a staggered loop like the finish: it starts once the player's own move has landed, then each card leaves `AUTO_PLAY_STAGGER_MS` (192ms) after the last one COMMITTED (`WIN_SWEEP_STAGGER_MS`, 96ms, once a draw has latched the sweep), so ~2.5 cards are in the air at once (~5 in the sweep). Because every flight takes the same time (see the flight-pace paragraph below), they land in exactly the order they left, and the gap is purely how fast the stream should feel - the flight's length doesn't change how long a cascade takes. The overlap is kept to the cascade's own plays; it polls the live `isSettled` (activeFlightCountRef, not the render value) and waits for EVERYTHING to land before (1) a draw/draw-and-play and the step right after it (stock/waste have their own flight machinery - draw-3 fans go through the deal layer - and the next play may take the card the draw is still flying in: acting on an airborne card shows it twice), and (2) a step after the board changed under it (`getState() !== expected`: the player moved mid-cascade - a drag's drop settles in its own distance-scaled time a cascade card could overtake, and it may be landing on the card the next step would take). That is why every screen's `firePlay` resolves `true`/`false` (committed or not): a miss must not re-baseline `expected` onto someone else's board. The first card still waits for the player's own card to land, for the same reason. Pinned by `useAutoFoundationCascade.test.tsx` and FreeCell's screen test (`the follow-up cards leave one stagger apart...`, which fails on the old hook). Not observed on a device.
- **Every auto-played step is its own undo entry, in every game with auto-play** (FreeCell, Klondike, Yukon, Canfield, Forty Thieves), so one Undo takes back exactly one card and the player can stop where they like. Each silent foundation move, sweep draw and sweep recycle pushes an entry holding the board just before it; a draw-and-play (stock straight to a foundation) pushes TWO (the draw, then the waste->foundation play), so each undo is a move kind `handleUndo` already flies. Auto-plays still never count toward moves/score, and every `handleUndo` calls `cascade.disarm()` so an undone card doesn't fly straight back up. The old shapes (Klondike/Yukon/FreeCell folded auto-plays into the previous entry's `cascaded` list; Canfield/Forty Thieves left them off the stack, so they snapped back with the player's move) survive only as legacy-save handling: the `cascaded` undo paths and the buried-foundation-card lookups stay for saves written before this change. Spider's completed-run removal is a rule, not an auto-play, and still undoes with the move that completed it.
- **What suppresses it:** an undo, a resumed save and a new deal (`finish.suppress()`) - nothing finishes again until the player's next move, so undoing back onto a finishable board can't immediately re-fire the cards just taken back. Both halves honor Settings' Auto-Move to Foundation. A resumed, already-finishable board sits until the player makes any move.

**Every card flight takes ONE fixed time, there is ONE pace knob, and a ghost is only ever retired at its spring's REAL end.** `dragdrop/dragSpring.ts`'s `FLIGHT_SPRING` (scale-1 225ms = 360ms at the default) is every flight: tap-to-move, undo, draw-1, a recycle, every auto-played and finish card (`DragGhostLayer`'s `flyTo` on a `show()` flight), Pyramid's pair flights (`FlyingPairCard`), Spider's completed-run flights (`FlyingSequenceCard`) and Klondike's/Canfield's draw-3 fans and their undo (through the deal layer: `DealAnimator.start`'s optional 6th `spring` argument, which also sizes the ghost pool and times the landing check) - however far it goes (Jay, 2026-10-01). Distance-scaled flights let a short hop overtake a long one to the same pile (two quick taps, or an auto-played card after a tap), and `FoundationCell`'s `settledCard` counts in-air cards, so the overtaken card showed on the pile while still airborne; and once flights overlap, a stream's pace is its gap, not its flight. Two exceptions: **a drag's drop** (`flyTo` on a `showLive()` flight - `flyTo` takes no pace options, it decides by `source`) settles over `dropSpringFor(the distance the finger left)` (scale-1 130-320ms = 208-512), because the card is usually nearly there and a full flight would leave the ghost covering the real card after every drag; and **everything else through the deal layer** (`DEAL_SPRING`, 280ms, unscaled - `start`'s default: deals, Spider/Scorpion stock deals, Aces Up rounds, Pyramid's win sweep, Klondike's legacy cascade-return undo). `SNAP_BACK_SPRING` (240ms) is unchanged too. `FLIGHT_TIME_SCALE` (1.6) multiplies the flight and drop durations. `scaledMs(ms)` is how any constant that must follow a flight derives from it (never hard-code a second copy): `AUTO_PLAY_STAGGER_MS` (`scaledMs(120)` = 192) and `WIN_SWEEP_STAGGER_MS` (`scaledMs(60)` = 96, also FreeCell's `FINISH_STAGGER_MS`), so the auto-play streams overlap their flights the same way at any pace, FreeCell's `FINISH_LAST_CARD_WAIT_MS` (2 x `springSettleMs(FLIGHT_SPRING)` = 966), `GameChrome`'s `UNDO_HOLD_REPEAT_MS` (`scaledMs(250)` = 400), Pyramid's `DEFER_MAX_WAIT_MS` (3 x a flight's settle = ~1.45s, so a deferral can never expire before its own draw ghost can land) and `SWEEP_WIN_REVEAL_MAX_WAIT_MS` (twice the nominal last-removal + sweep + hold timeline). Deliberately NOT scaled: `DEAL_SPRING`/`dealStaggerMs` (the deal), `SNAP_BACK_SPRING`, `useWinReveal`'s 400ms hold (a beat after the LAST landing, whatever the pace) and its 2.5s max wait (still ~3.7x the slowest single flight), `useCascadeFeedback`'s 45ms floor (a sound-pool limit, not a pace). **Reanimated's duration-based `withSpring` `duration` is the PERCEPTUAL duration: the spring really runs 1.5x that** (springUtils.ts's `perceptualCoefficient`), **and its solver caps stiffness at 8000, which with the default mass of 4 is reached at ~184ms: every shorter duration silently ran as the SAME ~283ms spring.** So the old 40-170ms (scale 1) sweep/auto-play flights were ~283ms springs whose ghost was retired at 40-170ms, with up to ~180px still to travel - the "cards vanish partway through" report. `FLIGHT_SPRING_MASS` (0.1) lifts the cap (critically damped motion depends only on sqrt(stiffness/mass)); the springs are exact down to ~30ms. Every timer that covers a spring uses `springSettleMs(config)` = `ceil(1.25 x duration + 33)`, never the bare `duration` (`DragGhostLayer`'s `settleAfter` - snapBack included - Pyramid's `FlyingPairCard`, Spider's `FlyingSequenceCard`; the deal's own timer is left at the bare `DEAL_SPRING` duration - measured 2.5px short of a 300px flight (7px of 900px) with the spring two frames late, judged not visible; a deliberate follow-up if it ever is): the 1.25 puts the tail under 0.4px for any distance, and the 33ms (two 60Hz frames) is the UI thread starting the spring after the JS timer that covers it - absolute, so it is added rather than folded into the factor (a flat 1.3 leaves 2.6px of a 100px sweep flight). `src/__tests__/components/dragSpring.test.ts` drives Reanimated's OWN `withSpring` frame by frame and requires < 1px residual at the retire time for every config at 60-900px (worst 0.68px, with the spring starting two frames late; the old timer left 50-310px on the sweep tier), and that every flight really ends at 1.5 x its duration. **Same-source hand-off rule (`DragGhostLayer.tsx`):** `showLive`'s persistent gesture values are shared by every drag from one slot/column, so a flight only sits on them WHILE ITS DRAG IS IN PROGRESS - `DragFlightHandle.release()` (called by `PileView`/`DraggableCard` as the first thing at drag end, before any await: a drop can sit in a hit test, a measurement or Pyramid's deferral for hundreds of ms) hands the ghost values of its own holding the same position. The ghost reads BOTH value sets from its first render and a `handedOff` shared value, written last, switches it (no re-render, no remount, no seam - cloning values under a mounted ghost, tried before, needs a re-render and jumps). After release a next drag from the same source can never touch the flight, applied or not; only a SNAP-BACK in progress (the very card being picked up again) and a drag that never released are still ended by a new claim (`liveOwnersRef`). `PileView` also captures its drag's own flight BEFORE the hit-test await (it used to read `flightRef` after it, so an overlapping drag's drop was applied with - and flew - the wrong ghost), and both `PileView` and `DraggableCard` stamp each drag with a token so a late drop/snap-back outcome never un-hides the cards under a NEWER drag. A flight's motion and settle timer begin once its ghost view has MOUNTED (`MountGate`, a layout effect): `flyTo` right after `show()` (the undo recycle flights) used to start the spring a whole render-and-commit before the ghost existed, so the ghost first appeared partway along its path. Pinned by `dragGhostLayer.test.tsx` (the real provider + `PileView`/`DraggableCard` with captured pan callbacks and a Reanimated stand-in whose values really animate over fake time).

**The win celebration is delayed until the winning card has flown in and landed (`useWinReveal`, `games/shared/useWinReveal.ts`) - a card must never teleport.** `won` flips in the SAME commit as the winning move, and the old code hung the celebration (foundations hiding their real cards so the bouncing win cascade can take over, fireworks, banner) straight on it. Hiding the foundations unregisters the very card the last flight is measuring to land on, so `CardRegistry.measure` returned null, the drain effect took its `!landed` branch (`flight.hide()`), and the winning card simply APPEARED while the fireworks started. Now `won` stays game state only (clock, recorded stat, cleared save, undo/hint gating) and a separate `winRevealed = useWinReveal(won, settled)` - true once `won` AND nothing is flying have held for 400ms (2.5s max wait so a win is never withheld; the optional third `maxWaitMs` param is for a screen whose winning move starts a longer sequence the reveal must wait for - Pyramid's sweep deal passes 4s) - gates only the visuals and the start of the win cascade (its `pendingWinCascadeRef` effect returns early unless `winRevealed`, deps `[state, winRevealed]`). Don't move a save/stat/clock concern onto `winRevealed`: the win must be recorded the instant it happens. **The reveal hands the real piles over to the bouncing win-cascade ghosts in ONE commit, in every game** (Scorpion's pattern, `cascadeHandoffFor`/`cascadeHandoff` in each screen): `runWinCascade` measures the always-mounted, card-sized origin containers while the real cards are still drawn (Pyramid's is one chain from the discard, after its sweep deal - see the Pyramid paragraph), then calls `winCascade.startChains(...)` and sets the hand-off state in the same async continuation (React batches them into one commit), and the real cards blank only when `winRevealed && handoff matches the current state object` (identity, so an undo or New Game un-blanks with nothing to reset; a pile whose chain didn't start, e.g. an unmeasurable origin, is never blanked). The old order - blank on `winRevealed`, THEN await `measureView`, THEN `startChains` - left every pile empty for a few frames (~140ms in a dev bundle) before the ghosts mounted. `WinCascadeLayer` also parks each chain's head ghost visible at its origin until its staggered entrance (followers peel off one at a time), and `ChainSpec.cardOrigins` (opt-in; Scorpion only) lets a fanned run keep every card's own spot into the cascade instead of collapsing onto the King's slot (`winCascadeMotion.ts`'s pure `cardXAtElapsed`/`cardYAtElapsed`/`fanOffsetScale`). Aces Up's origin is the drawn Ace's own `CardRegistry` rect (its pile container is `maxHeight` tall, not card-sized, and `ChainSpec.origin` must be card-sized for the rotation conversion) - worth a look under fake landscape. Spider refuses a second stock deal until the first has fully landed (`stockDealTokenRef`) and ignores taps/drags/deals/undo while a completed run is still assembled awaiting its sweep (`sweepPendingRef`/`claimSweep`), since the sweep cuts 13 cards off the end of that column. FreeCell also falls back to flying to the foundation slot's own card-sized container (`foundationSlotRefs`) when a landing card can't be found in `CardRegistry`, instead of hiding the ghost, and refuses a move whose grabbed card is no longer at the head of the pile (`moveHeadCard` in `freecell/rules.ts`, checked in `applyMove`): `tryMove` only knows positions, so a drop arriving after an auto-play took that very card would otherwise move whatever now sits there while the ghost shows a different card.
