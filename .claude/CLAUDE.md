# Solitaire

An ad-free, self-contained solitaire suite (Klondike, Spider, FreeCell, Pyramid) built with Expo. Part of the `@rific`/`@tastic`/InfiniteToken app ecosystem — depends on `@rific/auto-paper`, `@rific/feedback-press`, `@rific/focus-chain`, `@rific/splash-gate`, `@rific/toaster`, plus `@tastic/profile` (+ its `@tastic/core`/`@tastic/hud` peers) for player identity (a color + short tag, shared across the fleet via an iOS App Group) — unlike the fleet's physics-driven games, there's still no board-physics or split-screen engine here, just tap/drag card-game logic. A selected player's color/tag only drives the cosmetic card-back palette (`src/components/theme.ts`) - the felt is deliberately NOT profile-tinted, see the root-felt note below — it never segments `stats.ts`/`settings.ts`, which stay global regardless of who's selected.

**Expo has changed.** Read the exact versioned docs at https://docs.expo.dev/versions/v57.0.0/ before writing any code — don't rely on general Expo knowledge, this app is on SDK 57 specifically.

## Commands

```bash
npm run lint          # expo lint .
npm run fix            # expo lint . --fix
npm test               # Jest (44 suites, 572 tests)
npm run typecheck      # tsc
npm run verify         # lint + test + typecheck
npm run doctor         # expo install --fix && expo-doctor
npm start              # Expo dev server
npm run client          # Expo dev server (dev client build)
```

Always run `npm run lint` before finishing any task. This is an app (`"private": true`, no publish scripts) — `verify` doesn't include a build step.

**No `build:*`/`update` scripts exist in this app at all**, unlike every other app migrated onto this tooling so far (Swirlio, LightCycles, BoxHockey, CashierFu-Utility, Pong, AirHockey, Snake all have EAS `build:development`/`build:preview`/`build:production` and `update` scripts gated behind `verify`). Solitaire's `package.json` never had EAS build/update scripts to begin with — nothing here to gate. If EAS scripts are added later, gate them the same way (`"npm run verify && " + <script>`, inline-chained onto the script's own definition, not a separate `pre<script>` hook) — see Swirlio's CLAUDE.md for the full reasoning.

**The deal animation's destination measurements raced the React commit they depended on, and silently dropped ~90% of the board when it lost.** `CardRegistry.measure(cardId)` (`components/dragdrop/CardRegistry.ts`) only resolves once that card's own registration `useEffect` has run — but the deal's initial implementation called `measure()` for all 28 destination cards *synchronously, right after* `setState(newTableau)`, before React had even committed that render, let alone run the new cards' registration effects. Confirmed live: this raced the *previous* deal's still-registered (but about-to-be-replaced) cards against the *new* deal's not-yet-registered ones, and mostly matched neither — 25 of 28 destinations came back `null` on one measured run, silently excluding those cards from `entries` and leaving them hidden forever (a card whose destination is `null` never gets added to `deal.start()`'s entries, so it never fires `onCardLanded`, so its id never leaves `dealHiddenIds`). The fix: never call `CardRegistry.measure()` synchronously after the `setState` that mounts the new cards. Instead, stash a "deal is pending" token and do the actual measurement from a `useEffect` keyed on `[state]` — React fires effects bottom-up per commit (children's before parents'), so by the time a *parent* component's `[state]`-effect runs, every child `PileView`/`DraggableTableauCard` for that same commit has already run its own registration effect. See `KlondikeScreen.tsx`'s `pendingDealTokenRef` for the pattern; `PyramidScreen.tsx`'s equivalent doesn't need it for the *destination* side, since its destinations are computed analytically (`cardPosition()`) rather than via `CardRegistry.measure()` — it only measures two container refs (the stock pile, the triangle container), which aren't subject to this per-card mount race. It still needs the same `[state]`-deferral for the *origin* side, though: those two container refs are themselves behind Pyramid's `if (!state) return <GameLoading />` branch, so on the very first mount they aren't attached yet at the moment `startNewGame` calls `setState` — calling `runDeal` synchronously right after that (as it originally did) measured two still-null refs and silently skipped the deal (cards just appeared with no animation, every time you navigated to Pyramid fresh). Fixed by giving Pyramid its own `pendingDealTokenRef` + `[state]`-effect, same shape as Klondike/FreeCell/Spider — confirmed all four now defer their initial `runDeal` this way.

**A second, unrelated bug found in the same session: reused React keys across separate deals silently stalled a handful of cards forever.** All 52 cards' ids are shuffle-independent (`${suit}-${rank}-${deckIndex}`, see `engine/deck.ts`) — a fresh deal reuses the exact same ids as the one before it, just redistributed. If `deal.start()` is ever called again while a previous deal's ghosts are still mounted (shouldn't happen in normal play, since the skip-overlay covers the "New Game" button during a deal too, but is easy to trigger via rapid/automated interaction), React reconciles by id and reuses the *same* `DealGhostCard` instance for a repeated id rather than unmounting and remounting it — meaning its `useSharedValue` position and its "already notified" guard ref never reset, since both only initialize on a genuine first mount. Fixed by folding a monotonic generation counter into each ghost's React `key` (`DealLayer.tsx`'s `generation`), forcing a real unmount+mount - and therefore a full state reset - on every `deal.start()` call regardless of id overlap with the deal before it. The same generation is also stamped on every slot (`deal`) and checked in every callback (`generationRef`, bumped synchronously in `start()`, which also `cancel()`s the old slots), because the old slots stay mounted - timers live - until the commit AFTER `start()`: a timer firing in that gap used to report a stale card into the new deal.

**Pyramid's pairing/King removal lands cards in a real discard pile (`PyramidState.discard`, `rules.ts`) instead of just deleting them.** A solo King flies as a single card via the shared `ghost` (`DragGhostLayer`/`useDragGhost`), same as every other single-card flight in this app. A pair instead flies as **two cards travelling independently at the same time**, each from its own real board position straight to the discard pile (`PyramidScreen.tsx`'s `startPairFlight`/`PairFlightGhosts`/`FlyingPairCard`) - not merged into one stack, and not one card visiting the other before either moves. The single shared `ghost` can only ever animate one origin/delta for its whole group (see `DragGhostLayer.tsx`), so two cards converging from different starting points needed their own small overlay instead - the same "N independent simultaneous ghosts" idiom `DealLayer`/`WinCascadeLayer` already use for the same reason (see `DealLayer.tsx`'s doc comment), just with each ghost getting its own independent origin/destination instead of a shared one. Each card's flight is its own `withSpring`, scaled to its own distance from the discard pile via the same `autoMoveSpringFor` every other flight in this app uses, so a card starting closer settles sooner than one starting further away. For a drag-completed pair, "first" is still sitting mid-drag in the shared `ghost` at drop time - its live position is read directly off `ghost.originX/Y.value + dx/dy.value` before handing off to its own independent flight and retiring that ghost (`ghost.hide()`). Two earlier shapes of this flight were tried and rejected first: originally "first" visibly flew onto "second" before the (already-merged) pair continued on to discard, as two distinct legs; replacing that with a single flight of the two cards already merged into one stack (skipping the first leg, but still one shared ghost) was also rejected - both read as one object moving, when the actual ask was always two cards animating independently to the same destination at the same time. The discard pile itself (`PyramidScreen.tsx`'s `DiscardCell`) measures its position like `stockViewRef`/`triangleViewRef` (a plain view ref, `measureView()`) rather than `FoundationCell`'s per-card `CardRegistry` registration - there's only ever one discard pile, not a slot whose occupant identity keeps changing. **Undoing a pairing/King removal now animates too, flying each card independently from the discard pile back to its own original spot** (`PyramidScreen.tsx`'s `undoRemoval`, `RemovedCardRef`) - the mirror image of the forward removal flight: one shared origin (the discard pile, which doesn't move) fanning out to each card's own destination, reusing the same `PairFlightCardSpec`/`PairFlightGhosts`/`startPairFlight` machinery (generalized so each card's spec now carries its own `to` as well as its own `from` - the forward flight shares one `to` across cards with independent `from`s, the undo flight shares one `from` with independent `to`s). `UndoEntry` gained a `removedCards: RemovedCardRef[] | null` field (the PileRef each removed card came from) alongside the pre-existing `move: MoveInfo | null` for stock draws - the two are mutually exclusive. **Every undo resolves ALL its endpoints BEFORE it commits, and mounts its ghosts in the same synchronous stretch as the revert** - a pyramid-cell destination is pure math (`cardPosition` + the measured `triangleViewRef`), a waste-bound card's is the always-mounted waste container (`wasteViewRef`; there is one waste slot, so it is the same place the card's own registration would say), and the discard/stock are plain containers too. The old shape (commit the revert, then a `[state]`-effect measured the destinations and only then started the flight) left the restored cards visible NOWHERE for a frame or two (the discard already showing its older top, the cards hidden, no ghost yet) before the ghosts popped in. Undo of a draw and of a recycle measure both endpoints first and do `ghost.show` + `beginFlying` + `setStockHidden(true)` + `commitState` + `flyTo` in one stretch; undoing a draw also freezes the stock slot (`stockHidden`) until the returning ghost lands, instead of showing the returned card at once. The restored card(s) have to be hidden (`pyramidHiddenIds` for a pyramid destination, reusing `flying`/`wasteHiddenCount` for a waste one) in that same commit - React batches same-tick `setState` calls - to avoid a frame where the restored card flashes fully visible before its ghost covers it (same reasoning `startNewGame`'s `setPyramidHiddenIds(dealtIds)` already relies on for the initial deal). A waste-bound card's `flying` entry ends with ITS card's landing (the pair ledger's `flying.cardId`), not with the whole pair, so a landed Ace is not hidden again while the Queen is still on its way. `dealHiddenIds`/`isDealHidden` were renamed to `pyramidHiddenIds`/`isHidden` to reflect that the same hidden-until-landed mechanism now covers two different reasons a pyramid cell's card might be flying in, not just the initial deal. A card whose destination cannot be measured (a rare edge case) simply has no ghost and is not hidden, rather than left stuck invisible forever. **Fast play:** pair flights are independent - `pairFlights` is a list with a per-flight ledger keyed by gen (a landing settles only its own flight; a single slot let the next pair replace the last one, so its ghosts vanished mid-air and its `activeFlightCount` claim never settled), and the discard shows the topmost card not in `discardInAir` under the ghosts (`DiscardCell`'s additive `settledCard`, the `FoundationCell` idiom). Every action claims its flight synchronously (`claimFlight`, generation-stamped) and **re-validates against `stateRef.current` after its measurement awaits** (`replayMove`, then one synchronous `commitRemoval`) - committing the pre-await `result` overwrote whatever committed meanwhile and let a double-tapped King be removed twice. Pinned by `pyramidScreenQuickPlay.test.tsx`, whose mocked measurements have a latency so taps really overlap. **Overlapping draws and the waste:** the waste slot's frozen copy of the pre-flight top goes stale once draw flights overlap (each landed ghost vanished onto the card from before the whole stream), so `wasteInAir` (the waste's `discardInAir`) tracks the drawn cards still flying and the screen passes `StockWaste` the additive `settledWasteTop` (the topmost waste card not in it; omitted - `undefined` - keeps the frozen copy, which every other game and every non-draw flight still uses). **A card is never acted on while its own draw ghost is airborne:** a tap/drop on it (or a pair completed with it) waits - `whenLanded`, re-checked at every landing, bounded by `DEFER_MAX_WAIT_MS` - so the card visibly arrives, THEN flies on (measuring the hidden real card would start a second ghost from a slot the drawn card has not reached, shown twice); a draw waits out a recycle's group ghost still flying into the frozen-empty stock, and a recycle waits out draw ghosts still landing (it would pick the airborne card up twice) - plain draws still overlap freely. The check comes AFTER the measurement awaits and does not yield when nothing is in the way, so an earlier tap's commit is never interleaved with a later one's. **Every such wait is a LOOP, not a single check** (`while (!gate() && budget.left() > 0) await whenLanded(gate, budget.left())`, inline at all three call sites - `attemptMove`, `attemptDrop`, `handleDrawStock`): being resumed is not proof the gate still holds, because a landing resolves EVERY waiter whose predicate held at that instant and their continuations then run one after another - the first (a recycle) re-freezes the stock for the next, which used to draw from the freshly recycled stock while the recycle's group ghost was still flying into it (stock [5], waste [2, 3], three quick stock taps). The loop must stay inline (a helper looping inside an async function hands its answer back across a microtask boundary in which a sibling can change it again), and its deadline is ONE budget per action (`startDeferBudget`), not a fresh `DEFER_MAX_WAIT_MS` per resume. **`commitRemoval` drops a selection that names a card it removes** (`setSelected((sel) => removed.some(refsEqual) ? null : sel)`): an action clears the selection when it starts and may then park in the wait above, and a tap in that window selects the waste as `{waste, 0}` - "whatever is on top" - which, once the deferred pair had removed that card, pointed at the card that was UNDER it (highlighted, and paired by the next tap: a move the player never chose). A selection of an unrelated card made during the wait is kept. **New Game/restore retires every shared-ghost flight still in the air** (`trackFlight`/`hideAirborneFlights`: a King's, draws' - queued ones included -, recycles', undos'), after bumping `dealTokenRef` so their completions are generation-guarded; dropping `pendingFlightRef` alone left queued ghosts mounted for good.

**Pyramid's win is a SWEEP DEAL, then one chain from one pile.** rules.ts still folds whatever is left in the stock/waste into the discard ON the winning move (a won game's discard is all 52 cards, waste bottom-to-top then stock bottom-to-top - the order everything else depends on), so `won` stays game state exactly as before (clock, stat, save, recorded the instant it happens). But nothing flew for that fold, so the leftover cards now fly: the winning removal's `commitRemoval` calls `beginWinSweep`, which claims a flight (`claimFlight`, while the removal's own claim is still held, so `settled` never blips true) and marks every leftover as in the air on the discard (`discardInAir`, so the pile's top is always a card that really landed). Once nothing but the sweep's claim is outstanding (`activeFlightCount` down to 1 - the last removal has landed), `runSweep` deals the leftovers through the existing deal machinery (`useDealAnimator`: same stagger `dealStaggerMs`, spring, throttled sound/haptics and skip-tap - no flight layer of its own), one card per swept card from its own pile (the waste slot for the waste's, the stock slot for the stock's; a pile that cannot be measured deals from the other one, only with no origin at all does a card simply land) to the discard, in the discard array's order, face-up (the deal layer cannot turn a card over in flight, and every swept card is face-up already). The board keeps showing the pre-fold piles (`winHoldView`, kept in `sweepUi.view`, keyed to the won state's identity) and empties each pile when its last card takes off - driven by the deal layer's own take-off signal, `DealAnimator.start`'s additive optional `onCardDealt(cardId)` (once per card, at the instant its ghost is drawn over the spot it leaves; reported for every not-yet-taken-off card when a skip lands the deal at once; silenced by a cancel/restart exactly like `onCardLanded`), `SWEEP_PILE_BLANK_LAG_MS` after the pile's LAST card, on the run's timers so `cancelSweep` clears it. A timer armed from the scheduled delays right before `deal.start` (what this used to be) runs on the wrong clock: the deal's own clock only starts once its ghost pool has rendered and mounted (several frames on a phone) and a card's real take-off is that clock + its re-based delay + the render of its launch, so the timer ran ahead and the pile sat empty until the ghost popped in (worst for a pile whose last card leaves at delay 0). Pinned by `pyramidScreenWin.test.tsx`'s mount-latency cases and `dealLayer.test.tsx`'s `onCardDealt` block. The deal's `onAllLanded` (or a skip, which lands everything at once) settles the claim exactly once; a New Game mid-sweep, or the reveal's fallback timer, ends it via `cancelSweep` (an empty `deal.start([])` is the deal layer's only cancel). Timeline: last removal lands -> sweep (up to ~1.1s for 24 cards) -> 400ms hold -> reveal, so `useWinReveal` gained an additive `maxWaitMs` and Pyramid passes 4s (nominal ~1.9s worst case against the default 2.5s was too thin for a phone's JS stalls). The reveal then launches ONE chain of all 52 discard cards (head = the card on top) from the discard container; the discard blanks only in the commit its ghosts mount (`cascadeHandoff`, now just the discard). **A 52-card chain at the usual 42ms per card trails its head by ~2.1s - more than two bounce half-periods - and splits into a wave** (the ~28-card discard chain it replaced already did), so `ChainSpec` gained an additive `segmentDelayMs` and Pyramid passes `chainSegmentDelayMs(count)` (`winCascadeMotion.ts`: the usual delay, tightened so the whole head-to-tail span stays within `CHAIN_MAX_SPAN_MS` = 500ms, ~9.8ms per card at 52); `isGhostVisible` takes the chain's own delay. Pinned by `pyramidScreenWin.test.tsx` (a deal harness that follows the real deal's timeline) and `winCascadeMotion.test.ts` (a 52-card chain bends at most once with the cap, twice without).

**Landscape rotation is a fake: the OS stays portrait-locked and the game screen is visually rotated** (`@tastic/core`'s `OrientationProvider` reads the accelerometer; `useRotation()` gives 0/90/-90/180). Every game screen is wrapped by `withGameProviders` in `RotatedGameView`. Several things here exist only because of how that goes wrong:
- **`RotatedGameView` replaces `@tastic/core`'s `FakeLandscapeView` on purpose.** `FakeLandscapeView` (through 0.8.0) returned a different element tree at 0deg vs +/-90deg (`<View>` vs `<View><View>`), so React unmounted and remounted the WHOLE game screen - every card, all providers, and Inner's state (undo stack, hints) - on every rotation. Measured in the simulator: ~700-800ms of JS per rotation versus ~90-250ms for the update it should be. `RotatedGameView` keeps one identical tree at every angle and only swaps styles. Don't reintroduce a per-angle branch in the tree. (Fixed upstream in the next `@tastic/core` release, unpublished at the time of writing - swap back once it ships.)
- **The "wide" layout (`components/gameLayout.ts`) is what makes landscape playable.** Any window whose ROTATED footprint is landscape (`isWide`: a phone held sideways, an iPad, a desktop browser) drops the vertical chrome bands (portrait reserves 56pt top + 88pt bottom, which would eat 144 of a ~402pt-tall landscape screen): `GameChrome` puts the footer controls (Undo/New Game/Hint/Rules) in a column in the RIGHT side gutter (where the thumb is) and the moves/score/time readout in the LEFT one, hides the title (rules stay reachable from the info button), and the corner buttons stay put. Tap-the-felt-to-hide-the-footer is portrait-only (there the footer floats over the board, so hiding it frees room; in landscape it sits in a gutter and hiding it would give the board nothing back). The two gutters are PER-SIDE (`leftGutter`/`rightGutter`, each = its chrome column + its OWN safe-area inset): sizing both from the larger inset left ~44pt of dead space between the footer buttons and the board on the small-inset side of a phone held sideways. `useGameLayout()` gives every screen its `contentWidth` (net of the gutters) and `availableHeight`. Portrait is byte-for-byte unchanged.
- **Cards are sized to fit the height in the wide layout** (`useFittedCardWidth` + a per-game `src/games/<game>/boardModel.ts`). A board's height is affine in card width (`columnBoardModel`: top row + tallest STARTING tableau column + a face-up headroom + paddings), so the fit is closed-form; each `boardModel.test.ts` asserts the model against a real deal. When the fit shrinks the cards, `useFittedGap` spreads the leftover width into the gaps (up to `CARD_GAP_MAX`). `useTableauMaxHeight` has no floor in the wide layout (the per-game 300-460pt floors are portrait-tuned and exceed a landscape screen). Pyramid/TriPeaks fit their own real board height (`geometry.ts`). Scorpion's wide layout has no top row: the assisted stock packet is absolutely positioned one gap past column 7 (tableau centred on its own, so the width budget is 7+2 columns; `useTableauMaxHeight(..., { topRowCards: 0 })`), which gives ~59pt cards on 874x402 and no tableau jump when the stock is dealt/undone. Known trade-off: Yukon's deep starting columns give ~46pt cards.
- **The game's dialogs render inside the rotated frame.** Paper's `Portal` mounts at the APP ROOT by default - outside the rotated frame - so Settings/Rules/the New Game confirm used to rotate themselves with a transform while their layout (a `maxHeight: '90%'` sheet) was still resolved against the PORTRAIT window: turned 90deg they ran off a 402pt-wide screen, and the Settings sheet lost its first row (Lock Orientation, the one you need to get OUT of landscape) with no way to scroll to it. `withGameProviders` mounts a `Portal.Host` inside `RotatedGameView` and OUTSIDE the three providers (so it paints above their ghost overlays and DealLayer's skip-tap layer); `GameChrome` passes `rotation={0}` to its dialogs. The menu (unrotated) keeps the app-root portal.
- **`@tastic/hud`'s `ContentGutter` read raw `useWindowDimensions()`, which never changes under a fake rotation** - it capped the rotated board at the portrait width. `RotatedContentGutter` sizes from the rotated width (and reserves the wide layout's side gutters). Fixed upstream in `@tastic/hud` (unpublished at the time of writing) - swap back once it ships.
- **Every screen-space measurement (`measureInWindow`, Reanimated `measure()`, `e.absoluteX/Y`) is a transformed bounding box in true screen space** - confirmed on iOS/Fabric. The ghost overlays (`DragGhostLayer`, `DealLayer`, `WinCascadeLayer`, Spider's `SequenceFlightGhosts`, Pyramid's `PairFlightGhosts`) live inside the rotated frame, so subtracting the overlay's offset (right only at 0deg) put ghosts in the wrong place and moved a dragged card along the wrong axis. `overlayFrame.ts`'s `useOverlayFrame()`/`toLocal()` convert screen -> rotated-frame via the card's centre. That conversion assumes the measured rect is CARD-SIZED: measure a card slot (`StockWaste`'s `wasteRef`), never a wider wrapper. Pyramid/TriPeaks compute some endpoints analytically (a measured container's top-left + a local `cardPosition` offset), which is only right at 0deg - `localOffsetToScreenPoint` composes those through the container's centre (`geometry.ts` in each game). All of it is unit-tested in `src/__tests__/components/overlayFrameMath.test.ts` and each `geometry.test.ts`.
- **Lock Orientation** (`Settings.lockOrientation`) works by withholding sensor samples from `OrientationProvider` while locked (`components/lockableDeviceMotion.ts`, wired in `_layout.tsx`'s `OrientationBridge`). The provider's ONE shared reading then freezes for every consumer at once - including a screen that mounts after the lock, which the per-call-site `locked` argument of `useRotation()`/`useOrientationState()` cannot do (a call site that mounts while locked snapshots the LIVE reading). A lock restored at launch pins the default (portrait) reading. `@tastic/core`'s upcoming `OrientationProvider freezeWhileLocked` does this properly (and latches the first confident reading for a launch-time lock) - adopt it and delete the wrapper when it ships.
- **`GameStatusBar`** (mounted by `withGameProviders`) hides the OS status bar whenever the board is rotated - it's glued to the device's physical top edge and can't rotate with the content - and is always `light` (the felt is dark in every appearance mode). A second always-light `StatusBar` sits next to the `Stack` in `_layout.tsx`; a root-level-only one never took effect on iOS (bar stayed dark on the menu). `@tastic/core`'s `RotationAwareStatusBar` gains a `style` prop upstream.
- **The felt is ONE `TableBackground`, mounted at the root behind the whole `Stack` (`ThemedStack` in `app/_layout.tsx`); no screen paints its own.** Every top-level screen (each game via `GameChrome`, Home, Achievements, Profiles, `GameLoading`) is transparent and draws over it - it used to be a per-screen first child, which left every screen that hadn't rendered its content yet (a game waiting on its saved-board read) showing the Stack's black instead of felt. It only shows if TWO things are transparent, and only one of them is obvious: the screens' `contentStyle` (set in `ThemedStack`, overriding the opaque black `useThemedRootBackground` returns) AND the React Navigation theme's `colors.background` (`TRANSPARENT_NAVIGATION_THEME`, wrapped around the `Stack` with expo-router's `ThemeProvider`). React Navigation paints `colors.background` on the layers AROUND each screen - the `ScreenStack`'s native container on iOS/Android, each screen's wrapper on web - and `contentStyle` only reaches the layer inside them, so `contentStyle: transparent` alone left an opaque light-grey (`rgb(242,242,242)`) slab over the felt on web (and would have hidden it behind the native container). The root window colour `useThemedRootBackground` also syncs stays black underneath, untouched. **The felt is one fixed green for every player - `lightColors.tableFelt` `#0B6E4F` / `darkColors.tableFelt` `#08573F` (vignette `tableFeltDark`) - because it has to equal the native splash screen's `backgroundColor` in `app.json`'s `expo-splash-screen` plugin config exactly.** The splash is compiled into the binary and painted before any JS runs, so it cannot know the active profile (or anything else at runtime) and cannot be made per-profile; a felt that varied by profile could only ever match it for one of them. The felt used to be derived from the profile colour (complement of the card-back hue, `#205a2d` / `#123f22` for the default seed) - a visibly different, darker, less blue green than the splash, which is what this replaced. A profile's colour now only tints the card back. `src/__tests__/components/splashMatchesFelt.test.ts` fails if `app.json` and `theme.ts` drift apart - change both together (a splash colour change also needs a new native build). Verified: web (all four top-level screens) and the iOS 27 simulator (video frames through a real Home -> Klondike push and a Home tap back: the sliding panel covers the previous screen cleanly, no bleed-through, no black flash, one continuous felt). **Android is handled by source-reading only, NOT observed** (no emulator was available): its default push/pop tween holds the outgoing screen at full alpha for ~450ms (`rns_default_enter_out`, API 33+), which would show Home straight through the transparent game screen, so `ThemedStack` sets `animation: 'fade'` for Android only (`rns_fade_*`, a 150ms symmetric crossfade) and leaves iOS on its UIKit push. If Android still ghosts a screen during a push/pop, or the fade feels wrong there, that is where to look. The felt is deliberately NOT inside `RotatedGameView`: a fake landscape rotation turns the game frame, not the device screen, and an ellipse fitted to the portrait screen reads as the same wide ellipse once the phone is held sideways (reasoned, not observed on a device); its `Svg` is keyed on the window size instead of the rotation, since `react-native-svg` doesn't re-resolve its percentage-based gradient `Rect` after a resize.
- **Every game screen's loading state is the one shared `GameLoading`** (`components/GameLoading.tsx`; `if (!state) return <GameLoading />`, Spider's is `!ready || !state`) - four suit glyphs pulsing in a wave, dead-centered, all opacity on the UI thread. It replaced eleven hand-copied "Loading..." branches (nine top-aligned, Spider centered, Pyramid on a different text style) and it draws no background of its own (the root felt shows through). The indicator (`LoadingIndicator`, also used by Achievements while stats load) stays invisible for the first 250ms and then fades in: every wait it covers is one AsyncStorage round trip (a saved-board read that `preloadGameInProgress` already starts on finger-down), normally a few dozen ms, so showing it at once would only be a flash. Pinned by `src/__tests__/components/gameLoading.test.tsx`.

**Going Home / entering a game is fast because of four invariants - don't undo them.** It used to take seconds (5s then 7.6s on the 1st and 2nd Home tap in a dev bundle, and growing by ~2.5s every round trip; 2.7s then 4.1s even with a production JS bundle), and this file used to call that "pre-existing, wait it out". It was not: it was algorithmic (the production-JS figures are roughly half the dev ones, so most of it is real work rather than dev-mode overhead; the native side was still a Debug build, so a Release build on a phone remains the true check). Measured with the Simulator (production JS = `expo start --dev-client --no-dev --minify`, which isolates React dev-mode overhead from the real cost) after these fixes: Home tap ~20ms with no JS stall (was 2.7-4.1s), Home's first mount ~140ms (was 1.3-1.5s), game entry 0.2-0.5s of JS.
- **Home is `router.dismissTo('/')`, never `router.replace('/')`** (`GameChrome.tsx`). `replace` mounted a brand-new Home on top of the one already beneath the game, so every round trip leaked one more live Home (each a full menu); `dismissTo` pops back to the existing Home and only falls back to replace semantics when nothing is beneath (a deep link or the cold-launch resume). `back()` errors in that no-history case and `dismissAll()` returns nothing for a single-route stack, which is why `replace` had been picked in the first place.
- **`lastActiveGame` is not React state** (`stores/lastActiveGame.tsx`). Only Home ever read it, as a one-shot cold-launch resume; exposing it as state made every set/clear (each game mount, each Home tap) re-render every consumer and made each Home in the stack swap its whole menu for a `<Redirect>` and rebuild it, with the one-frame preview deferral already defeated (its `previewsRevealed` state survives the swap). The provider value is now stable for its lifetime and Home reads `consumeResumeGame()` once via `useState(consumeResumeGame)`. Any set/clear also drops a pending resume, so a deep link straight into a game can't later bounce back into a stale one. Covered by `src/__tests__/stores/lastActiveGame.test.tsx`.
- **Home's tiles are one small `Svg` each, not real cards** (`components/GamePreview.tsx`). The menu used to mount ~374 full `@tastic/cards` CardFace/CardBack trees drawn ~7x10pt - ~12k native views (every react-native-svg element is a real, never-flattened native view; court cards alone are ~200KB of path text each). A column-layout tile (everything but Pyramid/TriPeaks) is now merged into at most five `Path`s by drawing only each card's *visible strip* down to the next card in its column, so nothing overlaps and same-kind shapes can share a path (`components/previewGeometry.ts`, pure and unit-tested; the two overlapping layouts stay one `Rect` + pip per card) - ~100 nodes for the whole menu, ~12k before; it keeps the face/back split, suit colors, the theme's card-back color and invert-dark-mode. `src/__tests__/components/gamePreview.test.tsx` fails if the heavy art comes back. The same lesson is Swirlio's (see the comment atop its `src/constants/kaleidoscope.ts`): node count, not JS logic, is what stalls a phone - and Mac-simulator timings understate a real device, so a Release build on hardware is the real check.
- **Nothing ticks state at `GameChrome` level.** The once-a-second clock lives in `ElapsedClock` (`GameChrome.tsx`), so only the moves/score/time readout re-renders per second; the whole chrome used to, at ~140ms of JS per tick (~14% of the thread while dragging cards). Likewise `HeroCards` cancels its forever-loops while Home is blurred (`useIsFocused`), since Home now stays mounted under every game.

Also fixed on the same pass: the deal's full-screen skip-tap layer (`DealLayer.tsx`) stops short of the top chrome band (Home/Settings/title), so tapping Home mid-deal leaves at once instead of first just skipping the deal; and `PlayingCard`'s per-card gloss is one `Image` of a pre-baked gradient (`assets/card-sheen.png`) instead of a 7-view SVG on every card.

**Also landed (second pass):**
- **Saves are coalesced** (`stores/gameInProgress.ts`). Every move used to `JSON.stringify` the whole board plus the whole undo stack (each undo entry embeds a full state snapshot - ~1MB after 300 Klondike moves, several MB for a long Spider game) synchronously in the move's own commit, and a foundation cascade does dozens of moves back to back. `saveGameInProgress` now only remembers the latest object and writes it after 500ms of quiet (3s max wait during an unbroken burst); it also flushes when the app leaves the foreground, when any game screen unmounts (`useSaveInProgressBackstop`), and before every read, and `clearGameInProgress` drops a pending write so it can't resurrect a cleared game. A hard crash can lose only the last half second of moves. Covered by `src/__tests__/stores/gameInProgress.test.ts`. `lastActiveGame` also skips rewriting an unchanged value.
- **Deal ghosts are a small pool of reusable slots** (`DealLayer.tsx`: `GhostSlot`, `ghostPoolSize`, `LOOKAHEAD_MS`/`LAUNCH_TICK_MS`). A deal used to mount a full `PlayingCard` per dealt card (~52 mounts + 52 unmounts of card art; measured at ~half of a deal's remaining JS cost). Now `start()` sizes a fixed pool from the delays (the most flights that can overlap, counting each ghost as occupied from 150ms before its flight to ~80ms after it lands: 17 slots for 28 cards, 31 for 52) and `launchDue()` hands each card to a free slot ~150ms before its flight, re-basing its delay onto the launch. The deal's clock starts when the slots have MOUNTED (the `[generation]` effect), not at `start()`, so a slow mount delays every departure uniformly instead of spending the first cards' delays and sending them off together; cards that are LATE after a JS stall are spaced `LATE_LAUNCH_MIN_GAP_MS` apart (on-time cards keep their scheduled time) so a hitch doesn't become a blob plus a second blob. A slot is launched imperatively (`launch(spec, order)`: shared values reset to the origin/opacity 0 *before* the React commit that shows it, so the previous landing spot never flashes) and is hidden again by React state (`job` -> null), NOT a UI-thread opacity write, so it disappears in the same commit the caller's `onCardLanded` reveals the real card (a UI write ahead of that commit would blink a card-shaped hole). A landed slot is offered for reuse only from an EFFECT after that commit (`onIdle`), never from the landing callback itself - relaunching it in its landing tick would write the reset to the UI thread ahead of the reveal. Face-down deals reuse identical backs (the slot's face element is `useMemo`'d, so a relaunch renders nothing); face-up deals re-render a face instead of mounting one. `order` becomes `zIndex` so a later card still paints above an earlier one whichever slot it lands in. Skip lands both the in-flight slots (`completeNow`) and the not-yet-launched queue; a restart mid-deal keys slots by `${generation}-${slot}` (same key-reuse guard as before). Haptics are capped at one per 40ms like the sound pool. Covered by `src/__tests__/components/dealLayer.test.tsx`; verified on device for Yukon (52), Klondike (28) and FreeCell (52).
- **Initial deals are compressed to ~1.2s** (`dealStaggerMs(count)` in `dealSpring.ts`). A 52-card deal (FreeCell, Yukon, Spider, Scorpion) used to take ~2.1s with the board locked (only Home stayed live); each game's initial-deal line now uses `step.visitOrder * dealStaggerMs(sequence.length)`, which tightens the stagger just enough to fit `DEAL_TARGET_TOTAL_MS` (floor 14ms; 28-card deals keep ~34ms so they are unchanged). Measured on Yukon: 52-card deals now land in 1.22-1.29s (was ~2.1s) with ~770-1050ms of JS lag over the deal (was ~1250 over 2.1s). Stock draws and undo flights keep `DEAL_STAGGER_MS`. The remaining fixed cost is the ~400-500ms board commit at deal start (the pool size doesn't affect it: capping the pool at 10 left the start stall unchanged).
- **Cards don't re-render when the screen does** (`PileView.tsx`). `DraggableTableauCard` is `React.memo`'d and every prop is a primitive or a stable identity: the fan position is `top`/`zIndex` numbers (not a `cardStyle` object built per render), and the press/drag callbacks handed to every card are stable wrappers that read the latest `cards`/`drag`/`onPressCard` through a ref refreshed after each render. A screen re-renders on every card landing, flight, hint and selection, and each one used to re-render every card's whole wrapper chain in every column. Don't pass an inline object/lambda into a card, and don't give `PileView` a callback that changes identity without going through `latest`. Pinned by `src/__tests__/components/pileViewMemo.test.tsx` (which needs stable shared-value/ref mocks - the repo-wide Reanimated mock returns fresh ones every render).
- **Per-card animation state is lazy or shared.** The hint pulse (a shared value, an animated-style mapper and a UI-thread animation) lives in `HintRing`, mounted only while a card is hinted - every card used to allocate it and run a cancel+timing animation at mount; the drag-start position values are per column (`startAbsX/Y`), not per card; and `PlayingCard`'s `StyleSheet`s are built once per theme/invert/radius and shared (`stylesFor`) instead of once per card instance.
- **The saved-game read starts on finger-down** (`preloadGameInProgress`, called from each Home tile's `onPressIn`), so the AsyncStorage round trip overlaps the tap and the screen's mount; any save or clear invalidates it, and it is skipped while a save is waiting out its debounce.
- **Tried and rejected: the React Compiler** (`experiments.reactCompiler` in `app.json`; the repo already lints for it). Measured with the deal metric below on Yukon's 52-card deal: 1354/1361/1744ms of JS lag per deal with it vs 1365/1409/1571ms without - no gain, so it isn't worth the risk to the gesture/animation code. The lag metric: a 25ms `setInterval` accumulating `now - last - 25` (idle floor is ~250ms per second of wall time from timer coalescing, so compare deals to each other, not to zero). With the card memoization above the same deal measured ~1320/1366/1085ms (about -13%); stubbing the ghosts' card content with a plain box measured ~880ms - so the ghosts' real card art (52 full `PlayingCard` mounts+unmounts) is roughly half of the deal's remaining excess JS, and the board commit at deal start most of the rest.
- **Considered and NOT shipped: corner-only rendering of covered cards.** A fanned card shows only its top strip once the next card overlaps it, yet renders its whole face (a covered court card ~98 SVG elements, a covered back ~23 views). A pixel-exact corner-only face exists (design verified against `CardFace`'s source: the strip is at most `faceUpFanOffset(w)` = 0.44w, the center art is disjoint from it), but it is a net LOSS on a fresh deal: a covered card whose coverer hasn't landed yet has to be drawn in full (the body shows), so each covered card mounts light, remounts full at landing, then goes light again - total deal work up ~20% (the entry commit peak drops 38-57% in FreeCell/Forty Thieves/Golf/Yukon/Scorpion), and swapping `CardFace`<->a clone remounts the frame too. Only resume/mid-game boards are net wins (-18% to -54% views). Revisit once `@tastic/cards` grows a `cornerOnly` prop on `CardFace` (a ~4-line upstream change: the swap then preserves the frame/corner row and only mounts/unmounts the center) - do NOT ship an in-app clone of its private constants.

**Known remaining costs, measured/estimated but not addressed** (each needs care because of the deal/gesture machinery documented above, and ideally a Release build on a phone to profile first): (1) the board commit at deal start / game entry is ~850-1770 native views (each card ~23-41 views); (2) every tableau card still allocates a shake shared value + animated-style mapper and a Gesture (one `Pan` per column instead of per card would be a real refactor); (3) the persisted undo stack is unbounded (still one write per pause, but the blob keeps growing and is parsed on resume); (4) every game mounts twice (a chrome-less `GameLoading` commit, then the board); (5) `@tastic/cards` evaluates ~5.4MB of art data at startup and there is no `metro.config.js` (`inlineRequires` off). Don't tap while a dialog is still closing - the tap is swallowed.

**Measuring navigation cost without editing app code paths:** serve the app twice to a Debug dev client (`expo start --dev-client` vs `expo start --dev-client --no-dev --minify`, then `xcrun simctl openurl booted "exp+solitaire-app://expo-development-client/?url=http%3A%2F%2Flocalhost%3A<port>"`), and add temporary marks plus a 50ms `setInterval` lag detector that log a "JS stall Nms" when the thread was blocked >120ms. Production bundles don't forward `console.log` to Metro, so have the marks also `fetch('http://localhost:<port>/<msg>')` to a tiny local HTTP sink that appends arrivals to a file (arrival time is only reliable at stall boundaries: sends made inside one long JS task are delivered when it ends). Terminate the app between runs so each starts with zero stale screens.

**Testing rotation in the simulator:** the simulator has no accelerometer and the custom rotation ignores OS rotation, so inject a fake `deviceMotion` into `createLockableDeviceMotion(...)` in `_layout.tsx` (`addListener` emitting `accelerationIncludingGravity: { x: -9.8, y: 0 }` for a +90deg hold, `x: 9.8` for -90deg, `y: -9.8` for portrait, `y: 9.8` for 180deg; polling a local JSON file lets you change it from a shell) - temporarily. To SEE a ghost mid-flight, temporarily multiply `DEAL_SPRING`/`SNAP_BACK_SPRING`/`springForDistance` durations by 10. `ios/` (gitignored) targets the iOS 27 SDK, whose runtime aborts any app linked against it that hasn't adopted UIScene (`NoSceneLifecycleAdoption`); for local simulator runs, patch the built executable's SDK version down (`vtool -set-build-version 7 16.4 26.0 -replace -output ...` then `codesign --force --sign -`).

**FreeCell's auto-play is two separate things, both started only by the player** (`src/games/freecell/autoPlay.ts` is the pure policy, unit-tested in `src/__tests__/games/freecell/autoPlay.test.ts`; the other foundation games - Klondike/Yukon/Canfield/Forty Thieves - still use the older "any manual foundation move arms the cascade" behavior, on purpose, since the request was FreeCell-specific).
- **The safe-card cascade** (`useAutoFoundationCascade`, engine mechanism A) starts ONLY from a TAP whose tap-to-move resolved to a foundation. `applyMove`'s `opts.viaTap` (passed by `handleCardTap`, absent from `attemptDrop`/`PileView`'s `dragConfig.onDrop`) is what tells a tap from a drag; a drag onto a foundation, a tap that lands on a column/freecell, and every silent move arm nothing. It keeps the quicker `fast` flight pace.
- **The finish** (`useAutoFinish`, engine mechanism B) starts as soon as the whole board can go up on foundation moves alone (`canAutoFinish` - every column sorted highest-to-lowest, freecell cards included), after ANY player move (a drag or a tap, to a column or a freecell, not just a foundation one), once the player's own move has landed. It is a plain async loop, not the cascade's "wait for `settled` between steps": each card leaves `FINISH_STAGGER_MS` (60ms) after the last at `sweep` pace (40-90ms flights), so flights overlap and a 20-card finish takes about a second and a half instead of a full flight-plus-measure round trip per card. The board's LAST card first waits (<=600ms) for the earlier flights to land, so the win cascade doesn't start over cards still in the air. `nextSafeCascadeStep` returns null the moment the board is finishable, so the two never both fire at one settle.
- **What suppresses it:** an undo, a resumed save and a new deal (`finish.suppress()`) - nothing finishes again until the player's next move, so undoing back onto a finishable board can't immediately re-fire the cards just taken back. Both halves honor Settings' Auto-Move to Foundation. A resumed, already-finishable board sits until the player makes any move.

**The win celebration is delayed until the winning card has flown in and landed (`useWinReveal`, `games/shared/useWinReveal.ts`) - a card must never teleport.** `won` flips in the SAME commit as the winning move, and the old code hung the celebration (foundations hiding their real cards so the bouncing win cascade can take over, fireworks, banner) straight on it. Hiding the foundations unregisters the very card the last flight is measuring to land on, so `CardRegistry.measure` returned null, the drain effect took its `!landed` branch (`flight.hide()`), and the winning card simply APPEARED while the fireworks started. Now `won` stays game state only (clock, recorded stat, cleared save, undo/hint gating) and a separate `winRevealed = useWinReveal(won, settled)` - true once `won` AND nothing is flying have held for 400ms (2.5s max wait so a win is never withheld; the optional third `maxWaitMs` param is for a screen whose winning move starts a longer sequence the reveal must wait for - Pyramid's sweep deal passes 4s) - gates only the visuals and the start of the win cascade (its `pendingWinCascadeRef` effect returns early unless `winRevealed`, deps `[state, winRevealed]`). Don't move a save/stat/clock concern onto `winRevealed`: the win must be recorded the instant it happens. **The reveal hands the real piles over to the bouncing win-cascade ghosts in ONE commit, in every game** (Scorpion's pattern, `cascadeHandoffFor`/`cascadeHandoff` in each screen): `runWinCascade` measures the always-mounted, card-sized origin containers while the real cards are still drawn (Pyramid's is one chain from the discard, after its sweep deal - see the Pyramid paragraph), then calls `winCascade.startChains(...)` and sets the hand-off state in the same async continuation (React batches them into one commit), and the real cards blank only when `winRevealed && handoff matches the current state object` (identity, so an undo or New Game un-blanks with nothing to reset; a pile whose chain didn't start, e.g. an unmeasurable origin, is never blanked). The old order - blank on `winRevealed`, THEN await `measureView`, THEN `startChains` - left every pile empty for a few frames (~140ms in a dev bundle) before the ghosts mounted. `WinCascadeLayer` also parks each chain's head ghost visible at its origin until its staggered entrance (followers peel off one at a time), and `ChainSpec.cardOrigins` (opt-in; Scorpion only) lets a fanned run keep every card's own spot into the cascade instead of collapsing onto the King's slot (`winCascadeMotion.ts`'s pure `cardXAtElapsed`/`cardYAtElapsed`/`fanOffsetScale`). Aces Up's origin is the drawn Ace's own `CardRegistry` rect (its pile container is `maxHeight` tall, not card-sized, and `ChainSpec.origin` must be card-sized for the rotation conversion) - worth a look under fake landscape. Spider refuses a second stock deal until the first has fully landed (`stockDealTokenRef`) and ignores taps/drags/deals/undo while a completed run is still assembled awaiting its sweep (`sweepPendingRef`/`claimSweep`), since the sweep cuts 13 cards off the end of that column. FreeCell also falls back to flying to the foundation slot's own card-sized container (`foundationSlotRefs`) when a landing card can't be found in `CardRegistry`, instead of hiding the ghost, and refuses a move whose grabbed card is no longer at the head of the pile (`moveHeadCard` in `freecell/rules.ts`, checked in `applyMove`): `tryMove` only knows positions, so a drop arriving after an auto-play took that very card would otherwise move whatever now sits there while the ghost shows a different card.
