# Solitaire

An ad-free, self-contained solitaire suite (Klondike, Spider, FreeCell, Pyramid, Yukon, Golf, TriPeaks, Canfield, Scorpion, Forty Thieves, Aces Up - 11 games, `src/games/`) built with Expo. Part of the `@rific`/`@tastic`/InfiniteToken app ecosystem - depends on `@rific/auto-paper`, `@rific/feedback-press`, `@rific/focus-chain`, `@rific/splash-gate`, `@rific/toaster`, plus `@tastic/profile` (+ its `@tastic/core`/`@tastic/hud` peers) for player identity (a color + short tag, shared across the fleet via an iOS App Group) - unlike the fleet's physics-driven games, there's still no board-physics or split-screen engine here, just tap/drag card-game logic. A selected player's color/tag only drives cosmetic colors (the card back, the felt and the Paper theme, `src/components/theme.ts`, see the root-felt note below) - settings stay global regardless of who's selected, but stats are kept both device-wide and per profile (`StatsState.profiles`, keyed by `Profile.id` and filled for whichever profile is active when a deal resolves, see `src/stores/gameStats.tsx`).

**Expo has changed.** Read the exact versioned docs at https://docs.expo.dev/versions/v57.0.0/ before writing any code - don't rely on general Expo knowledge, this app is on SDK 57 specifically.

## Commands

```bash
npm run lint          # expo lint .
npm run fix            # expo lint . --fix
npm test               # Jest
npm run typecheck      # tsc
npm run verify         # lint + test + typecheck
npm run doctor         # expo install --fix && expo-doctor
npm start              # Expo dev server
npm run client          # Expo dev server (dev client build)
```

Always run `npm run lint` before finishing any task. This is an app (`"private": true`, no publish scripts) - `verify` doesn't include a build step.

**Builds and OTA updates go through Jay's own CLI, `jrd ship` (`@jayrdeaton/scripts`, `~/Developer/Scripts`, npm-linked globally, so an edit there applies to every app at once):** `jrd ship build <profile>` and `jrd ship update <profile>`, both of which run `verify` first. `development` builds LOCALLY (`expo prebuild --clean` + `eas build --local`) and copies the artifact to `~/Downloads/Builds/`; every other profile (`preview`, `production`) builds in the EAS cloud. Profiles are in `eas.json`. This app's own `build`/`update` npm scripts are deliberately plain `eas build`/`eas update`, a starting point for someone without jrd (Jay, 2026-10-15); don't point them at jrd. They used to be `@rific/updater`'s `rific-updater-build`/`-update` bins, which jrd's replace (the package itself stays: `@tastic/hud`'s update dialog uses it). **iOS 27:** an app LINKED against the iOS 27 SDK aborts at launch without UIScene adoption, which SDK 57's template doesn't wire (SDK 58's does); one built with Xcode 26 runs fine on iOS 27. Cloud builds use an Xcode 26 image, and local builds use this Mac's Xcode 27 with `plugins/withSceneDelegate.js`, which adopts the UIScene life cycle on SDK 57; see "iOS 27 on SDK 57" at the end of this file.

## Tooling

Onboarded onto the shared `@infinitetoken` config packages (`eslint-config`, `jest-config`, `tsconfig`) - previously hand-rolled its own `eslint-config-expo`-based config, `jest-expo`-preset-direct config, and `expo/tsconfig.base`-extending tsconfig (the same pattern documented in [Swirlio](../Swirlio/.claude/CLAUDE.md)'s and [BoxHockey](../BoxHockey/.claude/CLAUDE.md)'s CLAUDE.md).

`npx expo install --fix` + `npm update` genuinely found real staleness here - more than any other app surveyed so far: `@expo/metro-runtime`, `@react-native-async-storage/async-storage` (a full major version, `3.1.1` → `2.2.0` - the installed version was actually *ahead* of what SDK 57 expects), `expo-linking`, `expo-router`, `react-native`, `react-native-gesture-handler` (`^3.1.0` → `~2.32.0`, also a major-version rollback), `react-native-reanimated`, `react-native-safe-area-context`, `react-native-worklets`, `@types/jest`, and `jest-expo` were all misaligned with the installed Expo SDK, in both directions. **`npm update` alone wasn't enough to reach a stable clean state - a genuine wrinkle not seen in the other 7 migrated apps.** After the first `expo install --fix` + `npm update` pass, `npm outdated` showed `Current === Wanted` for everything, but `npx expo install --check` had newly drifted on two packages `npm update` had bumped past Expo's compatible range per their own loose semver (`react-dom` `^19.2.3` → resolved `19.2.8`; `react-native-screens` `^4.26.2` → resolved `4.27.0`) - `npm update` respects a package's declared semver range, which doesn't know about Expo's own SDK-compatibility matrix. Fixed by running `expo install --fix` a second time (pins both back to their SDK-57-compatible versions); confirmed clean afterward on both fronts: `npx expo install --check` reports up to date, `npm outdated` shows `Current === Wanted` for every dependency (remaining `Latest` values are all major bumps outside declared ranges, a deliberate-upgrade decision, not routine maintenance).

**On the web target specifically, `@tastic/profile`'s `ProfilesManager` create/edit flow doesn't reliably commit via the Name field's Enter key, and its documented "commit on unmount" fallback doesn't fire either** - confirmed live: typing a name and pressing Return left the row still open/editable, and navigating away via `router.back()` (Settings → Profiles → back) didn't commit it, because React Navigation's web implementation keeps the previous screen mounted (hidden, not unmounted) across a stack pop, unlike native. Only a hard browser navigation (a real page reload) actually unmounts the screen and would trigger that fallback. This is a gap in the third-party package's web behavior, not in Solitaire's own integration code - `onCreate`/`onSave`/`onDelete` are wired exactly per the package's documented prop shape. Unconfirmed whether this also affects native (where screens genuinely unmount on pop) - worth a real device check before relying on the unmount fallback there. Worked around during verification by seeding `AsyncStorage`'s web-backing `localStorage` key (`solitaire.profiles.v1`) directly rather than fighting the picker UI.

## How-to-play guide (2026-09-24)

A first-run, replayable "How to Play" flow, built on `@tastic/hud/guide` (the light-peer subpath of `@tastic/hud`; see that package's own CLAUDE.md, "The guide subpath"). Same shape as LightCycles, Snake, AirHockey, BoxHockey and Pong. **The code word is `guide` everywhere, never "onboarding"** (the fleet's word for a round countdown).

- **Content:** `src/constants/guideSteps.tsx`: `getGuideSteps({ touch })`, three cards, pure and hook-free. `touch` is `useIsTouchPrimaryDevice()` and only swaps the verb (tap vs click). **Per-game rules are deliberately NOT here**: `RulesDialog` (`constants/gameRules.ts`, plus its shared Scoring paragraph) already covers each of the 11 games; the guide teaches the suite-wide things a first-timer can't work out alone, and every sentence has to be true in all 11 games at the default settings:
  - **Tap to Play** (Click to Play on desktop): "Tap a card for its best move. Pyramid pairs take two taps." Ten games run the game's `autoMoveHint` on a tap (each screen's `handleCardTap`, Spider's `handlePressCard`; the tableau pick is `engine/autoMove.ts`'s `pickBestTableauTarget`). Pyramid's tap only SELECTS (`handleSelectPyramid`; a tap on the partner removes the pair, a King goes on one tap), so the first sentence would be false there without the scope. **Dragging is deliberately not taught:** a drag can't make every move. The discard pile has no `DropZone` (`games/shared/DiscardCell.tsx`), so an Aces Up discard (its main move; the card still lifts because `hasLegalMove` counts discards) and a Pyramid King both snap back when dragged there (`AcesUpScreen`'s header and `handleDrop`, `PyramidScreen`'s `attemptDrop`). Making the discard a drop zone in those two screens would make a drag line true again.
  - **Lower Is Better**: "Score is moves plus seconds. The first move starts the clock." `engine/score.ts`'s `computeScore` (every game's readout, through `GameChrome`); `useGameSession`'s `registerMove` starts the clock (a stock draw counts); `statsEngine.ts` keeps the LOWER best score. The clock half is otherwise only in the Rules sheet's Scoring paragraph.
  - **Get a Hint**: "Tap the light bulb in any game to see a move you can make." `GameChrome`'s `lightbulb-on-outline` Hint button, in both layouts; `engine/hint.ts`'s `findHint` rings a legal move, or the stock when a draw is the move, and each screen's `handleHint` toasts when there is none. Home has no light bulb, so this doesn't describe what's behind the card. The info button is left out for exactly that reason: every Home tile shows it (`renderRulesButton` in `app/index.tsx`).
  - Art: `src/components/GuideArt.tsx` (`GuideCardPlay`, whose `pointer` is `'finger'` on touch and `'mouse'` on desktop, also picking the screen-reader verb; `GuideScore`; `GuideHint`, the Hint button plus a ringed, glowing seven and the eight it goes on; only the card to move is ringed, as in a game). Plain Views plus Paper Icons/Text, colored from `useAutoPaperTheme()`: no Skia/SVG, and deliberately NOT the in-game `PlayingCard`/pile components or `@tastic/cards` (the mini cards are Views). None of hud's shared art (swipe, key caps, split phone) fits a card game.
- **Copy rules (Jay, 2026-09-24):** Title Case titles; one-word buttons (hud's defaults Skip / Back / Next / Ready, no `finishLabel`); bodies of 90 characters or less; no questions, no filler, no vague nouns, no em dashes; every sentence true for everyone who can see it (all 11 games, default settings); don't describe what's already visible behind the dialog; never tell a desktop player to tap or a touch player to click. **Plus a Solitaire-only rule: every body fits in TWO lines** of DejaVu Serif Bold (the app-wide Paper font, `ThemeProvider`'s `fontFamily`) at bodyMedium 14/20 on a 264pt page (a 360dp phone; `guideSteps.test.tsx` caps bodies at 62 characters as a proxy). A third line makes the turned card too tall, see Wiring. Measure a new body against the real TTF (`node_modules/dejavu-fonts-ttf/ttf/DejaVuSerif-Bold.ttf`, e.g. with PIL's `getlength` plus 0.25 letter spacing per character), since widths vary per letter. **Considered and left out:** dragging (see Tap to Play), the info button (visible on every Home tile behind the card), tap-the-readout-to-hide-the-footer (portrait only: false in the wide layout and in a desktop window), the shake on a card with no move (in Pyramid a shake means a failed pair), hint cycling (not true when the hint is a stock draw or the only move), Undo's hold-to-repeat (never checked with a mouse on web), auto-save (it shows itself the first time you come back).
- **Wiring:** `src/components/GuideHost.tsx` (the Redux seen version + `useRotation()` passed as `rotation` + the steps -> `GuideProvider`), mounted in `_layout.tsx` around `<ThemedStack />` inside `OrientationBridge`, so inside PersistGate, the auto-paper/Paper provider and the orientation provider. **The card is the one dialog here that is NOT under an in-frame Portal.Host:** `GuideProvider` renders it beside its children, so its Paper `Portal` lands in the nearest host above `GuideHost`, which is `FeedbackPressProvider`'s own `Portal.Host` (`FeedbackBridge` passes `paper={RNPaper}`), outside every rotated frame. It is handed the frame's live rotation as a transform instead of `rotation={0}` (the same `useRotation()` Home's `RotatedFrame` turns by, so it sits at the angle Home's Settings dialog visually does). Home (`app/index.tsx`'s `Home`) calls `useAutoShowGuide(!resumeGame)` BEFORE the cold-launch resume `<Redirect>` (hooks stay unconditional): held back whenever the launch is about to drop into a saved game, so the guide can never open over a live deal. Settings row: `SettingsDialog`'s `showHowToPlay` (default false) -> `BaseSettingsDialog`'s `onShowHowToPlay`; turned on ONLY at Home's call site, **never in `GameChrome`**: the score counts elapsed seconds, so a guide opened mid-deal would cost the player score.
- **Turned card height:** the fleet's rotation is fake (the OS window stays portrait), so a quarter-turned card's layout HEIGHT has to fit the window's short edge. hud handles that for every game now: `getGuideCardSize` swaps the axes for +/-90, widens the card, caps its height, shrinks the art under 480pt, and each page scrolls if it still doesn't fit (found in this app's review, fixed upstream 2026-09-24). Keeping every body to two lines means that scroll is never needed at the default text size. Not yet checked on a real device held sideways.
- **Persistence:** `src/redux/guideSlice.ts` (a `createGuideSlice` binding) mounted as `guide` in `store.ts` (its own key: Reset Stats never touches it). `GUIDE_VERSION` (`src/constants/guide.ts`) is what an existing player is stamped with. Players who already have a root store (otaVersion 4+, 464e3e1) are grandfathered by the slice itself. **Players last on otaVersion 3 (25532f0, 2026-09-12) or earlier have NO root store** (it arrived in 6dbe6e5), so `store.ts`'s `persistConfig.migrate` is `createReturningPlayerMigrate(AsyncStorage, LEGACY_STORAGE_KEYS)`: the 20 literal keys 25532f0 really wrote (the 11 `solitaire.game-in-progress.v1.<game>` saves, `solitaire.stats`/`.achievements` via `@tastic/achievements` 0.1.1's namespace, settings, theme, last-active-game, profiles, guest color, sound, vibrate; per-key source in guideSlice.ts), read from that commit's source, not today's constants. otaVersion 1 (5f3078f) and 2 (f065784) wrote the same set. `solitaire.stats.v1.<gameId>` is NOT listed: those builds only ever read it. **Early-write rule:** nothing may write one of those keys before PersistGate opens, or a fresh install is taken for a returning player. Today `solitaire.settings.v1`, `solitaire.theme-settings.v1` and `solitaire.last-active-game.v1` belong to providers mounted OUTSIDE PersistGate (`SettingsProvider`, auto-paper's `ThemeProvider`, `LastActiveGameProvider`), but none writes on mount (auto-paper's `onChange` skips the first render, see `@rific/core`'s `createSettingsContext`; the other two write only from their setters) and every setter call at boot (`ProfileThemeSync`, `OrientationBridge`, the game screens) comes from inside PersistGate. Only finish/skip writes; a replay never does. Bump `GUIDE_VERSION` only for a real controls/scoring change: every player sees it again.
- **Not built:** any in-game entry point (deliberate, see Wiring), and per-game first-visit tips (RulesDialog is the per-game layer).
- **Tested:** `guideSteps.test.tsx` (three illustrated cards per platform, Title Case, bodies <= 90 characters and <= 62 as the two-line proxy, no questions or dashes, touch vs desktop differ only by the verb, the Pyramid scope, no drag promise, the exact score copy, the hint card naming the light bulb and not the info button, each card's art component and pointer, the art's screen-reader labels, the score picture matching `computeScore`), `guideSlice.test.ts` (this app's binding; `LEGACY_STORAGE_KEYS` namespaced, unique, all 11 saved-deal keys, no `stats.v1` keys; the migrate over each key gives `GUIDE_VERSION` and no keys or a failed read gives 0, also end to end through real redux-persist, including a fresh install's second launch after the theme key was written; the real `persistConfig` has the migrate, imported under fake timers because store.ts's persistStore leaves redux-persist's 5s failsafe timer), `components/homeGuide.test.tsx` (the redirect guard), `components/settingsHowToPlay.test.tsx` (the prop -> row), `components/gameChromeHowToPlay.test.tsx` (never in a game). **Not verified live:** nothing here was run on a simulator, device or web build: the card's look (mini-card ink in dark mode, art sizes on a 320pt phone), the transform-rotated card under a fake landscape hold (the 358pt height is an estimate from hud's styles and the real font's widths, not a measurement; check it on a 375pt iOS simulator and a 360dp Android emulator held sideways, at the default and a larger text size), the Settings row, and the auto-show on a genuinely fresh install.
- **Packages:** the guide ships in the published `@tastic/hud` 0.13.0 (`./guide`, with `createReturningPlayerMigrate`). Solitaire has no yalc links any more (2026-09-25: `.yalc/` and `yalc.lock` removed, `@tastic/cards`/`hud`/`profile` installed from npm). ## Testing

- Framework: Jest (`@infinitetoken/jest-config/expo`, `jest-expo` preset)
- Tests live in `src/__tests__/`, mirroring the source subfolder structure for the games (`games/freecell`, `games/klondike`, `games/pyramid`, `games/spider`) plus a top-level `engine.test.ts`
- Native/Expo module mocks live in `src/__mocks__/`, one file per module (plus one scoped subpath), picked up automatically (no `jest.mock()` call needed) - see Tooling above
- Most suites are pure game-logic (`engine`, each game's `rules.ts`), but component-rendering tests exist too (`src/__tests__/components/`: e.g. `homeScreen`, `rotatedScreen`, `achievementsProfilesScreens`, `dealLayer`, `dragGhostLayer`, the per-game `*Screen*` suites). **The deal animation's destination measurements raced the React commit they depended on, and silently dropped ~90% of the board when it lost.** `CardRegistry.measure(cardId)` (`components/dragdrop/CardRegistry.ts`) only resolves once that card's own registration `useEffect` has run - but the deal's initial implementation called `measure()` for all 28 destination cards *synchronously, right after* `setState(newTableau)`, before React had even committed that render, let alone run the new cards' registration effects. Confirmed live: this raced the *previous* deal's still-registered (but about-to-be-replaced) cards against the *new* deal's not-yet-registered ones, and mostly matched neither - 25 of 28 destinations came back `null` on one measured run, silently excluding those cards from `entries` and leaving them hidden forever (a card whose destination is `null` never gets added to `deal.start()`'s entries, so it never fires `onCardLanded`, so its id never leaves `dealHiddenIds`). The fix: never call `CardRegistry.measure()` synchronously after the `setState` that mounts the new cards. Instead, stash a "deal is pending" token and do the actual measurement from a `useEffect` keyed on `[state]` - React fires effects bottom-up per commit (children's before parents'), so by the time a *parent* component's `[state]`-effect runs, every child `PileView`/`DraggableTableauCard` for that same commit has already run its own registration effect. See `KlondikeScreen.tsx`'s `pendingDealTokenRef` for the pattern; `PyramidScreen.tsx`'s equivalent doesn't need it for the *destination* side, since its destinations are computed analytically (`cardPosition()`) rather than via `CardRegistry.measure()` - it only measures two container refs (the stock pile, the triangle container), which aren't subject to this per-card mount race. It still needs the same `[state]`-deferral for the *origin* side, though: those two container refs are themselves behind Pyramid's `if (!state) return <GameLoading />` branch, so on the very first mount they aren't attached yet at the moment `startNewGame` calls `setState` - calling `runDeal` synchronously right after that (as it originally did) measured two still-null refs and silently skipped the deal (cards just appeared with no animation, every time you navigated to Pyramid fresh). Fixed by giving Pyramid its own `pendingDealTokenRef` + `[state]`-effect, same shape as Klondike/FreeCell/Spider - confirmed all four now defer their initial `runDeal` this way.

**A second, unrelated bug found in the same session: reused React keys across separate deals silently stalled a handful of cards forever.** All 52 cards' ids are shuffle-independent (`${suit}-${rank}-${deckIndex}`, see `engine/deck.ts`) - a fresh deal reuses the exact same ids as the one before it, just redistributed. If `deal.start()` is ever called again while a previous deal's ghosts are still mounted (shouldn't happen in normal play, since the skip-overlay covers the "New Game" button during a deal too, but is easy to trigger via rapid/automated interaction), React reconciles by id and reuses the *same* `DealGhostCard` instance for a repeated id rather than unmounting and remounting it - meaning its `useSharedValue` position and its "already notified" guard ref never reset, since both only initialize on a genuine first mount. Fixed by folding a monotonic generation counter into each ghost's React `key` (`DealLayer.tsx`'s `generation`), forcing a real unmount+mount - and therefore a full state reset - on every `deal.start()` call regardless of id overlap with the deal before it. The same generation is also stamped on every slot (`deal`) and checked in every callback (`generationRef`, bumped synchronously in `start()`, which also `cancel()`s the old slots), because the old slots stay mounted - timers live - until the commit AFTER `start()`: a timer firing in that gap used to report a stale card into the new deal.

**Pyramid's pairing/King removal lands cards in a real discard pile (`PyramidState.discard`, `rules.ts`) instead of just deleting them.** A solo King flies as a single card via the shared `ghost` (`DragGhostLayer`/`useDragGhost`), same as every other single-card flight in this app. A pair instead flies as **two cards travelling independently at the same time**, each from its own real board position straight to the discard pile (`PyramidScreen.tsx`'s `startPairFlight`/`PairFlightGhosts`/`FlyingPairCard`) - not merged into one stack, and not one card visiting the other before either moves. The single shared `ghost` can only ever animate one origin/delta for its whole group (see `DragGhostLayer.tsx`), so two cards converging from different starting points needed their own small overlay instead - the same "N independent simultaneous ghosts" idiom `DealLayer`/`WinCascadeLayer` already use for the same reason (see `DealLayer.tsx`'s doc comment), just with each ghost getting its own independent origin/destination instead of a shared one. Each card's flight is its own `withSpring` at `FLIGHT_SPRING`, the one time every flight in this app takes, so the two cards of a pair leave together and land together. For a drag-completed pair, "first" is still sitting mid-drag in the shared `ghost` at drop time - its live position is read directly off `ghost.originX/Y.value + dx/dy.value` before handing off to its own independent flight and retiring that ghost (`ghost.hide()`). Two earlier shapes of this flight were tried and rejected first: originally "first" visibly flew onto "second" before the (already-merged) pair continued on to discard, as two distinct legs; replacing that with a single flight of the two cards already merged into one stack (skipping the first leg, but still one shared ghost) was also rejected - both read as one object moving, when the actual ask was always two cards animating independently to the same destination at the same time. The discard pile itself (`PyramidScreen.tsx`'s `DiscardCell`) measures its position like `stockViewRef`/`triangleViewRef` (a plain view ref, `measureView()`) rather than `FoundationCell`'s per-card `CardRegistry` registration - there's only ever one discard pile, not a slot whose occupant identity keeps changing. **Undoing a pairing/King removal now animates too, flying each card independently from the discard pile back to its own original spot** (`PyramidScreen.tsx`'s `undoRemoval`, `RemovedCardRef`) - the mirror image of the forward removal flight: one shared origin (the discard pile, which doesn't move) fanning out to each card's own destination, reusing the same `PairFlightCardSpec`/`PairFlightGhosts`/`startPairFlight` machinery (generalized so each card's spec now carries its own `to` as well as its own `from` - the forward flight shares one `to` across cards with independent `from`s, the undo flight shares one `from` with independent `to`s). `UndoEntry` gained a `removedCards: RemovedCardRef[] | null` field (the PileRef each removed card came from) alongside the pre-existing `move: MoveInfo | null` for stock draws - the two are mutually exclusive. **Every undo resolves ALL its endpoints BEFORE it commits, and mounts its ghosts in the same synchronous stretch as the revert** - a pyramid-cell destination is pure math (`cardPosition` + the measured `triangleViewRef`), a waste-bound card's is the always-mounted waste container (`wasteViewRef`; there is one waste slot, so it is the same place the card's own registration would say), and the discard/stock are plain containers too. The old shape (commit the revert, then a `[state]`-effect measured the destinations and only then started the flight) left the restored cards visible NOWHERE for a frame or two (the discard already showing its older top, the cards hidden, no ghost yet) before the ghosts popped in. Undo of a draw and of a recycle measure both endpoints first and do `ghost.show` + `beginFlying` + `setStockHidden(true)` + `commitState` + `flyTo` in one stretch; undoing a draw also freezes the stock slot (`stockHidden`) until the returning ghost lands, instead of showing the returned card at once. The restored card(s) have to be hidden (`pyramidHiddenIds` for a pyramid destination, reusing `flying`/`wasteHiddenCount` for a waste one) in that same commit - React batches same-tick `setState` calls - to avoid a frame where the restored card flashes fully visible before its ghost covers it (same reasoning `startNewGame`'s `setPyramidHiddenIds(dealtIds)` already relies on for the initial deal). A waste-bound card's `flying` entry ends with ITS card's landing (the pair ledger's `flying.cardId`), not with the whole pair, so a landed Ace is not hidden again while the Queen is still on its way. `dealHiddenIds`/`isDealHidden` were renamed to `pyramidHiddenIds`/`isHidden` to reflect that the same hidden-until-landed mechanism now covers two different reasons a pyramid cell's card might be flying in, not just the initial deal. A card whose destination cannot be measured (a rare edge case) simply has no ghost and is not hidden, rather than left stuck invisible forever. **Fast play:** pair flights are independent - `pairFlights` is a list with a per-flight ledger keyed by gen (a landing settles only its own flight; a single slot let the next pair replace the last one, so its ghosts vanished mid-air and its `activeFlightCount` claim never settled), and the discard shows the topmost card not in `discardInAir` under the ghosts (`DiscardCell`'s additive `settledCard`, the `FoundationCell` idiom). Every action claims its flight synchronously (`claimFlight`, generation-stamped) and **re-validates against `stateRef.current` after its measurement awaits** (`replayMove`, then one synchronous `commitRemoval`) - committing the pre-await `result` overwrote whatever committed meanwhile and let a double-tapped King be removed twice. Pinned by `pyramidScreenQuickPlay.test.tsx`, whose mocked measurements have a latency so taps really overlap. **Overlapping draws and the waste:** the waste slot's frozen copy of the pre-flight top goes stale once draw flights overlap (each landed ghost vanished onto the card from before the whole stream), so `wasteInAir` (the waste's `discardInAir`) tracks the drawn cards still flying and the screen passes `StockWaste` the additive `settledWasteTop` (the topmost waste card not in it; omitted - `undefined` - keeps the frozen copy, which every other game and every non-draw flight still uses). **A card is never acted on while its own draw ghost is airborne:** a tap/drop on it (or a pair completed with it) waits - `whenLanded`, re-checked at every landing, bounded by `DEFER_MAX_WAIT_MS` - so the card visibly arrives, THEN flies on (measuring the hidden real card would start a second ghost from a slot the drawn card has not reached, shown twice); a draw waits out a recycle's group ghost still flying into the frozen-empty stock, and a recycle waits out draw ghosts still landing (it would pick the airborne card up twice) - plain draws still overlap freely. The check comes AFTER the measurement awaits and does not yield when nothing is in the way, so an earlier tap's commit is never interleaved with a later one's. **Every such wait is a LOOP, not a single check** (`while (!gate() && budget.left() > 0) await whenLanded(gate, budget.left())`, inline at all three call sites - `attemptMove`, `attemptDrop`, `handleDrawStock`): being resumed is not proof the gate still holds, because a landing resolves EVERY waiter whose predicate held at that instant and their continuations then run one after another - the first (a recycle) re-freezes the stock for the next, which used to draw from the freshly recycled stock while the recycle's group ghost was still flying into it (stock [5], waste [2, 3], three quick stock taps). The loop must stay inline (a helper looping inside an async function hands its answer back across a microtask boundary in which a sibling can change it again), and its deadline is ONE budget per action (`startDeferBudget`), not a fresh `DEFER_MAX_WAIT_MS` per resume. **`commitRemoval` drops a selection that names a card it removes** (`setSelected((sel) => removed.some(refsEqual) ? null : sel)`): an action clears the selection when it starts and may then park in the wait above, and a tap in that window selects the waste as `{waste, 0}` - "whatever is on top" - which, once the deferred pair had removed that card, pointed at the card that was UNDER it (highlighted, and paired by the next tap: a move the player never chose). A selection of an unrelated card made during the wait is kept. **New Game/restore retires every shared-ghost flight still in the air** (`trackFlight`/`hideAirborneFlights`: a King's, draws' - queued ones included -, recycles', undos'), after bumping `dealTokenRef` so their completions are generation-guarded; dropping `pendingFlightRef` alone left queued ghosts mounted for good.

**Pyramid's win is a SWEEP DEAL, then one chain from one pile.** rules.ts still folds whatever is left in the stock/waste into the discard ON the winning move (a won game's discard is all 52 cards, waste bottom-to-top then stock bottom-to-top - the order everything else depends on), so `won` stays game state exactly as before (clock, stat, save, recorded the instant it happens). But nothing flew for that fold, so the leftover cards now fly: the winning removal's `commitRemoval` calls `beginWinSweep`, which claims a flight (`claimFlight`, while the removal's own claim is still held, so `settled` never blips true) and marks every leftover as in the air on the discard (`discardInAir`, so the pile's top is always a card that really landed). Once nothing but the sweep's claim is outstanding (`activeFlightCount` down to 1 - the last removal has landed), `runSweep` deals the leftovers through the existing deal machinery (`useDealAnimator`: same stagger `dealStaggerMs`, spring, throttled sound/haptics and skip-tap - no flight layer of its own), one card per swept card from its own pile (the waste slot for the waste's, the stock slot for the stock's; a pile that cannot be measured deals from the other one, only with no origin at all does a card simply land) to the discard, in the discard array's order, face-up (the deal layer cannot turn a card over in flight, and every swept card is face-up already). The board keeps showing the pre-fold piles (`winHoldView`, kept in `sweepUi.view`, keyed to the won state's identity) and empties each pile when its last card takes off - driven by the deal layer's own take-off signal, `DealAnimator.start`'s additive optional `onCardDealt(cardId)` (once per card, at the instant its ghost is drawn over the spot it leaves; reported for every not-yet-taken-off card when a skip lands the deal at once; silenced by a cancel/restart exactly like `onCardLanded`), `SWEEP_PILE_BLANK_LAG_MS` after the pile's LAST card, on the run's timers so `cancelSweep` clears it. A timer armed from the scheduled delays right before `deal.start` (what this used to be) runs on the wrong clock: the deal's own clock only starts once its ghost pool has rendered and mounted (several frames on a phone) and a card's real take-off is that clock + its re-based delay + the render of its launch, so the timer ran ahead and the pile sat empty until the ghost popped in (worst for a pile whose last card leaves at delay 0). Pinned by `pyramidScreenWin.test.tsx`'s mount-latency cases and `dealLayer.test.tsx`'s `onCardDealt` block. The deal's `onAllLanded` (or a skip, which lands everything at once) settles the claim exactly once; a New Game mid-sweep, or the reveal's fallback timer, ends it via `cancelSweep` (an empty `deal.start([])` is the deal layer's only cancel). Timeline: last removal lands -> sweep (up to ~1.1s for 24 cards) -> 400ms hold -> reveal, so `useWinReveal` gained an additive `maxWaitMs` and Pyramid passes 4s (nominal ~1.9s worst case against the default 2.5s was too thin for a phone's JS stalls). The reveal then launches ONE chain of all 52 discard cards (head = the card on top) from the discard container; the discard blanks only in the commit its ghosts mount (`cascadeHandoff`, now just the discard). **A 52-card chain at the usual 42ms per card trails its head by ~2.1s - more than two bounce half-periods - and splits into a wave** (the ~28-card discard chain it replaced already did), so `ChainSpec` gained an additive `segmentDelayMs` and Pyramid passes `chainSegmentDelayMs(count)` (`winCascadeMotion.ts`: the usual delay, tightened so the whole head-to-tail span stays within `CHAIN_MAX_SPAN_MS` = 500ms, ~9.8ms per card at 52); `isGhostVisible` takes the chain's own delay. Pinned by `pyramidScreenWin.test.tsx` (a deal harness that follows the real deal's timeline) and `winCascadeMotion.test.ts` (a 52-card chain bends at most once with the cap, twice without).

**Landscape rotation is a fake: the OS stays portrait-locked and the whole app is visually rotated** (`@tastic/core`'s `OrientationProvider` reads the accelerometer; `useRotation()` gives 0/90/-90/180). Every screen draws inside a rotated frame: each game via `withGameProviders` (`@tastic/core`'s `FakeLandscapeView`), and Home, Achievements and Profiles via `RotatedScreen` (see the `RotatedScreen.tsx` bullet below); the root layout's toaster and update dialog sit in their own frame laid over the whole `Stack` (`_layout.tsx`'s `RootOverlays`). Nothing in the app is left in physical portrait. Several things here exist only because of how that goes wrong:
- **Every rotated frame keeps ONE identical element tree at every angle.** `FakeLandscapeView` through 0.8.0 returned a different tree at 0deg vs +/-90deg (`<View>` vs `<View><View>`), so React unmounted and remounted the WHOLE game screen - every card, all providers, and Inner's state (undo stack, hints) - on every rotation. Measured in the simulator: ~700-800ms of JS per rotation versus ~90-250ms for the update it should be. This app carried a local stand-in (`components/RotatedGameView.tsx`) until `@tastic/core` fixed it upstream (identical tree since 0.9.x, `passThrough`/`rotation` props since 0.12.0), and swapped back to `FakeLandscapeView` on 2026-10-08. Don't reintroduce a per-angle branch in the tree. At 0deg/180deg `FakeLandscapeView` SPLITS the caller's style: the outer View gets the keys that place/size it in its parent (position/insets, flex/flexGrow/flexShrink/flexBasis, width/height/min/max, aspectRatio, margins, alignSelf, display, zIndex, transform/transformOrigin; the exact list is `OUTER_STYLE_KEYS` in @tastic/core's FakeLandscapeView.tsx), the inner one gets the rest (flexDirection/flexWrap included; `direction` goes to both) plus `flexGrow/flexShrink: 1, flexBasis: 'auto'` to fill the outer. Every call site here (`withGameProviders`, and hud's `RotatedFrame` for `RotatedScreen` and `RootOverlays`) passes just `{ flex: 1 }`, which lays out exactly as the old stand-in did (its outer was always `flex: 1`, its inner the caller's style); a new call site with padding, a background or an absolute style should check which View each key lands on.
- **The "wide" layout (`components/gameLayout.ts`) is what makes landscape playable.** Any window whose ROTATED footprint is landscape (`isWide`: a phone held sideways, an iPad, a desktop browser) drops the vertical chrome bands (portrait reserves 56pt top + 88pt bottom, which would eat 144 of a ~402pt-tall landscape screen): `GameChrome` puts the footer controls (Undo/New Game/Hint/Rules) in a column in the RIGHT side gutter (where the thumb is) and the moves/score/time readout in the LEFT one, hides the title (rules stay reachable from the info button, which only the wide column has), and the corner buttons stay put. Hiding the footer is portrait-only (there the footer floats over the board; in landscape it sits in a gutter and hiding it would give the board nothing back). The two gutters are PER-SIDE (`leftGutter`/`rightGutter`, each = its chrome column + its OWN safe-area inset): sizing both from the larger inset left ~44pt of dead space between the footer buttons and the board on the small-inset side of a phone held sideways. `useGameLayout()` gives every screen its `contentWidth` (net of the gutters) and `availableHeight`. Portrait is byte-for-byte unchanged.

**Going Home / entering a game is fast because of four invariants - don't undo them.** It used to take seconds (5s then 7.6s on the 1st and 2nd Home tap in a dev bundle, and growing by ~2.5s every round trip; 2.7s then 4.1s even with a production JS bundle), and this file used to call that "pre-existing, wait it out". It was not: it was algorithmic (the production-JS figures are roughly half the dev ones, so most of it is real work rather than dev-mode overhead; the native side was still a Debug build, so a Release build on a phone remains the true check). Measured with the Simulator (production JS = `expo start --dev-client --no-dev --minify`, which isolates React dev-mode overhead from the real cost) after these fixes: Home tap ~20ms with no JS stall (was 2.7-4.1s), Home's first mount ~140ms (was 1.3-1.5s), game entry 0.2-0.5s of JS.
- **Home is `router.dismissTo('/')`, never `router.replace('/')`** (`GameChrome.tsx`). `replace` mounted a brand-new Home on top of the one already beneath the game, so every round trip leaked one more live Home (each a full menu); `dismissTo` pops back to the existing Home and only falls back to replace semantics when nothing is beneath (a deep link or the cold-launch resume). `back()` errors in that no-history case and `dismissAll()` returns nothing for a single-route stack, which is why `replace` had been picked in the first place.
- **`lastActiveGame` is not React state** (`stores/lastActiveGame.tsx`). Only Home ever read it, as a one-shot cold-launch resume; exposing it as state made every set/clear (each game mount, each Home tap) re-render every consumer and made each Home in the stack swap its whole menu for a `<Redirect>` and rebuild it, with the one-frame preview deferral already defeated (its `previewsRevealed` state survives the swap). The provider value is now stable for its lifetime and Home reads `consumeResumeGame()` once via `useState(consumeResumeGame)`. Any set/clear also drops a pending resume, so a deep link straight into a game can't later bounce back into a stale one. Covered by `src/__tests__/stores/lastActiveGame.test.tsx`.
- **Home's tiles are one pre-rendered face layer plus one small `Svg` of backs each, not real cards** (`components/GamePreview.tsx`). The menu used to mount ~374 full `@tastic/cards` CardFace/CardBack trees drawn ~7x10pt - ~12k native views (every react-native-svg element is a real, never-flattened native view; court cards alone are ~200KB of path text each). Now each tile's face-up cards are ONE transparent `Image` (`previewFaceBitmaps.ts` + `assets/previewFaces/`, 11 games x 4 card styles x 2 inks, 1.3MB, rendered by the real CardFace by the same `scripts/generate-card-face-bitmaps.mjs` as the card faces - regenerate when a `previewLayout.ts` changes too), and the face-down cards stay live SVG under it, a solid back in the profile's `cardBack` colour with a face-coloured frame (a tint can't recolour a baked back without flattening its frame). Column layouts merge every back into one `Path` of *visible strips* (`components/previewGeometry.ts`, pure and unit-tested); Pyramid/TriPeaks draw a `Rect` per back. That only works while no layout paints a back ABOVE a face - the generator throws if one ever does. The layout helpers live in `previewCanvas.ts` (dependency-free so the generator can bundle them; `GamePreview` re-exports them). `src/__tests__/components/gamePreview.test.tsx` fails if the per-card art comes back.
- **Nothing ticks state at `GameChrome` level.** The once-a-second clock lives in `ElapsedClock` (`GameChrome.tsx`), so only the moves/score/time readout re-renders per second; the whole chrome used to, at ~140ms of JS per tick (~14% of the thread while dragging cards). Likewise `HeroCards` cancels its forever-running wave while Home is blurred (`useIsFocused`), since Home now stays mounted under every game.
- **The hero fan's idle wave is ONE clock** (`components/heroFan.ts`: `heroBumpAt` maps one shared `withRepeat` clock to each card's bump; `HeroCards` owns the clock and its focus/AppState restarts). **Auto-play only ever follows the player's own play of a card to a foundation - in every game, a tap or a drag** (Jay, 2026-10-11: "Auto play should ONLY be instigated by the user playing a card to the foundation ... then if there are other available ones to be played THATS when auto play takes over"; and 2026-10-09: anything else "is robbing the player of their discovery"). The cascade takes ONE call for every non-silent player move, `afterPlayerMove(to)` (each screen's `applyMove`): a foundation destination arms it, ANY other destination stops a cascade still running from the player's last play (so a card that move uncovers is theirs), and a player's draw/recycle, an undo, New Game and a restore call `disarm()`. The solved-board finish follows the same rule (next paragraph). **An arm never outlives its cascade:** `useAutoFoundationCascade` disarms on every way out of its loop (ran dry, Auto-Move off, an undo, a 3s landing wait that ran out, misses) and drops an arm its effect can't start at once; `useAutoFinish` drops a move's permission when its loop ends or it can't follow (Auto-Move off, an undo), and keeps it only while the board isn't solved yet (a cascade a foundation play set off may still make it so). Before this, a left-over arm (Auto-Move toggled off and on, a held Undo released early, a timed-out wait) restarted auto-play on the player's next unrelated move. **A card already being measured when the cascade ends doesn't commit either:** every fire function re-checks `cascade.isArmed()` after its measurement await (FreeCell's `firePlay` takes the calling automation's check - the finish passes `finish.isAllowed()`), and the cascade's own stock draws (`handleDrawStock` with `opts.sweep`) bail after their awaits if it was disarmed or the board moved on. Without it, an auto-played card mid-measurement when the player tapped the stock went up after the draw, and the draw's stale result then undid it on the board (pinned by Klondike's `an auto-played card still being measured when the player taps the stock...`). **The PLAYER's own draws never commit over a newer board either (2026-10-12):** Klondike's draw-1/recycle, Canfield's single-card draw and Forty Thieves' draw used to work out `drawStock(current)` before their measurement await and commit it after, so a second stock tap inside one measurement drew the SAME card again (two moves, two undo entries for one card) and a tap-to-move that committed meanwhile was undone in state while its ghost flew on. Each `handleDrawStock` now measures first (Klondike both the stock and the waste, since the re-read draw may turn out to be a recycle; Canfield/Forty Thieves the stock), then reads `stateRef.current`, recomputes `drawStock` and commits it - with its undo entry holding that board and `session.registerMove()` - in one synchronous stretch, branching on what the re-read draw really is (a draw, a recycle, a fan when a recycle ahead of it refilled the stock, or nothing - Forty Thieves' stock ran out). Pyramid's `handleDrawStock` is the model. What stays at the tap, before the await: `cascade.disarm()` and the `startFlights(1)` claim. A New Game or restore mid-measurement (`dealTokenRef` moved on) drops the draw without settling, since `resetFlightConcurrency` already dropped its claim. Draw-3 fans (and Canfield's recycle, which doesn't fly) have nothing to measure first and still commit at the tap. Pinned by the `the player's draw is worked out from the board as it is once its measurement is back` describes in `klondikeScreenWin`/`canfieldScreenWin`/`fortyThievesScreenWin` (their `mockMeasureViewMs` delays every `measureView`; all ten cases fail on the old code). **What went (2026-10-11):** `armFromAceEvent` - an ace a column move turned over (Klondike, Yukon) or a Canfield foundation-starter the reserve turned over flew straight up; FreeCell's tap-only cascade (`viaTap`/`armsSafeCascade`: a drag to a foundation now arms it too) and its finish after ANY move (`allowsFinish`; brought back for every auto-play game on 2026-10-12, then dropped again on 2026-10-14, see the next paragraph); and Klondike's/Forty Thieves' New Game and restore never disarmed, so a cascade still running carried on into the new deal (a face-up Ace there flew up). `detectRevealedCard` and Canfield's `isFoundationStarterCard` existed only for the reveal trigger and are deleted. **Still auto-played, deliberately:** whatever a foundation play (or its cascade's own moves) uncovers, if safe - an ace turned over UNDER the card the player sent up goes next; and the end-game finish through the stock (Klondike/Canfield/Forty Thieves' `isFullyAutoCompletableWithDraws`, which reads face-down and stock cards to decide) - Jay chose to keep it (2026-10-11). Spider's completed-run removal and Pyramid's win sweep are rules, not auto-play, and were left alone. **Known edge, not fixed:** a cascade can take a card the player has just picked up to drag (nothing tells it which card is in hand); the drop is then refused by the head-card check below. Pinned by `useAutoFoundationCascade.test.tsx`/`useAutoFinish.test.tsx` (rule + no-lingering-arm cases), `klondikeScreenWin.test.tsx`'s `auto-play only ever follows the player's own play of a card to a foundation` (drawn ace, column-move ace, waste reveal, a column move stopping a running cascade, New Game mid-cascade - each fails on the old code), the same-named describes in `yukonScreenWin`/`canfieldScreenWin`, and FreeCell's screen tests. A new game with auto-play must route every player move through `afterPlayerMove` and disarm on New Game/restore.

**A SOLVED board finishes faster than ordinary auto-play, but only after the player's foundation play, and its pace ramps up** (Jay, 2026-10-12, asked for it to start after ANY move; 2026-10-14 changed his mind: "I dont want it to start automatically, I want it to also wait for user interaction to play a card to the foundation, and I want the speed to ramp up, instead of just immediately flying in to the foundation"). `useAutoFinish` (FreeCell, Klondike, Yukon, Canfield, Forty Thieves):
- **Solved** (each game's `canAutoFinish`): not already won (`isFullyAutoCompletable` is TRUE on a won board), nothing hidden (no face-down card anywhere; the stock, waste and Canfield's reserve empty), and every remaining card clears by foundation moves alone (the NON-draw `isFullyAutoCompletable`; Forty Thieves' own, since its 8 foundations are not one per suit). FreeCell hides nothing, so its `canAutoFinish` is just every column sorted. The hidden-card checks are the point: the draws-aware finish through the stock reads face-down and stock cards, and a plain column move setting it off would give the stock order away. That one still needs a foundation play, unchanged.
- **Trigger:** the player's play of a card TO a foundation, tap or drag, that leaves the board solved (`finish.afterPlayerMove(to)` next to `cascade.afterPlayerMove(to)`: allowed only when `to` is a foundation), or the cascade that play set off, the moment it makes the board solved (the play's permission is kept while the board isn't solved yet). A move to any other pile (a column, a freecell, a card taken back off a foundation) never starts it and stops one still running, like the cascade. Never an undo, a resume or New Game (`finish.suppress()` next to every `cascade.disarm()` there; in `startNewGame` itself, since the win banner calls it directly): undoing a card off a solved board leaves it solved, and it would fly straight back up. The player's next foundation play starts it again. Honors Auto-Move to Foundation.
- **Hand-off:** every game's cascade `computeNextStep` (FreeCell's `nextSafeCascadeStep`) returns null once the board is solved, so the cascade ends and the finish takes over at its own pace; otherwise both loops fight over the same cards (misses, and three misses end a loop). A draws-aware sweep through the stock switches to the finish pace the moment it empties the stock and waste.
- **Pace ramps up:** `finishGapMs(i)` (dragSpring.ts) is the gap in front of the finish's i-th card: `FINISH_RAMP_START_MS` (= `AUTO_PLAY_STAGGER_MS`, 96ms, so a cascade handing over to the finish doesn't slow down) for the first, then each gap keeps `FINISH_RAMP_FACTOR` (0.85) of what is left above `FINISH_STAGGER_MS` (`scaledMs(30)` = 48ms, the top speed): 96, 89, 83, 77, 73 ... ~59 by the 10th card, ~50 by the 20th. A miss doesn't advance the ramp. Those three constants are the knobs. Flights unchanged (`FLIGHT_SPRING`, so cards to one foundation still land in order). The gap runs on a FIXED clock: each card leaves its gap after the card before it LEFT, not after that card's measurement and commit (the old loop slept a full gap after each commit, so the real gap was 96ms plus that overhead). A card slower to measure than the gap is followed at once. 48 is just above `useCascadeFeedback`'s 45ms floor, so a step whose measurement comes back quicker than the one before can occasionally lose its tick. The hook owns the wait for a card whose own pile is still landing (`isLanding`, bounded by `FINISH_LANDING_WAIT_MS`, now in `useAutoFinish.ts`; a wait that runs out is a miss). Every screen's `firePlay` takes a third `stillWanted` check (default `cascade.isArmed()`; the finish passes `isAllowed`).
- **The clock is NOT stopped when the board is solved** (Jay, 2026-10-12): it runs until the last card commits, as before. A 52-card FreeCell finish is roughly 2.8s of take-offs (a flat 48ms gap was 2.5s; ordinary auto-play's 96ms would be 5s).
- Pinned by `useAutoFinish.test.tsx` (foundation-only trigger, the ramp, fixed clock, landing wait) and each game's screen tests (a column move never starts it, the next foundation play does, the ramped gaps, no double fire, hidden-card and undo/resume/New Game guards).

**FreeCell's auto-play is two separate things** (`src/games/freecell/autoPlay.ts` is the pure policy, unit-tested in `src/__tests__/games/freecell/autoPlay.test.ts`): the cascade and the finish, both started only by the player's play of a card to a foundation (the finish once the board is solved, above).
- **The safe-card cascade** (`useAutoFoundationCascade`, engine mechanism A) starts from the player's tap or drag of a card to a foundation. Like every game's cascade (see below), its cards overlap.
- **The finish** (`useAutoFinish`, engine mechanism B) starts as soon as the whole board can go up on foundation moves alone (`canAutoFinish` - every column sorted highest-to-lowest, freecell cards included) after the player's foundation play, or once the cascade it set off makes it so - without waiting for that play to land. It is a plain async loop like the cascade's (below): every card, the first included, leaves its ramped gap (`finishGapMs`, 96ms down toward 48) after the one before LEFT (the player's own, for the first), so several flights overlap. The hook holds back a card still flying in to its own pile (`isLanding`, e.g. a card the player's column move put there just before their foundation play - pinned by the `CLUBS_LEFT_TWO_ON_ACE` test, which fails without it), bounded by `FINISH_LANDING_WAIT_MS` (two flights). The board's LAST card does NOT wait for the earlier flights: it leaves one stagger after the card before it like every other. It used to hold until every flight had landed so the win cascade wouldn't start over cards in the air, which read as the stream, a pause, then one straggler (Jay, 2026-10-03). That wait was redundant anyway: the win cascade starts on `winRevealed`, which waits for `settled`. Pinned by `the last card leaves one stagger after the card before it...`. `nextSafeCascadeStep` returns null the moment the board is finishable, so the two never both fire at one settle.
- **Auto-played cards follow the player's card at once and overlap, in every game with auto-play** (`useAutoFoundationCascade`, FreeCell/Klondike/Yukon/Canfield/Forty Thieves). The cascade used to send one card per settle - each card waited for the one before it to LAND, the first one for the player's own (a full flight plus two measurements and a couple of renders each), which read as "way too slow" (Jay, 2026-10-02). Now it is a loop that starts the moment it is armed (its `[state]` effect runs right after the arming move's commit) and sends every card `AUTO_PLAY_STAGGER_MS` (96ms) after the one before - the first one 96ms after the player's own card, while that is still in the air - so ~5 cards are in the air at once. Because every flight takes the same time (see the flight-pace paragraph below), they land in exactly the order they left, and the gap is purely how quick the stream reads. The ONE thing a card waits for is its own pile to stop landing (`isLanding`, from `useFlightConcurrency`, kept live in `updateFlying` rather than read off a render): picking up a card whose own ghost is still airborne shows it twice (a card the sweep just drew onto the waste, a card the player just dropped there). A draw/draw-and-play waits the same way for the stock and the waste (the deal layer flies one draw-3 batch at a time; a second `deal.start` would cancel the first). After a wait the card goes at once, with no extra gap. The hook has no `settled` input any more; a wait that runs out (3s) ends the cascade (the next foundation play starts a new one). Every screen's `firePlay` resolves `true`/`false` (committed or not), for the miss count. One gap for every auto-played card: the old separate sweep gap and the `sweepingRef` latch are gone. Pinned by `useAutoFoundationCascade.test.tsx` and FreeCell's screen tests (`the follow-up cards leave one stagger apart...`). Not observed on a device.
- **A stock draw never sets it off** (Jay, 2026-10-09). Klondike, Canfield and Forty Thieves used to auto-play a drawn ace (Canfield: a drawn foundation-starter) straight up (`armFromAceEvent` in each `handleDrawStock`); that call is gone, and a player's draw or recycle (not a sweep's own draw, `opts.sweep`) calls `cascade.disarm()`, so a cascade still running from the player's last play can't take the card just drawn either. See the rule paragraph above for the rest (2026-10-11).
- **Every auto-played step is its own undo entry, in every game with auto-play** (FreeCell, Klondike, Yukon, Canfield, Forty Thieves), so one Undo takes back exactly one card and the player can stop where they like. Each silent foundation move, sweep draw and sweep recycle pushes an entry holding the board just before it; a draw-and-play (stock straight to a foundation) pushes TWO (the draw, then the waste->foundation play), so each undo is a move kind `handleUndo` already flies. Since 2026-10-14 each auto-play also counts as a move (see Scoring), and every `handleUndo` calls `cascade.disarm()` so an undone card doesn't fly straight back up. The old shapes (Klondike/Yukon/FreeCell folded auto-plays into the previous entry's `cascaded` list; Canfield/Forty Thieves left them off the stack, so they snapped back with the player's move) survive only as legacy-save handling: the `cascaded` undo paths and the buried-foundation-card lookups stay for saves written before this change. Spider's completed-run removal is a rule, not an auto-play, and still undoes with the move that completed it.
- **What suppresses it:** an undo, a resumed save and a new deal (`finish.suppress()`) - nothing finishes again until the player's next move (any move), so undoing back onto a finishable board can't immediately re-fire the cards just taken back. The player's move to a column or a freecell stops the CASCADE, not the finish (a move that keeps every column sorted lets the finish carry on). Both halves honor Settings' Auto-Move to Foundation. A resumed, already-finishable board sits until the player's next move.

**Undo is a queue, every press is one undo, and undos overlap each other's flights - a held Undo streams the cards back like the auto-play streams them up** (2026-10-07; Jay: holding Undo "only undoes one move every other click"). Every game's `handleUndo` used to refuse to start while ANY flight was in the air, and the hold repeated on a fixed 400ms `setInterval` (`@rific/feedback-press`'s `useHoldToRepeat`) against a ~540ms real undo flight: every other tick was dropped, and still clicked. Now:
- **`useFlightConcurrency`'s `runUndo(gate, run, opts)`** (every screen's `handleUndo` is just `runUndo(undoGate, revertTopUndo, opts)`): requests queue and run one at a time, in order; `run` (the screen's revert of the TOP entry) starts synchronously when it can, so a lone undo behaves exactly as before. `undoBusyRef` is now held from the REQUEST until every undo is done and its flights have landed (every other action still refuses/bails on it; the cascade and finish hold back on it), and a request that cannot start waits instead of being dropped - refused only when there is nothing to undo, when `opts.cancelled()` turns true, or after `UNDO_MAX_WAIT_MS` (3s, then `undoBusyRef` is let go). `reset()` (New Game/restore) and unmount refuse everything queued (`undoEpochRef` guards a revert still awaiting its measurements). A press event handed in as `opts` is ignored (only a real `cancelled` function counts).
- **The first undo waits for every flight in the air, as undo always did; from then on nothing but an undo can start one** (`undoStreakRef`), so each later undo checks only its own entry's **`UndoGate`**: `{ takesFrom }` starts as soon as nothing is LANDING on those piles (`isLanding` - picking up a card whose own ghost is still airborne shows it twice; the same rule the auto-play cascade follows), `'exclusive'` waits for everything to land and holds every later undo until its own flights have landed (what undo used to be for every entry), `'blocked'` waits for a reason of the screen's own (Spider's pending sweep), `null` = nothing to undo. Landing order stays FIFO because every undo flight is `FLIGHT_SPRING`, so the count-based destination hiding (`flying` entries) still reveals the right card when two undos land on one pile. **Per game:** a plain one-move revert through the ghost layer is `{ takesFrom: [move.to] }` everywhere (FreeCell, Yukon, Scorpion, Spider, Aces Up incl. the discard, draw-1 undos in Klondike/Canfield/Forty Thieves/Golf/TriPeaks); one that LANDS on the waste adds the waste (`[move.to, WASTE]` - its frozen-top bookkeeping expects one arrival at a time; Golf/TriPeaks never land on it); Pyramid's removals are `{ takesFrom: [] }` (+ `[WASTE]` for a waste-bound card - nothing lands on the discard during an undo) and its draws `[WASTE]` (overlapping draws share the one `stockHidden` flag: the first landing unfreezes the stock while a later back is still flying in, which shows a back that is already there). **`'exclusive'`:** every deal-layer revert (draw-3 fans, Spider/Scorpion stock deals, Aces Up rounds - a second `deal.start` cancels the first), recycles, Spider's run completions, legacy entries with a `cascaded` list (their single-slot `pendingCascadeUndoRef`), and every `move: null` entry. A NEW kind of undo entry needs a deliberate gate - `'exclusive'` if in doubt.
- **Reverts read the stack and board through refs, never the render closure** (several undos can run between two renders): `useUndoStack` (`games/shared/useUndoStack.ts`, a `useState` whose stable setter also updates `undoStackRef` synchronously - every write must go through it) and `stateRef`; `resolvePile` takes the live board (`resolvePile(ref, current)`), Spider's `finishMoveUndo(current, ...)` too.
- **The hold is `components/undoHold.ts`'s `useUndoHold`, not `useHoldToRepeat`:** undo at the long press, then the next one `UNDO_HOLD_REPEAT_MS` (= `AUTO_PLAY_STAGGER_MS`, 96ms) after each undo has STARTED (the request resolves at its commit); it passes `cancelled` = "the finger lifted", so releasing never lets one more through; it stops at the first refused request (nothing left), at press-out and on unmount. It has no click of its own: each undo's card sound + haptic is the feedback, so there is exactly one per card that comes back. `GameChromeProps.onUndo` is an `UndoHandler` (`(opts?) => Promise<boolean> | void`); its tap is `onPress={() => void onUndo()}`.

Two things seen there are pre-existing, not this change: a legacy `cascaded` entry's auto-plays fly back on the DEAL layer, which paints above every DragGhostLayer ghost and has no take-off hold - the cascaded card was visible nowhere for ~2 frames and drawn over the primary card landing on it (see "Not covered" in the take-off/landing paragraph below); and a draw-undo ghost shows its face on the stock for ~100-200ms before the back. Pinned by `useFlightConcurrency.test.tsx` (the runner, against a stand-in screen), `undoHold.test.tsx`, FreeCell's `undos pressed back to back ...` / `an undo pressed while the tapped card is still flying ...`, and Pyramid's/Spider's "undo waits" cases (which used to assert a refusal).

**Every card flight takes ONE fixed time, there is ONE pace knob, and a ghost is only ever retired at its spring's REAL end.** `dragdrop/dragSpring.ts`'s `FLIGHT_SPRING` (scale-1 225ms = 360ms at the default) is every flight: tap-to-move, undo, draw-1, a recycle, every auto-played and finish card (`DragGhostLayer`'s `flyTo` on a `show()` flight), Pyramid's pair flights (`FlyingPairCard`), Spider's completed-run flights (`FlyingSequenceCard`) and Klondike's/Canfield's draw-3 fans and their undo (through the deal layer: `DealAnimator.start`'s optional 6th `spring` argument, which also sizes the ghost pool and times the landing check) - however far it goes (Jay, 2026-10-01). Distance-scaled flights let a short hop overtake a long one to the same pile (two quick taps, or an auto-played card after a tap), and `FoundationCell`'s `settledCard` counts in-air cards, so the overtaken card showed on the pile while still airborne; and once flights overlap, a stream's pace is its gap, not its flight. Two exceptions: **a drag's drop** (`flyTo` on a `showLive()` flight - `flyTo` takes no pace options, it decides by `source`) settles over `dropSpringFor(the distance the finger left)` (scale-1 130-320ms = 208-512), because the card is usually nearly there and a full flight would leave the ghost covering the real card after every drag; and **everything else through the deal layer** (`DEAL_SPRING`, 280ms, unscaled - `start`'s default: deals, Spider/Scorpion stock deals, Aces Up rounds, Pyramid's win sweep, Klondike's legacy cascade-return undo). `SNAP_BACK_SPRING` (240ms) is unchanged too. `FLIGHT_TIME_SCALE` (1.6) multiplies the flight and drop durations. `scaledMs(ms)` is how any constant that must follow a flight derives from it (never hard-code a second copy): `AUTO_PLAY_STAGGER_MS` (`scaledMs(60)` = 96) and `FINISH_STAGGER_MS` (`scaledMs(30)` = 48, the solved-board finish's top speed), so the auto-play streams overlap their flights the same way at any pace, `useAutoFinish`'s `FINISH_LANDING_WAIT_MS` (2 x `springSettleMs(FLIGHT_SPRING)` = 966), `GameChrome`'s `UNDO_HOLD_REPEAT_MS` (= `AUTO_PLAY_STAGGER_MS`, see the undo paragraph above), Pyramid's `DEFER_MAX_WAIT_MS` (3 x a flight's settle = ~1.45s, so a deferral can never expire before its own draw ghost can land) and `SWEEP_WIN_REVEAL_MAX_WAIT_MS` (twice the nominal last-removal + sweep + hold timeline). Deliberately NOT scaled: `DEAL_SPRING`/`dealStaggerMs` (the deal), `SNAP_BACK_SPRING`, `useWinReveal`'s 400ms hold (a beat after the LAST landing, whatever the pace) and its 2.5s max wait (still ~3.7x the slowest single flight), `useCascadeFeedback`'s 45ms floor (a sound-pool limit, not a pace). **Reanimated's duration-based `withSpring` `duration` is the PERCEPTUAL duration: the spring really runs 1.5x that** (springUtils.ts's `perceptualCoefficient`), **and its solver caps stiffness at 8000, which with the default mass of 4 is reached at ~184ms: every shorter duration silently ran as the SAME ~283ms spring.** So the old 40-170ms (scale 1) sweep/auto-play flights were ~283ms springs whose ghost was retired at 40-170ms, with up to ~180px still to travel - the "cards vanish partway through" report. `FLIGHT_SPRING_MASS` (0.1) lifts the cap (critically damped motion depends only on sqrt(stiffness/mass)); the springs are exact down to ~30ms. Every timer that covers a spring uses `springSettleMs(config)` = `ceil(1.25 x duration + 33)`, never the bare `duration` (`DragGhostLayer`'s `settleAfter` - snapBack included - Pyramid's `FlyingPairCard`, Spider's `FlyingSequenceCard`; the deal's own timer is left at the bare `DEAL_SPRING` duration - measured 2.5px short of a 300px flight (7px of 900px) with the spring two frames late, judged not visible; a deliberate follow-up if it ever is): the 1.25 puts the tail under 0.4px for any distance, and the 33ms (two 60Hz frames) is the UI thread starting the spring after the JS timer that covers it - absolute, so it is added rather than folded into the factor (a flat 1.3 leaves 2.6px of a 100px sweep flight). `src/__tests__/components/dragSpring.test.ts` drives Reanimated's OWN `withSpring` frame by frame and requires < 1px residual at the retire time for every config at 60-900px (worst 0.68px, with the spring starting two frames late; the old timer left 50-310px on the sweep tier), and that every flight really ends at 1.5 x its duration. **Same-source hand-off rule (`DragGhostLayer.tsx`):** `showLive`'s persistent gesture values are shared by every drag from one slot/column, so a flight only sits on them WHILE ITS DRAG IS IN PROGRESS - `DragFlightHandle.release()` (called by `PileView`/`DraggableCard` as the first thing at drag end, before any await: a drop can sit in a hit test, a measurement or Pyramid's deferral for hundreds of ms) hands the ghost values of its own holding the same position. The ghost reads BOTH value sets from its first render and a `handedOff` shared value, written last, switches it (no re-render, no remount, no seam - cloning values under a mounted ghost, tried before, needs a re-render and jumps). After release a next drag from the same source can never touch the flight, applied or not; only a SNAP-BACK in progress (the very card being picked up again) and a drag that never released are still ended by a new claim (`liveOwnersRef`). `PileView` also captures its drag's own flight BEFORE the hit-test await (it used to read `flightRef` after it, so an overlapping drag's drop was applied with - and flew - the wrong ghost), and both `PileView` and `DraggableCard` stamp each drag with a token so a late drop/snap-back outcome never un-hides the cards under a NEWER drag. ## Scoring (audited 2026-10-14)

- **Score = moves + seconds, lower is better** (`engine/score.ts`'s `computeScore`, the one formula: GameChrome's readout, WinBanner, the recorded stat).
- **A move** is one `session.registerMove()`: every board change a player could make, tap or drag, a stock draw or recycle, a Spider/Scorpion stock deal, an Aces Up round, a Pyramid pair or King, AND every auto-play (the cascade, the solved-board finish, the draws-aware sweep's draws, recycles and draw-and-plays, which count as two) - Jay, 2026-10-14: with auto-plays free, turning Auto-Move off raised the score; now it only saves taps. NOT counted: Undo presses (and an undo never takes a move back off the count), hints, Spider's run removal and Pyramid's win sweep (rules, not moves a player could make).
- **Variants** (`engine/variants.ts`): one game under one rule set, the unit stats are kept in (`StatsState.variants` is keyed by `VariantId`) and par is set for. A game's DEFAULT variant keeps the bare game id (`'klondike'` = Draw 1, `'spider'` = 1 Suit, `'canfield'` = Draw 3, `'scorpion'` = Assisted...), so stats from before variants carry over into it with no migration; the rest are `<game>-<rule>` (`'klondike-draw3'`, `'spider-4suit'`...). Each screen names its deal's variant from the rule it was DEALT with (its own state, e.g. `klondikeVariant(klondikeDraw)`), not the live setting, and passes it to the win/loss hooks and every `record*` call; the hooks derive the game (`gameOfVariant`) for the save. Per-game figures ("Klondike Solved", Games Solved, totals) sum over a game's variants (`getGameWins`/`getGamesWon`); streaks are per variant. The Stats screen shows each game's default variant always and the others once played.
- **Par** (`engine/par.ts`, `parFor(variant)` = `{ moves, seconds, score }`): moves = the median winning move count of a simulated Hint-following player (a little randomness, up to 10 tries per deal, 300 deals per variant, on the real `rules.ts`; 2026-10-14), seconds = the moves a player decides (all but foundation plays in the five auto-play games) x `SECONDS_PER_DECISION` (3, the one time knob), score = moves + seconds. ESTIMATED, not measured: Spider 2/4 suit and both Forty Thieves rules (the simulated player never won), and Golf No Wrap / Aces Up rest on 9 and 2 wins. **Re-measure with `npm run par`** (`scripts/simulate-par.mjs`, ~40s, deterministic; `--only <prefix>`, `--deals`, `--tries`) after any change to a game's rules or to Hint: it bundles the real rules with esbuild (with `@tastic/cards` aliased to its plain `src/types.ts`) and prints a PAR_INPUTS block to paste, commenting out variants with under 20 wins. A new variant needs a controller in its `CONTROLLERS` map or it stops. Shown in WinBanner (under each number, plus "N% under par"), the Rules sheet's Scoring paragraph (GameChrome's `par` prop; Home's sheet has none) and the Stats screen. The speed/fewest_moves/low_score achievements (same ids, so unlocked tiers stay) are now best/par ratios across every variant (`getBestParRatio`): at par / 20% / 40% under on time, at par / 5% / 10% on moves, at par / 20% / 35% on score; the Overall section shows one "Best Score" vs par instead of the raw cross-game bests, which only ever named the quickest game.
- **The clock** (`useGameSession`) starts with the first move, stops at the winning commit (Spider: the winning move, before its last run sweeps), and PAUSES while anything holds it (`setPaused(reason, paused)`, a set of reasons): `'app'` whenever the app is not `active` (a call, the app switcher, the home screen), and `'dialog'` while GameChrome's Rules or Settings is open (Jay, 2026-10-14; the New Game confirm doesn't pause). A first move or a resume made while held starts held. It used to keep running in the background, so time away counted only when the OS kept the app alive. Elapsed is banked in ms, so pauses don't drop part-seconds. Time on Home doesn't count either: the game screen unmounts and its save holds the elapsed time it was left at.
- **A save holds the elapsed time from when it was MADE**, so `useSaveInProgressBackstop` saves again (through the screen's own guarded `save`) on unmount and when the app leaves the foreground, as well as every 10s. Before, leaving a game handed back up to 10s of clock every trip.
- **Win recording reads `session.getMoves()`/`getElapsed()`**, never a render's `session.moves`: an auto-played winning card commits after a measurement await, and a move the player made during it is only in the live count (`checkWin(next)` takes no move count any more).
- **Losses:** `record.losses` (labelled "Lost" on the Stats screen) is both a New Game over a deal in progress and a dead board (`useStuckLossCheck`). Both use `recordDealAbandoned`. **A dead board's loss is recorded when the player LEAVES it** (Jay, 2026-10-14): New Game (each screen's `handleNewGame`, which the LossBanner's New Game also calls) or leaving the screen (`useStuckLossCheck`'s unmount, which also clears the save). Undo out of it cancels it. It used to be recorded on arrival, which counted one deal twice after an Undo (a loss plus a win, or two losses). The dead board is never saved (the saves skip `stuck`), so a killed app resumes one move before it, the same as an Undo.
- Pinned by `components/gameSession.test.tsx`, `components/stuckLossCheck.test.tsx`, `gameChromeHowToPlay.test.tsx` (the dialog hold), `statsEngine.test.ts` (variants, par ratios), `games/shared/winBanner.test.tsx`, and the five auto-play games' screen tests (move counts).

## Hints (2026-10-14)

- **No more ping-pong.** Every game's `scoreHintMove` measures a move's runs the same way before and after it (`a` = the run the moving group's base card continued at its source, `b` = the run it lands on, net = max(count + b, a) - max(count + a, b)), so a move and its exact reverse score as opposites and a relocation that gains nothing scores 0; the size tiebreak only applies to a score already above 0. Aces Up gained a scorer (it had none, so Hint showed a lone card to the empty pile and back). Scorpion's already-complete K-A column moved whole into an empty column no longer earns the completion bonus. Klondike and Forty Thieves also score a waste play onto a column (it scored 0, so Hint drew instead); Forty Thieves' waste card into an empty column still scores 0. On top of that, `findHint` never suggests a SHUFFLE (`isShuffle`: scores 0 or less and its exact reverse is legal right after), which is what kept the ping-pong going on boards with nothing to draw (Yukon, FreeCell, Spider with an empty column, Scorpion's dealt stock); if that leaves nothing, Hint draws or reports none ("No helpful moves right now."). A followed-Hint simulation over 200 deals per game: Canfield, Aces Up and FreeCell 0 reversals; Yukon 20, Spider 1-suit 39, Spider 4-suit 8, Scorpion 8-9 (from thousands each), all after a move that turned a card over, which can't really be undone. Each game's `rules.test.ts` pins its case, `engine.test.ts` the shuffle filter. **Known, not fixed:** Spider's Hint never suggests filling an empty column so the stock can be dealt again; Aces Up's `isStuck` never declares a loss while a lone card can still move to an empty pile, though that move can never lead to a discard.
- **A run gets ONE outline, not a ring per card** (Jay, 2026-10-14), for a hint and a selection alike: `PileView` draws `RunOutline` (PlayingCard.tsx, the same `hintRing`/`selectedRing` style, so it looks like one card's ring stretched over the run) over the run's own box from `columnTops` (head's top to the bottom card's bottom, zIndex above every card, `layout={FAN_GLIDE}` so it glides with the column), and the run's cards draw no ring of their own. Per-card rings drew a ladder of lines across a run, and each hint glow spilled over the face of the card above. A single card keeps its own ring; a selection wins over a hint (as on one card); no outline while any card of the run is hidden. No screen passes a `selectedCount` above 1 today, so only hints show it. Pinned by `pileViewRunOutline.test.tsx`; the outline was NOT looked at on the simulator (the simulator tool's taps arrive late and kept landing on the wrong screen).
- **The ring marks only what to move** (`hintCountFor` rings the source run, never the destination; Pyramid rings both cards of a pair, `pairHinted`, since both leave), with a soft glow (`boxShadow` on `PlayingCard`'s `hintRing`) that breathes with the ring (`startHintPulse`, 1100ms to 0.4 and back). **Its color is the app theme's tertiary, lifted** (Jay, 2026-10-14: a theme color, muted like everything else, and not the card back's own hue, or a ringed card in a stack blends into the backs beside it): `theme.ts` fills TableColors' `hintGreen` slot (the name is `@tastic/cards`' type; nothing in that package draws it) with `getTonalColor(getTriadicPalette(cardBack, THEME_HARMONY).tertiary, HINT_RING_TONE)`. `ProfileThemeSync` seeds the Paper theme with that same muted card back, so this IS the theme's tertiary, only lighter (`HINT_RING_TONE` 0.62 in `constants/theme.ts`, so it reads on the dark felt by lightness, not hue alone). The card back is the theme's primary; the felt stays the card back's 180-degree opposite (Jay kept it over a triad felt), so the ring sits 120 degrees from the back and 60 from the felt. The guide's `GuideHint` uses the same color. Pinned by `hintRingColor.test.tsx` (8 profile colors, light and dark).
- **The glide** (Jay: "a ghost animation of one card going to another"): each press of the Hint button shows a see-through copy (0.7 opacity) of the hinted card or run lifting off, gliding onto where it would land (`HINT_GLIDE_MS` = `scaledMs(300)`) and fading there; the real cards never move. `components/hinting/HintGlideLayer.tsx` (`HintGlideProvider`, innermost in `withGameProviders`, so it paints over the board and under every real flight) draws it; `games/shared/useHintGlide.ts` measures the anchor card (CardRegistry) and the landing spot: the destination's top card (one fan step below it in a column, at the step the column uses now, `fanTops.ts`), an empty pile's drop zone, or a card-sized container for a spot that isn't one (Aces Up's and Pyramid's discard, `measureSlot`). It claims nothing, hides nothing and registers nothing, so no flight or undo waits on it; a board change drops it (on screen or still measuring). A drawStock hint has no glide (the stock is ringed), and neither has an Auto Hint (2026-10-15, Jay: the button shows the ghost and the outline, Auto Hint just the outline; each screen's `handleHint` skips `playHintGlide` on `request.auto`). Pinned by `hintGlide.test.tsx` and `klondikeScreenWin.test.tsx`'s `hint` describe. Seen working on the web build (mounted on the ringed card, retired on time); the motion itself was NOT watched (the browser pane was hidden, so no frames were drawn), and nothing was checked on a device.
- **Auto Hint** (`Settings.autoHintSeconds`: 0 = Off, 15, 30; default Off; a Settings row that steps through them): `components/autoHint.ts`'s `useAutoHint`, run by `GameChrome`, asks for a hint once the board (`autoHintKey`, each screen's state object) has sat unchanged that long. ## Top rows (2026-10-11)

- **FreeCell and Forty Thieves split their top row into two groups** (foundations | freecells; foundations | waste + stock). The row is as wide as the tableau, each group's cards sit at HALF the tableau's gap (`cardLayout.ts`'s `splitTopRowGroupGap`), and what that saves pools between the groups (space-between): `columns * gap / 2`, 16pt for FreeCell and 20pt for Forty Thieves on a phone. So there is something to squeeze, both size their tableau with `SPLIT_TOP_ROW_MIN_GAP` (4pt) as `cardLayoutForRow`'s and `useFittedGap`'s `minGap`: ~1.75pt of card width on a 402pt phone (FreeCell 48 -> 46.25, Forty Thieves 38 -> 36.2), nothing in the wide layout (its gap is already spread). Smaller top-row cards (Jay's first idea) were not built: every ghost layer (DragGhostLayer, DealLayer, WinCascadeLayer) flies a card at one size, so each card crossing between the rows would pop at its landing or need a mid-flight scale in all three. ## OS portrait lock (2026-10-08)

The OS is locked to portrait on every device and the app draws all rotation itself (`@tastic/core`'s `OrientationProvider` reads the accelerometer). `@tastic/core`'s Expo config plugin (`"@tastic/core"` in `app.json`'s `plugins`) owns every native setting that depends on: `orientation: "portrait"`; `ios.requireFullScreen` plus a Portrait-only iPad orientation list (audit F009: without it Expo forces all four iPad orientations, so iOS turned the screen on top of the app's own rotation, and Split View, Slide Over and Stage Manager are the price); and `android:appCategory="game"` (Android 16 and later ignore the portrait lock on tablets and unfolded foldables, except for games). Don't set any of those by hand here, and don't add `expo-screen-orientation` (it re-enables upside down on home-button iPhones). The why behind each is in @tastic/core's README. Check the result with `npx expo config --type introspect`; it only takes effect in a new native build.

## iOS 27 on SDK 57 (remove on Expo SDK 58)

`eas.json` pins the `preview` and `production` iOS builds to `macos-tahoe-26.5-xcode-26.6` (set fleet-wide 2026-10-14). An app linked against the iOS 27 SDK aborts at launch on iOS 27 ("UIScene life cycle is required for apps built with this SDK") unless it adopts the UIScene life cycle, which SDK 57's native template doesn't do and SDK 58's does. A build made with Xcode 26 runs fine on iOS 27. **When this app moves to Expo SDK 58, remove both `ios.image` pins and this section**, so builds go back to EAS's default image for the SDK. Local builds (`jrd ship build development`, or any profile with `--local`) use this Mac's default Xcode 27 instead, made safe by `plugins/withSceneDelegate.js` (listed in `app.json`, 2026-10-15; Jay's phone went to iOS 27 and a local build crashed at launch, and he chose this over keeping Xcode 26 plus its iOS platform, ~15 GB, or spending cloud builds). SDK 57's `expo` package already ships `ExpoAppSceneDelegate` (creates the window, starts React Native, forwards links, user activities and quick actions, `RCTLinkingManager` included) and `ExpoReactNativeFactoryProvider`, but its template never wires them; the plugin makes SDK 58's template changes on the prebuild: `AppDelegate` conforms to `ExpoReactNativeFactoryProvider` and no longer creates the window, starts React Native or overrides the Linking/Universal Links methods, `Info.plist` gets the `UIApplicationSceneManifest` pointing at `$(PRODUCT_MODULE_NAME).SceneDelegate`, and `SceneDelegate.swift` (a bare `ExpoAppSceneDelegate` subclass) joins the app target. It throws if `AppDelegate.swift` isn't the stock template (so a template change or another plugin's edit fails loudly, not half-applied) and does nothing on SDK 58+. Verified on the iOS 27 simulator with a Release build linked against the iOS 27 SDK: launches to Home, a `solitairesuite://achievements` link opens Achievements, and backgrounding then reopening resumes the same process. Not verified: a real device, a link that cold-starts the app, a Debug (Metro) build. A local `production` build uses no EAS build; upload it with `eas submit --path` or Transporter (the App Store only takes builds from a released Xcode). **On SDK 58, delete the plugin and its `app.json` entry, and drop both `ios.image` pins.**
